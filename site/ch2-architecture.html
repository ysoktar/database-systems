Mimari ve veri modelleri

Bir DBMS veriyi kullanıcıya hangi soyutlama düzeylerinde gösterir? Şema ile veri neden ayrıdır ve bu ayrım programları değişikliklerden nasıl korur?

Veri modelleri

Data model (veri modeli): bir veritabanının yapısını tanımlamak için kullanılan kavramlar topluluğu: veri tipleri, ilişkiler ve kısıtlar. Çoğu model ayrıca temel işlemleri (basic operations) ve kullanıcı tanımlı işlemleri (dynamic aspect / behavior) içerir.

Şema, durum (state), örnek (instance)

  • Database schema: veritabanının tanımı. Tasarım sırasında belirlenir, nadiren değişir. Şemanın çizilmiş hâline schema diagram, her nesnesine schema construct denir.
  • Database state (snapshot, current set of occurrences/instances): belli bir andaki veri. Her güncellemeyle değişir.
  • Empty state: şema tanımlandı ama veri yok. Initial state: ilk yükleme. Valid state: şemanın yapısına ve kısıtlarına uyan durum.
  • Şema = intension, durum = extension.
  • Schema evolution: gereksinimler değişince şemanın değişmesi (ör. EMPLOYEE'ye bir sütun eklemek). DBMS'lerin çoğu bunu destekler: ALTER TABLE (Ch 7).

COMPANY'de: EMPLOYEE(Fname, …, Ssn, …, Dno) tanımı şemadır. Bugün 8 çalışan var: bu bir state. Yeni bir çalışan eklemek (INSERT) şemayı değil durumu değiştirir. Email sütunu eklemek (ALTER TABLE) ise şemayı değiştirir.

Aşağıdaki kutu farkı COMPANY üzerinde gösteriyor (SQL komutlarını Ch 6'da ayrıntılı göreceksiniz; burada yorum satırlarını okumanız yeterli). Önce EMPLOYEE'deki satırları sayar (8), sonra bir çalışan ekler (INSERT) ve yeniden sayar (9): durum değişti. Ardından katalogdan EMPLOYEE'nin sütunlarını okur: hâlâ aynı on sütun, yani şema değişmedi. Son komut eklenen satırı siler, böylece COMPANY ilk hâline döner ve kutu tekrar çalıştırılabilir.

-- the current state: 8 employees
SELECT COUNT(*) AS employees FROM EMPLOYEE;
-- an update changes the state ...
INSERT INTO EMPLOYEE (Fname, Lname, Ssn, Dno) VALUES ('Ayşe', 'Yılmaz', '111222333', 5);
SELECT COUNT(*) AS employees FROM EMPLOYEE;
-- ... the schema (the columns, read from the catalog) is still the same
SELECT COLUMN_NAME FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'company' AND TABLE_NAME = 'EMPLOYEE' ORDER BY ORDINAL_POSITION;
-- undo the insert, so that the box can be run again
DELETE FROM EMPLOYEE WHERE Ssn = '111222333';

Üç-şema mimarisi (three-schema architecture)

Amaç: kullanıcı uygulamalarını fiziksel veritabanından ayırmak. Şema üç düzeyde tanımlanır:

  1. Internal level (iç düzey) → internal schema: fiziksel depolama yapısı; physical data model ile tam ayrıntı: dosyalar, kayıt biçimleri, erişim yolları.
  2. Conceptual level (kavramsal düzey) → conceptual schema: tüm veritabanının, bütün kullanıcılar için yapısı. Fiziksel ayrıntıyı gizler; varlıkları, tipleri, ilişkileri, işlemleri ve kısıtları anlatır. Genellikle bir representational modelle (ör. ilişkisel) uygulanır.
  3. External level (dış düzey, view level) → birden çok external schema (user view): her biri bir kullanıcı grubunun ilgilendiği kısmı gösterir, gerisini gizler.

Düzeyler arasındaki istek ve sonuç dönüşümlerine mapping denir: external/conceptual mapping ve conceptual/internal mapping. Mapping'ler ek yük getirir; bu yüzden bazı DBMS'ler external düzeyi tam desteklemez.

Veri bağımsızlığı (data independence)

Tanım: bir düzeydeki şemayı, bir üst düzeydeki şemayı değiştirmek zorunda kalmadan değiştirebilmek.

Logical data independence (mantıksal): conceptual şemayı external şemaları ve uygulama programlarını değiştirmeden değiştirebilmek. Ör. bir tabloya sütun eklemek, bir kayıt tipini kaldırmak, bir kısıt eklemek; sadece view tanımları ve mapping'ler değişir. Gerçekleştirmesi daha zordur, çünkü programlar mantıksal yapıya bağlıdır.

Physical data independence (fiziksel): internal şemayı conceptual şemayı değiştirmeden değiştirebilmek. Ör. bir index eklemek, dosyayı yeniden düzenlemek, farklı bir depolama aygıtına taşımak. Sorgular aynı sonucu (belki daha hızlı) verir. Çoğu DBMS'te iyi desteklenir.

İki bağımsızlığı da COMPANY üzerinde deneyebilirsiniz. İlk kutuda EXPLAIN, DBMS'in bir sorguyu nasıl çalıştıracağını (yürütme planını) gösterir; sonucu değil. Index eklenmeden önce plan tablonun tamamını tarayıp satırları süzer (Filter + Table). CREATE INDEX internal şemaya yeni bir erişim yolu ekler; plan artık index'i kullanır (IndexedTableAccess). Sorgunun kendisi ve sonucu ise aynıdır.

-- the query plan before: scan the whole table, keep the rows with Lname = 'Wong'
EXPLAIN FORMAT=TREE SELECT * FROM EMPLOYEE WHERE Lname = 'Wong';
-- a change to the internal schema (a new access path)
CREATE INDEX emp_lname_idx ON EMPLOYEE (Lname);
-- the query plan after: the new index is used
EXPLAIN FORMAT=TREE SELECT * FROM EMPLOYEE WHERE Lname = 'Wong';
-- the same query still gives the same answer
SELECT Fname, Lname FROM EMPLOYEE WHERE Lname = 'Wong';
-- undo, so that the box can be run again
DROP INDEX emp_lname_idx ON EMPLOYEE;

Plan metnini bu sitedeki motor (go-mysql-server) üretir; gerçek MySQL'in EXPLAIN FORMAT=TREE çıktısı farklı biçimdedir ama aynı şeyi anlatır: önce tam tarama, sonra index ile erişim.

İkinci kutuda bir kullanıcı grubu için bir external şema, yani bir view tanımlanıyor (Ch 7'de ayrıntılı): bu grup yalnızca çalışan adını ve departman adını görür. Sonra kavramsal şema değişiyor: EMPLOYEE'ye bir sütun ekleniyor (ALTER TABLE). View'u kullanan sorgu hiç değişmeden aynı sonucu vermeye devam ediyor.

-- an external schema for a user group: name and department name only
CREATE OR REPLACE VIEW EMP_DEPT AS
  SELECT E.Fname, E.Lname, D.Dname
  FROM   EMPLOYEE E JOIN DEPARTMENT D ON E.Dno = D.Dnumber;
SELECT * FROM EMP_DEPT WHERE Dname = 'Research';
-- the conceptual schema changes: a new column
ALTER TABLE EMPLOYEE ADD COLUMN Email VARCHAR(40);
-- programs that use the view do not notice
SELECT * FROM EMP_DEPT WHERE Dname = 'Research';
-- undo, so that the box can be run again
ALTER TABLE EMPLOYEE DROP COLUMN Email;
DROP VIEW EMP_DEPT;

DBMS dilleri

DilNe tanımlar?
DDL (data definition language)Conceptual (ve iç/dış ayrımı net olmayan sistemlerde hepsi) şemayı. SQL'de CREATE, ALTER, DROP.
SDL (storage definition language)Internal şemayı. Günümüz ilişkisel DBMS'lerinde ayrı bir dil yoktur; parametreler ve komutlarla (ör. CREATE INDEX) yapılır.
VDL (view definition language)External şemaları. SQL'de CREATE VIEW.
DML (data manipulation language)Erişim ve güncelleme: retrieval, insertion, deletion, modification. SQL'de SELECT, INSERT, UPDATE, DELETE.
  • High-level / nonprocedural DML (set-at-a-time, declarative): ne istendiğini söyler, nasıl bulunacağını değil. Tek komut birçok kaydı döndürür. Ör. SQL. Tek başına etkileşimli kullanılabilir ya da bir programa gömülebilir (embedded; o zaman program dili host language, DML data sublanguage olur).
  • Low-level / procedural DML (record-at-a-time): kayıtları tek tek getirir; döngü gibi programlama yapılarıyla birlikte kullanılmak zorundadır. Ör. eski ağ modeli DML'i (DL/1).
  • Query language: etkileşimli kullanılan high-level DML.
  • SQL, DDL + VDL + DML'i (ve kısıt, yetki tanımlarını) tek dilde birleştirir.

DBMS arayüzleri

Menü tabanlı (web) arayüzler, apps for mobile devices, formlar, grafik arayüzler (GUI), doğal dil arayüzleri, keyword-based search, konuşma girdisi/çıktısı, parametric users için arayüzler (az tuşla hazır işlemler) ve DBA için arayüzler (hesap oluşturma, yetki, şema değişikliği gibi ayrıcalıklı komutlar).

DBMS ortamı ve bileşenleri

Kitaptaki Figure 2.3'ün özeti: üstte kullanıcılar (DBA, casual, programmer, parametric), ortada derleyiciler ve işlemciler, altta depolama:

  • DDL compiler: şema tanımlarını işler, meta-data'yı system catalog'a yazar.
  • Interactive query interface → query compiler → query optimizer: sorguyu ayrıştırır, doğrular, verimli bir yürütme planına çevirir.
  • Precompiler: uygulama programına gömülü DML komutlarını ayıklar; DML compiler bunları derler; geri kalan kod host dil derleyicisine gider. Hepsi canned transaction'lara bağlanır.
  • Runtime database processor: planları ve canned transaction'ları çalıştırır; stored data manager ve buffer management üzerinden diske erişir.
  • Concurrency control / backup / recovery subsystems runtime işlemciyle birlikte çalışır.
  • Database system utilities: loading (dosyaları veritabanına yükleme), backup, database storage reorganization, performance monitoring; ayrıca sorting, data compression, user monitoring.
  • Diğer araçlar: CASE araçları, data dictionary / repository sistemleri (tasarım kararları, kullanım standartları da saklanır), uygulama geliştirme ortamları, iletişim yazılımı.

Merkezi ve istemci/sunucu mimariler

  • Centralized: tüm DBMS işlevleri, uygulamalar ve arayüz tek bir sistemde (eskiden mainframe; terminaller sadece ekran).
  • Basic client/server: specialized servers (file server, printer server, web server, DBMS server …) ve bunlara bağlanan client'lar.
  • Two-tier client/server: kullanıcı arayüzü ve uygulama programları istemcide; sorgu ve transaction işlevleri sunucuda (query server / transaction server; ilişkisel DBMS'te SQL server). Bağlantı ODBC ya da JDBC gibi bir API ile.
  • Three-tier / n-tier (web uygulamaları): istemci (GUI, web tarayıcı) ↔ application server / web server (iş kuralları, ara katman) ↔ database server. Ara katman güvenliği artırır (istemci doğrudan veritabanına erişmez). n-tier'da iş mantığı daha çok katmana bölünür.

DBMS sınıflandırması

  • Veri modeline göre: relational (en yaygın), object, object-relational, NoSQL (key-value, document, column-based, graph), hiyerarşik ve ağ (legacy), XML.
  • Kullanıcı sayısına göre: single-user ve multiuser.
  • Dağıtıma göre: centralized (veri tek yerde) ve distributed (DDBMS; veri ağdaki birçok sitede). Homogeneous (her yerde aynı DBMS) ya da heterogeneous; federated (multidatabase) sistemler bağımsız DBMS'leri gevşekçe birleştirir.
  • Maliyete göre: açık kaynak (MySQL, PostgreSQL), ticari (Oracle, SQL Server, DB2), farklı lisans türleri.
  • Erişim yolu tipine ve amaca göre: general-purpose ve special-purpose (ör. eski hava yolu rezervasyon sistemleri: OLTP, online transaction processing).

Kendinizi sınayın

EMPLOYEE tablosuna yeni bir index eklendi; tüm uygulamalar hiç değiştirilmeden aynı sonuçları vermeye devam ediyor. Bu, hangisinin örneğidir?

  1. Logical data independence
  2. Physical data independence
  3. Self-describing nature
  4. Program-operation independence
Index bir erişim yoludur, yani internal şemanın parçasıdır. Internal şema değişti, conceptual şema aynı kaldı: bu fiziksel veri bağımsızlığıdır.

Hangisi intension ile extension'ı doğru eşleştirir?

  1. Intension = veritabanı durumu; extension = şema
  2. Intension = internal şema; extension = external şema
  3. Intension = şema; extension = veritabanı durumu
  4. Intension = DDL; extension = DML
Şema veritabanının tanımıdır (intension) ve nadiren değişir. Durum (state), belirli bir andaki veridir (extension) ve her güncellemeyle değişir.

CREATE VIEW hangi dil kategorisine ve hangi şema düzeyine karşılık gelir?

  1. VDL, external şema
  2. DDL, internal şema
  3. SDL, conceptual şema
  4. DML, external şema
View, kullanıcı grubuna özel bir görünümdür: external düzey. Onu tanımlayan dil VDL'dir. SQL'de VDL, DDL'in bir parçası gibi görünse de kavramsal olarak ayrıdır.

Bir web uygulamasında tarayıcı → uygulama sunucusu → veritabanı sunucusu düzeni hangi mimaridir?

  1. Centralized
  2. Two-tier client/server
  3. Distributed (DDBMS)
  4. Three-tier client/server
