Functional dependencies and normalization

How can we tell whether a table is well designed? This page first shows the informal guidelines and the anomalies a bad design leads to, then explains functional dependencies and normal forms, which measure these things formally. The tool on the page finds which normal form a relation is in and decomposes it step by step.

  • Explain with an example which insertion, deletion and update anomalies repeated information in a table leads to.
  • Define a functional dependency; compute the closure of a set of attributes and find the candidate keys and the prime attributes.
  • Decide whether a relation is in 1NF, 2NF, 3NF or BCNF, and point to the dependency that breaks the rule.
  • Decompose a relation into the next normal form and show with the NJB test that the decomposition is lossless.

The big picture: one rule

All the definitions of normalization come down to one question: is the left side of every dependency a key? In X → A, if X is a key, each value of X appears once in the table and A is written once. If X is not a key, the same X value repeats in many rows and A is written again each time. That repetition is where anomalies come from. The fix is always the same: move X and A to a table of their own.

Three terms are enough (details below): X → A means that once the value of X is known, the value of A is fixed too (Ssn → Ename). A key is a minimal set of attributes whose value differs in every row. A prime attribute is one that is part of a candidate key.

Informal guidelines for good design

Before the formal concepts, the book gives four guidelines:

  1. Keep the meaning clear. Each row should represent one entity or one relationship instance; employee, department and project attributes should not be mixed in one table, and other entities are referred to by foreign keys.
  2. Avoid repetition. Storing the same information in many rows wastes space and leads to the three anomalies below.
  3. Reduce NULLs. Attributes that would be empty in most rows move to a separate table together with the primary key.
  4. Do not produce spurious tuples. Joining the tables with a natural join must not produce rows that were not in the original (a lossless join). Dependency preservation can be given up if necessary, a lossless join never.

Anomalies

The book's relation EMP_PROJ(Ssn, Pnumber, Hours, Ename, Pname, Plocation) stores the information of employees and projects again in every (employee, project) row. This design has three kinds of anomaly:

  • Update (modification) anomaly: if a project's name changes, it must be changed in the row of everyone who works on that project. If one is forgotten, the data becomes inconsistent.
  • Insertion anomaly: a project nobody works on yet cannot be inserted, because part of the row's primary key (Ssn) would be empty. In the same way, an employee not yet assigned to a project cannot be inserted.
  • Deletion anomaly: if the row of the only person who works on a project is deleted, the project's information is lost too.

The name and manager of the Research department repeat in four rows. DROP TABLE IF EXISTS demo.EMP_DEPT;   -- so that the box can be run again
CREATE TABLE demo.EMP_DEPT AS
  SELECT E.Fname AS Ename, E.Ssn, E.Bdate, E.Address, D.Dnumber, D.Dname, D.Mgr_ssn AS Dmgr_ssn
  FROM   EMPLOYEE E JOIN DEPARTMENT D ON E.Dno = D.Dnumber;
-- the department's name is stored once per employee: four times for Research
SELECT Ename, Dnumber, Dname FROM demo.EMP_DEPT WHERE Dnumber = 5;
-- renaming it in one row only leaves the data inconsistent
UPDATE demo.EMP_DEPT SET Dname = 'R&D' WHERE Ssn = '123456789';
SELECT DISTINCT Dnumber, Dname FROM demo.EMP_DEPT WHERE Dnumber = 5;   -- department 5 now has two names

Functional dependencies

Functional dependencies (FDs) are used to measure formally how good a design is. X → Y ("X functionally determines Y") means: in any state of the relation, two rows with the same X values must also have the same Y values. Formally, for any rows t1 and t2, if t1[X] = t2[X] then t1[Y] = t2[Y].

  • Ssn → Ename: the Ssn determines an employee's name.
  • Pnumber → {Pname, Plocation}: the project number determines the project's name and location.
  • {Ssn, Pnumber} → Hours: how many hours a week an employee works on a project is determined by the employee and the project together.

An FD is a property of the schema and must hold in every valid state of the relation. FDs are derived not from the data itself but from the real-world meaning of the attributes. If K is a key of R, then K determines all the attributes of R, because no two distinct rows have the same K value.

FDs cannot be derived from data, but they can be ruled out. By looking at a state of a relation we can say that an FD may exist, but we cannot prove that it does. What we can say for certain is that if two rows break an FD, that FD does not exist.

In the tool, choose a table and an X → Y: if two rows with the same X but a different Y are found, they are marked in red and the FD is ruled out; otherwise the FD may hold in this data. In the book's TEACH state (Figure 14.7), Text → Course may hold and Teacher → Course is ruled out.

Keys and closure

Normal forms are defined with keys. Normalization is splitting a bad table into smaller tables that satisfy these definitions; in practice one usually goes up to 3NF or BCNF. Storing the join of split tables as one table on purpose, for performance, is called denormalization.

  • Superkey: a set of attributes whose values cannot be the same for two rows in any valid state.
  • Key: a superkey that stops being a superkey if any attribute is removed, i.e. a minimal superkey. If there are several keys, each is a candidate key; one is chosen as the primary key, the others become secondary keys.
  • Prime attribute: an attribute that is a member of some candidate key. Nonprime attribute: an attribute that is a member of no candidate key.

The closure X+ of a set of attributes X is all the attributes X determines through the dependencies. It is simple to compute: start with X, add the right side of every dependency whose left side is in the set, and continue until nothing new is added. If X+ contains every attribute, X is a superkey. First normal form (1NF)

This is exactly the UNF → 1NF step of the journey. 1NF disallows composite attributes, multivalued attributes and nested relations, i.e. attributes whose value in a row is not atomic. 1NF is considered part of the definition of a relation, and most relational DBMSs allow only relations in 1NF to be defined.

In the book's Figure 14.9, the Dlocations attribute of the relation DEPARTMENT(Dname, Dnumber, Dmgr_ssn, Dlocations) is multivalued: the Research department has three locations, Bellaire, Sugarland and Houston. The best way to bring this into 1NF is to move Dlocations to a separate relation together with the primary key: DEPT_LOCATIONS(Dnumber, Dlocation). This is what COMPANY does. The other options (rows that repeat the department's information for each location, or a fixed number of columns such as Dlocation1, Dlocation2, …) produce repetition and NULLs.

In Figure 14.10, each row of the EMP_PROJ relation contains a nested relation PROJS made of the employee's projects. To bring this into 1NF, the nested relation is moved to a separate relation, taking the primary key with it: EMP_PROJ1(Ssn, Ename) and EMP_PROJ2(Ssn, Pnumber, Hours).

-- not in 1NF: one value holding a set of locations
SELECT Dnumber, GROUP_CONCAT(Dlocation ORDER BY Dlocation SEPARATOR ', ') AS Dlocations
FROM   DEPT_LOCATIONS GROUP BY Dnumber;
-- 1NF: DEPT_LOCATIONS(Dnumber, Dlocation), one atomic value per row
SELECT Dnumber, Dlocation FROM DEPT_LOCATIONS ORDER BY Dnumber, Dlocation;

Second normal form (2NF)

If a dependency X → Y no longer holds when any attribute is removed from X, it is a full functional dependency. For example {Ssn, Pnumber} → Hours is full, because neither Ssn → Hours nor Pnumber → Hours holds. {Ssn, Pnumber} → Ename is not full, because Ssn → Ename also holds; this is called a partial dependency.

2NF: a relation schema is in 2NF if every nonprime attribute is fully functionally dependent on the primary key. That is, no nonprime attribute should depend on only part of the key.

In the 1NF → 2NF step of the journey, Ename and Pname repeated because of partial dependencies. The book's example is the same. EMP_PROJ is not in 2NF: Ename depends only on Ssn, and Pname and Plocation only on Pnumber. 2NF normalization moves each partial dependency into its own relation. In the walkthrough below, in each decomposition step the relation as it was is on the left and the two relations it gives are on the right; the underlined attributes are each relation's key. The result has the same structure as the book's Figure 14.11a: EP1(Ssn, Pnumber, Hours), EP2(Ssn, Ename) and EP3(Pnumber, Pname, Plocation).

Third normal form (3NF)

A dependency X → Z that can be derived from the dependencies X → Y and Y → Z is called a transitive dependency. For example Ssn → Dmgr_ssn is transitive, because Ssn → Dnumber and Dnumber → Dmgr_ssn hold. Ssn → Ename is not transitive, because there is no X with Ssn → X and X → Ename.

3NF: a relation schema is in 3NF if it is in 2NF and no nonprime attribute is transitively dependent on the primary key. Note: in X → Y → Z, if Y is a candidate key this is not a problem. For example in EMP(Ssn, Emp#, Salary), Ssn → Emp# → Salary is transitive, but since Emp# is a candidate key the relation is in 3NF.

In the 2NF → 3NF step of the journey, the department name repeated because of a transitive dependency. EMP_DEPT is in 2NF (its key has a single attribute, so there can be no partial dependency) but not in 3NF: Dname and Dmgr_ssn depend on the primary key Ssn transitively, through Dnumber. 3NF normalization moves this dependency into a separate relation and gives the result of the book's Figure 14.11b: ED1(Ename, Ssn, Bdate, Address, Dnumber) and ED2(Dnumber, Dname, Dmgr_ssn).

An informal summary of the three normal forms: in 1NF all the attributes depend on the key; in 2NF all the attributes depend on the whole key; in 3NF all the attributes depend on nothing but the key.

General definitions for several candidate keys

The definitions above consider only the primary key. The general definitions take all the candidate keys into account; every attribute that is a member of some candidate key is prime.

  • General 2NF: R is in 2NF if every nonprime attribute is fully functionally dependent on every key of R.
  • General 3NF: for every dependency X → A that holds in R, either (a) X is a superkey of R, or (b) A is a prime attribute of R. Condition (a) catches two kinds of violation: a prime attribute (part of a key) determining a nonprime attribute (a 2NF violation), and a nonprime attribute determining a nonprime attribute (a transitive dependency). Condition (b) covers the dependencies that 3NF allows but BCNF catches.

The book's relation LOTS(Property_id, County_name, Lot, Area, Price, Tax_rate) has two candidate keys: Property_id and {County_name, Lot}. It has four dependencies: FD1 and FD2 come from the two keys, FD3 is County_name → Tax_rate, FD4 is Area → Price. County_name → Tax_rate breaks 2NF, because County_name is part of a key (County_name, Lot). Area → Price breaks 3NF, because Area is not a superkey and Price is not prime. With the option below you can decompose LOTS first into 2NF (LOTS1 and LOTS2), then into 3NF (LOTS1A, LOTS1B and LOTS2); these are the stages of the book's Figure 14.12.

Boyce-Codd normal form (BCNF)

BCNF: R is in BCNF if, for every dependency X → A that holds in R, X is a superkey of R. This is the definition of 3NF with condition (b) removed; so every BCNF relation is in 3NF, every 3NF relation is in 2NF, every 2NF relation is in 1NF. But there are relations that are in 3NF and not in BCNF.

The book's relation TEACH(Student, Course, Instructor) has two dependencies: {Student, Course} → Instructor and Instructor → Course (each instructor teaches a single course). {Student, Course} is a candidate key. In Instructor → Course, Instructor is not a superkey, but since Course is a prime attribute, condition (b) of 3NF holds: TEACH is in 3NF but not in BCNF.

A relation not in BCNF is decomposed, giving up the preservation of some dependencies if necessary. There are three possible decompositions of TEACH, and all three lose the dependency {Student, Course} → Instructor:

  • D1: {Student, Instructor} and {Student, Course}
  • D2: {Course, Instructor} and {Course, Student}
  • D3: {Instructor, Course} and {Instructor, Student}

The preservation of dependencies can be given up, but the lossless join cannot. The NJB test tells whether a binary decomposition is lossless: the decomposition D = {R1, R2} is lossless if and only if one of the dependencies (R1 ∩ R2) → (R1 − R2) or (R1 ∩ R2) → (R2 − R1) is in F+. That is, the common attributes of the two parts must determine the rest of one of the parts. You can test the three decompositions below: only in D3 does the common attribute Instructor determine Course.

The general procedure: if R is not in BCNF and the dependency X → A causes the violation, R is decomposed into two relations: (i) R − A and (ii) X ∪ A. If one of them is not in BCNF, the process is repeated. In TEACH the violation is Instructor → Course, so the decomposition is (TEACH − Course) and (Instructor ∪ Course), i.e. D3. When the dependency Area → County_name is added to LOTS1A, the same procedure gives the result of the book's Figure 14.13a.

The project's name repeats in the row of every employee on the project. When the name changes, all these rows must be changed; if one is forgotten, the same project appears with two different names. The fix is to move the project information into its own relation (EP3).

In the relation R(A, B, C, D), F = {A → B, B → C, C → D}. What is the closure A+, and which is the candidate key of R?

  1. A+ = {A, B}; key {A, B}
  2. A+ = {A, B, C, D}; key {A}
  3. A+ = {A, B, C, D}; key {D}
  4. A+ = {A, B, C, D}; key {A, B}
Computing the closure: start from A; B is added with A → B, C with B → C, D with C → D. Since A+ contains all the attributes, A is a superkey; since it has one attribute, it is also minimal, i.e. a candidate key. You can try the tool with this example.

In the relation R(Ssn, Pnumber, Hours, Ename), F = {Ssn, Pnumber → Hours; Ssn → Ename}. What is the highest normal form R is in?

  1. 1NF
  2. 2NF
  3. 3NF
  4. BCNF
The candidate key is {Ssn, Pnumber}. Ssn → Ename is a partial dependency: the nonprime Ename depends only on the Ssn part of the key. So R is not in 2NF. To bring it into 2NF, (Ssn, Ename) is moved into a separate relation.

Which statement is true?

  1. Every 3NF relation is in BCNF.
  2. A BCNF decomposition always preserves all the functional dependencies.
  3. In a decomposition, the lossless join can be given up to preserve the dependencies.
  4. Every BCNF relation is in 3NF, but the converse is not always true.
The normal forms get stricter: BCNF ⇒ 3NF ⇒ 2NF ⇒ 1NF. 3NF allows a dependency X → A if A is a prime attribute; BCNF does not. In a decomposition the lossless join is required; the preservation of dependencies can be given up if necessary.

For TEACH(Student, Course, Instructor), F = {Student, Course → Instructor; Instructor → Course}. Which decomposition is lossless according to the NJB test?

  1. {Student, Instructor} and {Student, Course}
  2. {Course, Instructor} and {Course, Student}
  3. {Instructor, Course} and {Instructor, Student}
  4. None
The NJB test: R1 ∩ R2 must determine R1 − R2 or R2 − R1. In D3 the common attribute is Instructor, and since Instructor → Course holds, it determines the rest of the part {Instructor, Course}. In D1 the common part is Student, in D2 Course, and neither determines anything.
