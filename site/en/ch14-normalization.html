Functional dependencies and normalization

How can we tell whether a table is well designed? This page first shows the informal guidelines and the anomalies a bad design leads to, then explains functional dependencies and normal forms, which measure these things formally. The tool on the page finds which normal form a relation is in and decomposes it step by step.

  • Explain with an example which insertion, deletion and update anomalies repeated information in a table leads to.
  • Define a functional dependency; compute the closure of a set of attributes and find the candidate keys and the prime attributes.
  • Decide whether a relation is in 1NF, 2NF, 3NF or BCNF, and point to the dependency that breaks the rule.
  • Decompose a relation into the next normal form and show with the NJB test that the decomposition is lossless.

From start to finish: the topic as one story

Read this section once, from top to bottom. It assumes you know nothing about the topic. The details and the things to try come in the sections after it.

1. One table, one problem

A company keeps its employees and projects in a single table. Each row says: "this employee works on this project for this many hours a week."

SsnPnumberEnameDnumberDnamePnameHours
1231John Smith5ResearchProductX32.5
1232John Smith5ResearchProductY7.5
3332Franklin Wong5ResearchProductY10

Look at the yellow cells. "John Smith" is written twice. "Research" is written three times. The same fact sits in several places.

Why is that bad? Three examples:

  • Research is renamed "R&D". You have to change all three rows. Forget one, and the table contradicts itself.
  • A new project starts, but nobody works on it yet. You cannot add it to the table, because every row needs an employee.
  • Franklin Wong leaves and his row is deleted. If nobody else is on that project, the project's name is lost too.

These three problems are called anomalies. They all have the same cause: repetition.

The only goal of normalization: write each fact exactly once.

2. Which fact depends on which?

To find repetition we ask one question: if I know this column, which other column do I know too?

  • If I know an employee's number, I know their name. We write this as Ssn → Ename.
  • If I know a department's number, I know its name: Dnumber → Dname.
  • If I know a project's number, I know its name: Pnumber → Pname.
  • To know the hours I need both, the employee and the project: {Ssn, Pnumber} → Hours.

These arrows are called functional dependencies. The left side of the arrow determines the right side.

3. What identifies a row? The key

The columns that identify each row on their own are called the key. In this table Ssn alone is not enough, because John Smith is in two rows. Pnumber alone is not enough either. The two together are enough: an employee appears only once per project. So the key is {Ssn, Pnumber}. In the tables, key columns are underlined.

Columns that are part of the key are called prime columns. Here Ssn and Pnumber are prime. The other columns, the actual information in the table (Ename, Dnumber, Dname, Pname, Hours), are nonprime columns. "Prime" here has nothing to do with prime numbers; it simply means "part of a key".

4. The real cause of repetition

Look at the yellow cells again. Why is John Smith written twice? Because Ssn = 123 is in two rows, and Ssn → Ename. Every time Ssn repeats, the name repeats with it.

The rule: if the left side of an arrow is not a key, the fact on its right side repeats.

The fix is always the same: we move that arrow to a table of its own. For Ssn → Ename we open a small table (Ssn, Ename). Each employee is written there once. We delete Ename from the big table. Since Ssn stays in both tables, we can join them again whenever we need to.

The normal forms apply this rule step by step. Each one forbids one more kind of repetition.

9. Careful when splitting: nothing may be lost

At every split we check one thing: when we join the parts again, do we get back exactly the original table?

For a good split the answer is yes. For a bad split the join produces rows that were never in the original. These are called spurious tuples.

The check is easy: the shared column of the two parts must be the key of one of the parts. The shared column of EMP and DEPT is Dnumber, and Dnumber is DEPT's key. So this split is safe. This check is called the NJB test.

There is also a second wish: every arrow should stay inside a single table after the split. This is called dependency preservation. It is kept when possible; sometimes, as in the BCNF example, it is given up. A lossless join is never given up.

Summary

  1. Repetition causes anomalies.
  2. The cause of repetition is an arrow whose left side is not a key.
  3. The fix is to move that arrow to a table of its own.
  4. 1NF asks for one value per cell. 2NF removes dependencies on part of the key, 3NF removes dependencies on a non-key column. BCNF leaves no exceptions.
  5. After every split, joining the parts must give back exactly the original table.

The problem: repetition and anomalies

Normalization has one goal: never write the same fact twice. When a fact repeats in many rows, the table can contradict itself as soon as it is changed, added to or deleted from. This section shows the problem; the next sections are the tools to measure it (dependencies, keys) and to remove it (normal forms).

Before the formal concepts, the book gives four guidelines:

  1. Keep the meaning clear. Each row should represent one entity or one relationship instance; employee, department and project attributes should not be mixed in one table, and other entities are referred to by foreign keys.
  2. Avoid repetition. Storing the same information in many rows wastes space and leads to the three anomalies below.
  3. Reduce NULLs. Attributes that would be empty in most rows move to a separate table together with the primary key.
  4. Do not produce spurious tuples. Joining the tables with a natural join must not produce rows that were not in the original (a lossless join). Dependency preservation can be given up if necessary, a lossless join never.

Anomalies

The book's relation EMP_PROJ(Ssn, Pnumber, Hours, Ename, Pname, Plocation) stores the information of employees and projects again in every (employee, project) row. This design has three kinds of anomaly:

  • Update (modification) anomaly: if a project's name changes, it must be changed in the row of everyone who works on that project. If one is forgotten, the data becomes inconsistent.
  • Insertion anomaly: a project nobody works on yet cannot be inserted, because part of the row's primary key (Ssn) would be empty. In the same way, an employee not yet assigned to a project cannot be inserted.
  • Deletion anomaly: if the row of the only person who works on a project is deleted, the project's information is lost too.

Functional dependencies

Functional dependencies (FDs) are used to measure formally how good a design is. X → Y ("X functionally determines Y") means: in any state of the relation, two rows with the same X values must also have the same Y values. Formally, for any rows t1 and t2, if t1[X] = t2[X] then t1[Y] = t2[Y].

  • Ssn → Ename: the Ssn determines an employee's name.
  • Pnumber → {Pname, Plocation}: the project number determines the project's name and location.
  • {Ssn, Pnumber} → Hours: how many hours a week an employee works on a project is determined by the employee and the project together.

An FD is a property of the schema and must hold in every valid state of the relation. FDs are derived not from the data itself but from the real-world meaning of the attributes. If K is a key of R, then K determines all the attributes of R, because no two distinct rows have the same K value.

FDs cannot be derived from data, but they can be ruled out. By looking at a state of a relation we can say that an FD may exist, but we cannot prove that it does. What we can say for certain is that if two rows break an FD, that FD does not exist.

In the tool, choose a table and an X → Y: if two rows with the same X but a different Y are found, they are marked in red and the FD is ruled out; otherwise the FD may hold in this data. In the book's TEACH state (Figure 14.7), Text → Course may hold and Teacher → Course is ruled out.

Keys and closure

Normal forms are defined with keys. Normalization is splitting a bad table into smaller tables that satisfy these definitions; in practice one usually goes up to 3NF or BCNF. Storing the join of split tables as one table on purpose, for performance, is called denormalization.

  • Superkey: a set of attributes whose values cannot be the same for two rows in any valid state.
  • Key: a superkey that stops being a superkey if any attribute is removed, i.e. a minimal superkey. If there are several keys, each is a candidate key; one is chosen as the primary key, the others become secondary keys.
  • Prime attribute: an attribute that is a member of some candidate key, that is, one that belongs to a key ("prime" here does not mean a prime number; it means "part of a key"). Nonprime attribute: an attribute that is a member of no candidate key.

The closure X+ of a set of attributes X is all the attributes X determines through the dependencies. It is simple to compute: start with X, add the right side of every dependency whose left side is in the set, and continue until nothing new is added. If X+ contains every attribute, X is a superkey. In the dependency diagram on top each dependency is a line: it drops from the left side and rises with arrows to the right side; the key is underlined.

One rule and four normal forms

With dependencies and keys in hand, every normal form comes down to one question: is the left side of every dependency a key? In X → A, if X is a key, each value of X appears once in the table and A is written once. If X is not a key, the same X value repeats in many rows and A is written again each time. The fix is always the same: move X and A to a table of their own and remove A from the original.

The normal forms tighten this rule step by step. Each includes all the conditions of the one before and forbids one more kind of repetition:

1NF one value per cell
2NF + nothing depends on part of a key
3NF + nothing depends on a non-key
BCNF + no exceptions: every left side is a superkey

1NFSeveral values in one cellDlocations = "Bellaire, Houston, Sugarland"
2NFPart of a key → a nonprime attributeSsn → Ename, with key {Ssn, Pnumber}
3NFA non-key → a nonprime attributeDnumber → Dname, with key Ssn
BCNFA non-key → any attribute (a prime one too)Instructor → Course (TEACH)

Three questions tell which normal form a dependency breaks:

  1. Is the left side X a superkey? If yes, there is no problem; this dependency breaks no normal form.
  2. Is the right side A prime? If yes, only BCNF is broken; 3NF allows it.
  3. Is X part of a candidate key? If yes, it is a partial dependency and 2NF is broken; if not, it is a transitive dependency and 3NF is broken.

First normal form (1NF)

In one sentence
Every cell holds a single, indivisible (atomic) value.
What problem does it solve?
With a list in a cell (Dlocations = "Bellaire, Houston, Sugarland"), searching, updating and defining a foreign key on that value are only possible by taking the text apart.
How is it tested?
Does any cell hold several values, a composite value or a nested table?
How is it fixed?
Move the multivalued attribute, together with the row's key, to a separate table: DEPARTMENT and DEPT_LOCATIONS(Dnumber, Dlocation). Repeating the department row for each location or adding columns like Dlocation1, Dlocation2 produces repetition and NULLs.

The book's two examples: in Figure 14.9 DEPARTMENT's Dlocations moves to DEPT_LOCATIONS as above. In Figure 14.10 every employee row contains a nested table of projects; it too is split off with its key: EMP_PROJ1(Ssn, Ename) and EMP_PROJ2(Ssn, Pnumber, Hours). 1NF counts as part of the definition of a relation; relational DBMSs only allow 1NF tables anyway.

-- not in 1NF: one value holding a set of locations
SELECT Dnumber, GROUP_CONCAT(Dlocation ORDER BY Dlocation SEPARATOR ', ') AS Dlocations
FROM   DEPT_LOCATIONS GROUP BY Dnumber;
-- 1NF: DEPT_LOCATIONS(Dnumber, Dlocation), one atomic value per row
SELECT Dnumber, Dlocation FROM DEPT_LOCATIONS ORDER BY Dnumber, Dlocation;

Second normal form (2NF)

In one sentence
Every nonprime attribute depends on the whole key, not on part of it.
What problem does it solve?
With key {Ssn, Pnumber}, Ssn → Ename: an employee's name is written again for every project they work on. Pnumber → Pname: a project's name repeats for each of its employees.
How is it tested?
Does part of the key determine a nonprime attribute on its own? Then it is a partial dependency. With a single-attribute key there is no part, so a 1NF table is already in 2NF.
How is it fixed?
For each partial dependency X → A, (X, A) becomes a separate table and A leaves the original. Only what depends on the whole key stays in the original.

A dependency that breaks when any attribute leaves its left side is full: {Ssn, Pnumber} → Hours is full, because hours need both the employee and the project. {Ssn, Pnumber} → Ename is not full, because Ssn alone is enough. Below, the book's EMP_PROJ is taken to 2NF step by step; at each step the relation before is on the left and the two relations it becomes are on the right. The result is the same as Figure 14.11a: EP1(Ssn, Pnumber, Hours), EP2(Ssn, Ename), EP3(Pnumber, Pname, Plocation).

Third normal form (3NF)

In one sentence
No nonprime attribute depends on another nonprime attribute; each depends only on the key.
What problem does it solve?
In EMP_DEPT, Ssn → Dnumber → Dname: a department's name is written again for every employee in it. Research four times.
How is it tested?
Does a non-key X determine a nonprime A? Then there is a chain key → X → A: a transitive dependency.
How is it fixed?
(X, A) becomes a separate table and A leaves the original; X stays in the original as a foreign key: ED1(Ename, Ssn, Bdate, Address, Dnumber) and ED2(Dnumber, Dname, Dmgr_ssn).

One exception: if the X in the middle of the chain is a candidate key, there is no problem. In EMP(Ssn, Emp#, Salary), Ssn → Emp# → Salary looks transitive, but Emp# also identifies the row on its own, so Salary does not repeat. Below, EMP_DEPT is taken to 3NF (Figure 14.11b). A summary of the three normal forms that sticks: every attribute depends on the key (1NF), the whole key (2NF) and nothing but the key (3NF).

General definitions for several candidate keys

So far we looked only at the primary key. A table may have several candidate keys; the general definitions take all of them into account, and every attribute that appears in some candidate key is prime.

  • General 2NF: R is in 2NF if every nonprime attribute is fully functionally dependent on every key of R.
  • General 3NF: for every dependency X → A that holds in R, either (a) X is a superkey of R, or (b) A is a prime attribute of R. Condition (a) catches two kinds of violation: a prime attribute (part of a key) determining a nonprime attribute (a 2NF violation), and a nonprime attribute determining a nonprime attribute (a transitive dependency). Condition (b) covers the dependencies that 3NF allows but BCNF catches.

The book's relation LOTS(Property_id, County_name, Lot, Area, Price, Tax_rate) has two candidate keys: Property_id and {County_name, Lot}. It has four dependencies: FD1 and FD2 come from the two keys, FD3 is County_name → Tax_rate, FD4 is Area → Price. County_name → Tax_rate breaks 2NF, because County_name is part of a key (County_name, Lot). Area → Price breaks 3NF, because Area is not a superkey and Price is not prime. With the option below you can decompose LOTS first into 2NF (LOTS1 and LOTS2), then into 3NF (LOTS1A, LOTS1B and LOTS2); these are the stages of the book's Figure 14.12.

Boyce-Codd normal form (BCNF)

In one sentence
The left side of every arrow is a superkey. No exceptions.
Difference from 3NF
For an X → A whose left side is not a key, 3NF allows it if A is prime. BCNF never allows it.
How is it tested?
Is there an arrow whose left side is not a superkey? The right side does not matter.
How is it fixed?
For the violating X → A, split R into (R − A) and (X ∪ A): TEACH → (Student, Instructor) and (Instructor, Course). The price: {Student, Course} → Instructor is lost.
An arrow whose left side is not a key: X → A3NFBCNF
A is not prime (Dnumber → Dname)forbiddenforbidden

TEACH(Student, Course, Instructor) has {Student, Course} → Instructor and Instructor → Course. Since Course is prime, TEACH is in 3NF; since Instructor is not a superkey, it is not in BCNF. There are three ways to split it in two, and all three lose {Student, Course} → Instructor:

  • D1: {Student, Instructor} and {Student, Course}
  • D2: {Course, Instructor} and {Course, Student}
  • D3: {Instructor, Course} and {Instructor, Student}

Dependency preservation can be given up, a lossless join cannot. The NJB test: {R1, R2} is lossless if and only if the shared attributes (R1 ∩ R2) determine the rest of one of the parts. Test the three below: only in D3 does the shared attribute Instructor determine Course.

The general procedure: if R is not in BCNF and X → A violates it, split R into (R − A) and (X ∪ A); if a part is not in BCNF, repeat. For TEACH this gives D3. When Area → County_name is added to LOTS1A, the same procedure gives Figure 14.13a.

In the relation R(A, B, C, D), F = {A → B, B → C, C → D}. What is the closure A+, and which is the candidate key of R?

  1. A+ = {A, B}; key {A, B}
  2. A+ = {A, B, C, D}; key {A}
  3. A+ = {A, B, C, D}; key {D}
  4. A+ = {A, B, C, D}; key {A, B}

The candidate key is {Ssn, Pnumber}. Ssn → Ename is a partial dependency: the nonprime Ename depends only on the Ssn part of the key. So R is not in 2NF. To bring it into 2NF, (Ssn, Ename) is moved into a separate relation.

Which statement is true?

  1. Every 3NF relation is in BCNF.
  2. A BCNF decomposition always preserves all the functional dependencies.
  3. In a decomposition, the lossless join can be given up to preserve the dependencies.
  4. Every BCNF relation is in 3NF, but the converse is not always true.
The normal forms get stricter: BCNF ⇒ 3NF ⇒ 2NF ⇒ 1NF. 3NF allows a dependency X → A if A is a prime attribute; BCNF does not. In a decomposition the lossless join is required; the preservation of dependencies can be given up if necessary.

For TEACH(Student, Course, Instructor), F = {Student, Course → Instructor; Instructor → Course}. Which decomposition is lossless according to the NJB test?

  1. {Student, Instructor} and {Student, Course}
  2. {Course, Instructor} and {Course, Student}
  3. {Instructor, Course} and {Instructor, Student}
  4. None
The NJB test: R1 ∩ R2 must determine R1 − R2 or R2 − R1. In D3 the common attribute is Instructor, and since Instructor → Course holds, it determines the rest of the part {Instructor, Course}. In D1 the common part is Student, in D2 Course, and neither determines anything.
