NULL and nested queries

The first half of Ch 7: how NULLs affect comparisons (three-valued logic), using a query inside another query, and how to ask an "every" (∀) question in SQL.

  • Say whether a condition involving NULL is TRUE, FALSE or UNKNOWN; use IS NULL.
  • Write nested queries with IN, ANY/ALL and EXISTS; recognize whether a subquery is correlated.
  • Explain the NULL trap of NOT IN and avoid it with NOT EXISTS.
  • Write an "every …" (division) question with a double NOT EXISTS or with EXCEPT.

NULL and three-valued logic

NULL has three meanings: an unknown value (the value exists but is not known: the birth date is unknown), an unavailable / withheld value (it exists but is withheld: an unlisted home phone), a not applicable attribute (the LastCollegeDegree of someone with no college degree). SQL does not distinguish them.

Each NULL is considered different from every other; so the result of a comparison involving NULL is neither TRUE nor FALSE: UNKNOWN. That is why SQL uses a three-valued logic:

WHERE selects only the rows for which it is TRUE; FALSE and UNKNOWN are discarded. To remember it: in AND, FALSE "wins"; in OR, TRUE "wins"; UNKNOWN remains only if the result cannot be decided otherwise. NOT UNKNOWN = UNKNOWN.

IS NULL and IS NOT NULL

You cannot test whether a value is NULL with = NULL (the result is always UNKNOWN). IS NULL / IS NOT NULL are used for that.

-- wrong: Super_ssn = NULL is UNKNOWN for every row, so no row is returned
SELECT Fname, Lname FROM EMPLOYEE WHERE Super_ssn = NULL;
-- right (Q18)
SELECT Fname, Lname FROM EMPLOYEE WHERE Super_ssn IS NULL;

In one of WORKS_ON's 16 rows (Borg, project 20) Hours is NULL. The box below counts a condition and its negation separately. COUNT(*) gives the number of rows in the result (all the aggregate functions are on the next page; here it is only used for counting). Predict before running: do the two numbers add up to 16?

-- Hours is NULL for Borg on project 20
SELECT COUNT(*) AS more_than_10     FROM WORKS_ON WHERE Hours > 10;
SELECT COUNT(*) AS not_more_than_10 FROM WORKS_ON WHERE NOT (Hours > 10);
SELECT COUNT(*) AS all_rows         FROM WORKS_ON;   -- 16, not 9 + 6

The same rule holds in joins: rows whose join column is NULL do not match in an inner join (in Q8 Borg has no supervisor). How NULLs are handled in aggregate functions is on the next page.

Nested queries

A complete SELECT written in the WHERE (or FROM, SELECT) part of a query is called a nested query (inner query, subquery), and the query that contains it the outer query.

IN

v IN V: TRUE if the value v is an element of the multiset V.

The easiest way to read a nested query is to go from the inside out: first run the inner query on its own and see what it returns, then put those values in its place in the outer query. The box below does this step by step:

-- step 1: the inner query alone: which department number is Research?
SELECT Dnumber FROM DEPARTMENT WHERE Dname = 'Research';
-- step 2: the outer query with that value written in by hand
SELECT Fname, Lname FROM EMPLOYEE WHERE Dno IN (5);
-- step 3: the nested query: the same answer, without knowing the number in advance
SELECT Fname, Lname
FROM   EMPLOYEE
WHERE  Dno IN (SELECT Dnumber FROM DEPARTMENT WHERE Dname = 'Research');

Q4A uses the same idea with two inner queries: one "the projects of the department Smith manages", the other "the projects Smith works on". The outer query selects the projects that are in either of these two sets (OR).

SELECT DISTINCT Pnumber
FROM   PROJECT
WHERE  Pnumber IN (SELECT Pnumber
                   FROM   PROJECT, DEPARTMENT, EMPLOYEE
                   WHERE  Dnum = Dnumber AND Mgr_ssn = Ssn AND Lname = 'Smith')
   OR  Pnumber IN (SELECT Pno
                   FROM   WORKS_ON, EMPLOYEE
                   WHERE  Essn = Ssn AND Lname = 'Smith');

If the inner query returns a single column and a single row (a scalar), = can be used instead of IN. Tuples can be compared too:

SELECT DISTINCT Essn
FROM   WORKS_ON
WHERE  (Pno, Hours) IN (SELECT Pno, Hours
                        FROM   WORKS_ON
                        WHERE  Essn = '123456789');

ANY / SOME and ALL

  • v = ANY V (= SOME): TRUE if V has at least one element equal to v. = ANY ≡ IN.
  • v > ALL V: TRUE if v is greater than every element of V. If V is empty, ALL returns TRUE and ANY FALSE.
  • The other operators can be combined too: >, >=, <, <=, <> (not equal). E.g. v <> ALL V means "v is equal to no element of V", i.e. NOT IN.
SELECT Lname, Fname, Salary
FROM   EMPLOYEE
WHERE  Salary > ALL (SELECT Salary FROM EMPLOYEE WHERE Dno = 5);

SELECT Lname, Fname, Salary
FROM   EMPLOYEE
WHERE  Salary > ANY (SELECT Salary FROM EMPLOYEE WHERE Dno = 5);

NOT IN and the NULL trap. If the inner query returns a NULL, x NOT IN (…) can never be TRUE: x <> NULL is UNKNOWN and, ANDed in, makes everything UNKNOWN. NOT EXISTS does not have this problem. In the box below the two queries ask the same question but give different answers.

The inner part of the first query, SELECT Super_ssn FROM EMPLOYEE, returns eight values; one of them is NULL because Borg has no supervisor. For Smith, for example, the condition becomes '123456789' <> '333445555' AND … AND '123456789' <> NULL; the last term is UNKNOWN, so the whole condition is at best UNKNOWN and the row is not selected.

-- Super_ssn contains a NULL (Borg), so NOT IN returns nothing
SELECT Lname FROM EMPLOYEE
WHERE  Ssn NOT IN (SELECT Super_ssn FROM EMPLOYEE);
-- NOT EXISTS gives the expected answer
SELECT Lname FROM EMPLOYEE E
WHERE  NOT EXISTS (SELECT * FROM EMPLOYEE S WHERE S.Super_ssn = E.Ssn);

Ambiguity and scope

An unqualified column name belongs to the tables of the innermost query that contains it. If the same table is used in the inner and the outer query, aliases are needed. The rule: a name not found in a table of the inner query is looked up in the outer tables.

Correlated nested queries

If the WHERE of the inner query uses a column of the outer query, the queries are correlated. The inner query is evaluated once for each row of the outer query (conceptually). That is why reading "from the inside out" does not work in one step here: the result of the inner query changes with the row the outer query is looking at.

In Q16 below, when the outer query looks at the row E = Wong the inner query becomes WHERE 'Franklin' = D.Dependent_name AND 'M' = D.Sex: Wong's dependents are Alice, Theodore and Joy; none of them is Franklin, the inner query returns nothing and Wong is not selected. Then for E = Smith the inner query becomes 'John' = Dependent_name AND 'M' = Sex, empty again. For each of the eight employees the inner query is computed again, with that employee's values.

SELECT E.Fname, E.Lname
FROM   EMPLOYEE AS E
WHERE  E.Ssn IN (SELECT D.Essn
                 FROM   DEPENDENT AS D
                 WHERE  E.Fname = D.Dependent_name AND E.Sex = D.Sex);

On COMPANY's starting data the result is empty: nobody has a dependent with their own first name and sex. The box below gives Smith a son named John, runs the same query again and deletes the row it added. Only John Smith appears in the result: the dependents of Wong and Wallace have names different from their own. (If you ran the INSERT yourself, the box above shows Smith too; that is correct. Reset database brings back the starting data.)

-- Smith (John, M) gets a son named John: E.Fname = D.Dependent_name AND E.Sex = D.Sex now holds for Smith
INSERT INTO DEPENDENT VALUES ('123456789', 'John', 'M', '1990-01-01', 'Son');
-- Q16 again: now John Smith is returned
SELECT E.Fname, E.Lname
FROM   EMPLOYEE AS E
WHERE  E.Ssn IN (SELECT D.Essn
                 FROM   DEPENDENT AS D
                 WHERE  E.Fname = D.Dependent_name AND E.Sex = D.Sex);
-- undo the insert, so that COMPANY is unchanged and the box can be run again
DELETE FROM DEPENDENT WHERE Essn = '123456789' AND Dependent_name = 'John';

Every nested query that uses = or IN, correlated or not, can also be written as a single flat query (with a join):

SELECT E.Fname, E.Lname
FROM   EMPLOYEE AS E, DEPENDENT AS D
WHERE  E.Ssn = D.Essn AND E.Sex = D.Sex AND E.Fname = D.Dependent_name;

EXISTS and NOT EXISTS

EXISTS (Q): TRUE if the result of Q has at least one row, FALSE if it is empty. (The SELECT list of the inner query does not matter; by convention SELECT * is written.) EXISTS never returns UNKNOWN.

SELECT Fname, Lname
FROM   EMPLOYEE
WHERE  NOT EXISTS (SELECT *
                   FROM   DEPENDENT
                   WHERE  Ssn = Essn);

SELECT Fname, Lname
FROM   EMPLOYEE
WHERE  EXISTS (SELECT * FROM DEPENDENT  WHERE Ssn = Essn)
  AND  EXISTS (SELECT * FROM DEPARTMENT WHERE Ssn = Mgr_ssn);

Division: "for every …"

SQL has no universal quantifier (∀, "for all"). Questions of the form "X is related to every element of Y" are written in two ways:

  1. With set difference: if (the set Y) EXCEPT (the set X is related to) is empty. NOT EXISTS ( … EXCEPT … ).
  2. With double negation: ∀y P(x, y) ≡ ¬∃y ¬P(x, y). "There is no element of Y that X is not related to": two nested NOT EXISTS.

Let us build Q3A piece by piece. The question: "the employees who work on every project controlled by department 5". Think of a single employee, Wong:

-- (1) the set Y: the projects of department 5
SELECT Pnumber FROM PROJECT WHERE Dnum = 5;
-- (2) the projects Wong works on
SELECT Pno FROM WORKS_ON WHERE Essn = '333445555';
-- (3) Y EXCEPT Wong's projects: the projects of department 5 that Wong does NOT work on
SELECT Pnumber FROM PROJECT WHERE Dnum = 5
EXCEPT
SELECT Pno FROM WORKS_ON WHERE Essn = '333445555';

If (3) were empty, Wong would be working on every project of 5; but the result contains 1 (ProductX), so Wong is not selected. Q3A makes this check for every employee: it puts the outer query's row (Ssn) in place of '333445555' and tests that (3) is empty with NOT EXISTS.

SELECT Fname, Lname
FROM   EMPLOYEE
WHERE  NOT EXISTS ( (SELECT Pnumber
                     FROM   PROJECT
                     WHERE  Dnum = 5)
                    EXCEPT
                    (SELECT Pno
                     FROM   WORKS_ON
                     WHERE  Ssn = Essn) );

SELECT Lname, Fname
FROM   EMPLOYEE
WHERE  NOT EXISTS ( SELECT *
                    FROM   WORKS_ON B
                    WHERE  B.Pno IN (SELECT Pnumber
                                     FROM   PROJECT
                                     WHERE  Dnum = 5)
                      AND  NOT EXISTS ( SELECT *
                                        FROM   WORKS_ON C
                                        WHERE  C.Essn = Ssn
                                          AND  C.Pno = B.Pno ) );

The result is empty: nobody in COMPANY works on all three projects (1, 2, 3) of department 5. Reading Q3B: select the employee if there is no B such that "(1) B is a WORKS_ON row of someone working on one of 5's projects and (2) there is no row C showing that this employee works on B's project".

Change Q3A so that Wong appears in the result. Wong works on 2, 3, 10, 20; if you add a row for project 1 he covers all the projects of 5: INSERT INTO WORKS_ON VALUES ('333445555', 1, 5.0); Then ask "every project of department 4" (10 and 30) instead: who comes out?

A common mistake: writing the "on every project" question with WHERE Pno IN (SELECT Pnumber FROM PROJECT WHERE Dnum = 5). That means "on at least one project" (∃), not "on every project" (∀). The counting method also works (HAVING COUNT(*) = (SELECT COUNT(*) …), notebook Exercise 8) but needs care with duplicates and grouping.

Other constructs

  • UNIQUE(Q): TRUE if the result of Q has no duplicate rows (standard SQL; MySQL does not support it). Tests whether the result of a query is a set or a multiset.
  • Explicit sets: WHERE Pno IN (1, 2, 3).
  • Renaming: new names for result columns with AS: SELECT E.Lname AS Employee_name, S.Lname AS Supervisor_name (Q8A).
SELECT DISTINCT Essn FROM WORKS_ON WHERE Pno IN (1, 2, 3);
SELECT E.Lname AS Employee_name, S.Lname AS Supervisor_name
FROM   EMPLOYEE AS E, EMPLOYEE AS S
WHERE  E.Super_ssn = S.Ssn;

Test yourself

What does SELECT Lname FROM EMPLOYEE WHERE Salary > ALL (SELECT Salary FROM EMPLOYEE WHERE Dno = 7) return? (There is no department 7.)

  1. All the employees
  2. Nobody
  3. An error: the subquery is empty
  4. Only the highest-paid one (Borg)
x > ALL V means "V has no element greater than or equal to x"; if V is empty this is always true. So when you use ALL, think about the possibility that the subquery comes back empty.
SELECT Lname FROM EMPLOYEE WHERE Salary > ALL (SELECT Salary FROM EMPLOYEE WHERE Dno = 7);

Which query is not a correct answer to "employees who have at least one dependent"?

  1. SELECT Lname FROM EMPLOYEE WHERE Ssn IN (SELECT Essn FROM DEPENDENT)
  2. SELECT Lname FROM EMPLOYEE E WHERE EXISTS (SELECT * FROM DEPENDENT D WHERE D.Essn = E.Ssn)
  3. SELECT Lname FROM EMPLOYEE, DEPENDENT WHERE Ssn = Essn
  4. SELECT DISTINCT Lname FROM EMPLOYEE, DEPENDENT WHERE Ssn = Essn
IN and EXISTS select each employee at most once; a join produces one row for each matching pair of rows. Wong has three dependents, Smith three, Wallace one: C returns seven rows, the others three. (If two employees had the same last name, D would merge them too; SELECT DISTINCT Ssn, Lname is safer for that.)

For an employee whose Salary is NULL, what is the result of the condition WHERE Salary > 30000 OR Dno = 5? (The employee's Dno is 5.)

  1. UNKNOWN; the row is not selected
  2. FALSE; the row is not selected
  3. TRUE; the row is selected
  4. An error
UNKNOWN OR TRUE = TRUE. In an OR a single TRUE is enough. If Dno were 4, it would be UNKNOWN OR FALSE = UNKNOWN and the row would not be selected.

SELECT Lname FROM EMPLOYEE WHERE Dno NOT IN (SELECT Dnum FROM PROJECT WHERE Plocation = 'Houston'). The projects in Houston are ProductZ (Dnum 5) and Reorganization (Dnum 1). Who is in the result?

  1. Nobody, NOT IN always returns nothing
  2. Those in department 4: Zelaya, Wallace, Jabbar
  3. Those in departments 5 and 1
  4. All the employees
Since there is no NULL in the inner query, NOT IN works normally: Dno ∉ {5, 1}. NOT IN returns nothing only when the inner query contains a NULL.

Which one is a correlated nested query?

  1. SELECT Lname FROM EMPLOYEE WHERE Dno IN (SELECT Dnumber FROM DEPARTMENT WHERE Dname = 'Research')
  2. SELECT Lname FROM EMPLOYEE WHERE Salary > (SELECT AVG(Salary) FROM EMPLOYEE)
  3. SELECT Pname FROM PROJECT WHERE Pnumber IN (1, 2, 3)
  4. SELECT Lname FROM EMPLOYEE E WHERE Salary > (SELECT AVG(Salary) FROM EMPLOYEE X WHERE X.Dno = E.Dno)
The criterion: does the inner query use a column of a table in the outer query? In D the inner query uses E.Dno; for each employee the average of their own department is computed again. B is independent: it is computed once. (AVG is the aggregate function that gives the average; on the next page.)

Which is the correct template for "employees who work on all the projects"?

  1. … WHERE NOT EXISTS (SELECT * FROM PROJECT P WHERE NOT EXISTS (SELECT * FROM WORKS_ON W WHERE W.Essn = E.Ssn AND W.Pno = P.Pnumber))
  2. … WHERE EXISTS (SELECT * FROM WORKS_ON W WHERE W.Essn = E.Ssn)
  3. … WHERE E.Ssn IN (SELECT Essn FROM WORKS_ON)
  4. … WHERE NOT EXISTS (SELECT * FROM WORKS_ON W WHERE W.Essn = E.Ssn)
"There is no project that E does not work on": the outer NOT EXISTS ranges over the projects, the inner NOT EXISTS expresses "E does not work on this project". B and C mean "on at least one project", D "on no project".
