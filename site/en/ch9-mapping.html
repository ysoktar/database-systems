ER-to-relational mapping

At the end of conceptual design we have an ER or EER diagram, while the DBMS works with tables. The mapping algorithm of Ch 9 turns every construct of the diagram, step by step, into tables, primary keys and foreign keys. On this page you can see the rule of each step, the reason for it and its result on COMPANY.

  • Map an ER diagram to tables with the nine-step algorithm, and determine each table's primary key and foreign keys correctly.
  • Compare the three approaches for 1:1 relationships (foreign key, merged table, separate relationship table) and say when each one fits.
  • Decide which of the options 8A, 8B, 8C and 8D can be used for a specialization by looking at its constraints (total/partial, disjoint/overlapping).
  • Map a category (union type) with a surrogate key; explain which ER constraints are lost in the mapping.

Scope. All the Ch 9 slides (1–38), which the syllabus assigns to week 9, are on this page. The ER and EER concepts themselves are explained on the Ch 3 and Ch 4 pages; here only their translation into tables is covered.

Goals of the mapping

Three goals are kept in mind during mapping. The first is to preserve all the information: every attribute of the diagram must appear as a column in a table. The second is to preserve the constraints as far as possible: keys become primary keys, relationships become foreign keys. But the relational model cannot express every ER constraint; for example, an upper bound such as "a department can have at most 10 employees", or a complete classification such as "every student is either domestic or foreign", cannot be enforced with tables. The third is to minimize NULL values: columns that would stay empty in most rows make the design worse.

The algorithm here is implemented in most commercial design tools. The site's ER studio uses the same algorithm too: you can draw your own diagram and see its translation into tables step by step.

The mapping algorithm: Steps 1–7

Step 1: Regular (strong) entity types

For each regular entity type E, a table R is created and all the simple attributes of E are added to R as columns. Of composite attributes only the simple components are taken; for example Fname, Minit and Lname are added instead of Name. One of E's key attributes is chosen as R's primary key; if the chosen key is composite, all the simple attributes that form it together become the primary key. In COMPANY this step creates the tables EMPLOYEE, DEPARTMENT and PROJECT; their primary keys are Ssn, Dnumber and Pnumber.

Step 2: Weak entity types

For each weak entity type W whose owner is E, a table R is created and the simple attributes of W are added to R. The primary key of the owner's table is added to R as a foreign key. R's primary key is the combination of the owner's primary key and W's partial key. In COMPANY the DEPENDENT table is made this way: EMPLOYEE's Ssn is added as a foreign key under the name Essn, and the primary key becomes {Essn, Dependent_name}. Since the weak entities become meaningless when their owner is deleted, this foreign key usually has ON DELETE CASCADE.

Step 3: Binary 1:1 relationship types

For each binary 1:1 relationship type R, the tables S and T that correspond to the participating entity types are identified. There are three approaches:

  1. The foreign key approach (two tables). One of the tables, say S, is chosen and T's primary key is added to S as a foreign key. It is better to choose the entity that totally participates in the relationship as S, because then the foreign key is NULL in no row. In COMPANY DEPARTMENT is chosen for MANAGES, because every department has a manager but not every employee manages a department. So DEPARTMENT gets a Mgr_ssn column; the relationship's attribute Start_date also goes to DEPARTMENT as Mgr_start_date.
  2. A merged table (one table). The two entity types and the relationship are merged into a single table. This approach fits when both participations are total, because then both sides of every row are filled.
  3. A separate relationship table (three tables). A third table (a cross-reference) is created that links the primary keys of the two tables. This is the same method used for M:N relationships, and it is the least preferred approach for 1:1.

You can see with the COMPANY data why the foreign key goes to the side with total participation. The first box queries the design the book chooses: the Mgr_ssn column of DEPARTMENT has no NULLs. The second box works out what each employee's row would hold if the foreign key were put in EMPLOYEE; the value comes out NULL for every employee who is not a manager.

SELECT Dnumber, Dname, Mgr_ssn, Mgr_start_date
FROM   DEPARTMENT;

SELECT E.Ssn, E.Fname, D.Dnumber AS Manages_dno
FROM   EMPLOYEE E LEFT JOIN DEPARTMENT D ON D.Mgr_ssn = E.Ssn;

SELECT COUNT(*) AS employees, COUNT(D.Dnumber) AS filled, COUNT(*) - COUNT(D.Dnumber) AS null_rows
FROM   EMPLOYEE E LEFT JOIN DEPARTMENT D ON D.Mgr_ssn = E.Ssn;

Step 4: Binary 1:N relationship types

For each binary 1:N relationship type R, the table S of the entity type on the N side of the relationship is identified. The primary key of the other table (T) is added to S as a foreign key; the relationship's simple attributes also go to S. The reason is that every entity on the N side takes part in the relationship at most once: since every employee has a single department, the department number fits in the employee's row. In COMPANY, for WORKS_FOR DEPARTMENT's primary key is added to EMPLOYEE as Dno, for CONTROLS to PROJECT as Dnum, and for the recursive SUPERVISION to EMPLOYEE as Super_ssn. Using a relationship table is also possible but is rarely done.

Step 5: Binary M:N relationship types

For each binary M:N relationship type R, a new table S is created, a relationship table. The primary keys of the participating entity types' tables are added to S as foreign keys, and their combination becomes S's primary key. The relationship's simple attributes are added to S too. An M:N relationship cannot be expressed with a single foreign key, because an employee works on many projects and a project has many employees. In COMPANY WORKS_ON is made this way: the primary keys of EMPLOYEE and PROJECT are added as Essn and Pno, the Hours column is the relationship's attribute, and the primary key is {Essn, Pno}.

The box below shows with data why an M:N relationship does not fit into either side. The first query lists the employees who work on more than one project, the second the projects with more than one employee. Since neither list is empty, neither a single Pno column in EMPLOYEE nor a single Essn column in PROJECT can hold this information.

SELECT Essn, COUNT(*) AS projects
FROM   WORKS_ON GROUP BY Essn HAVING COUNT(*) > 1;

SELECT Pno, COUNT(*) AS employees
FROM   WORKS_ON GROUP BY Pno HAVING COUNT(*) > 1;

Step 6: Multivalued attributes

For each multivalued attribute A, a new table R is created. R has a column for A and the primary key K of the table of the entity that A belongs to (as a foreign key). R's primary key is the combination of A and K. If A is composite, its simple components are added. In COMPANY the table DEPT_LOCATIONS(Dnumber, Dlocation) is created for DEPARTMENT's Locations attribute; its primary key is {Dnumber, Dlocation}, because a department has several locations.

SELECT Dnumber, Dlocation FROM DEPT_LOCATIONS ORDER BY Dnumber;

Step 7: n-ary (n > 2) relationship types

For each n-ary relationship type R, a new table S is created. The primary keys of all the participating entity types are added to S as foreign keys, and the relationship's simple attributes as columns. The primary key is usually the combination of all the foreign keys. However, if a participant's cardinality is 1, that participant's foreign key is not included in the primary key, because a combination of the others already determines that participant. Information lost in the mapping. Tables cannot carry everything an ER diagram says. The total participation of the "1" side of a 1:N relationship (every department must have at least one employee) cannot be enforced with a foreign key. An upper bound such as (1,10), derived attributes and a specialization being disjoint also do not show directly in the tables; they need CHECK, triggers or application code.

Mapping EER constructs: Step 8

Each specialization or generalization with superclass C (attributes {k, a1, …, an}, primary key k) and subclasses {S1, …, Sm} is turned into tables with one of four options:

OptionTablesWhen can it be used?
8A: separate tables for the superclass and the subclassesL(k, a1, …, an) for the superclass; Li(k, attributes of Si) for each subclass. Each Li's k is a foreign key to L.Always: total or partial, disjoint or overlapping.
8B: subclass tables onlyLi(k, a1, …, an, attributes of Si) for each subclass; no table for the superclass.Only for a total specialization, because there is no table for an entity that is in no subclass. If it is overlapping, an entity repeats in several tables.
8C: a single table with one type columnL(k, a1, …, an, the attributes of all subclasses, t). The column t (the type or discriminating attribute) says which subclass a row belongs to.Only for a disjoint specialization, because t can take a single value. With many subclass-specific attributes there are many NULLs.
8D: a single table with several Boolean type columnsL(k, a1, …, an, the attributes of all subclasses, t1, …, tm). Each ti is a Boolean that says whether the row belongs to Si.Can be used for an overlapping specialization too.

Shared subclasses and categories (Step 9)

Shared subclasses

A shared subclass such as STUDENT_ASSISTANT is a subclass of several classes (multiple inheritance). All these classes must have the same key; if their keys differed, the subclass would be modelled as a category. The options of Step 8 can be applied to a shared subclass too. In the simplified UNIVERSITY schema below, STUDENT_ASSISTANT is a subclass of both EMPLOYEE and STUDENT; with 8A its table's primary key becomes a foreign key to both superclasses.

Step 9: Categories (union types)

When mapping a category whose superclasses have different keys, the table for the category gets a new key column. This is called a surrogate key. In the book's example an OWNER table is created for the OWNER category, and its primary key is the surrogate key Owner_id. The table of each superclass that forms the category (PERSON, BANK, COMPANY) gets an Owner_id foreign key that refers to this key; for those who own no vehicle this column stays NULL. The superclasses of the REGISTERED_VEHICLE category (CAR and TRUCK), on the other hand, share the same key (Vehicle_id), so no surrogate key is needed.

Test yourself

How is the relationship EMPLOYEE —(N)— WORKS_FOR —(1)— DEPARTMENT mapped?

  1. EMPLOYEE's Ssn is added to DEPARTMENT as a foreign key.
  2. DEPARTMENT's Dnumber is added to EMPLOYEE as a foreign key.
  3. A separate table called WORKS_FOR must be created.
  4. EMPLOYEE and DEPARTMENT are merged into a single table.
Step 4: in a 1:N relationship the foreign key goes into the table on the N side. Since every employee has a single department, the Dno column carries one value in each row of EMPLOYEE. Put the other way round, a department's many employees would not fit in a single column.

What is the primary key of the table for the weak entity DEPENDENT (partial key Dependent_name, owner EMPLOYEE)?

  1. {Dependent_name}
  2. {Essn}
  3. {Essn, Dependent_name}
  4. A new artificial key, Dependent_id
Step 2: the primary key of a weak entity's table is the combination of the owner's primary key (Essn, added as a foreign key) and the weak entity's partial key (Dependent_name).

The relationship STUDENT —(M)— ENROLLS —(N)— COURSE has a Grade attribute. Where does Grade go?

  1. Into the table ENROLLS(Student_id, Course_id, Grade); primary key {Student_id, Course_id}
  2. Into the STUDENT table
  3. Into the COURSE table
  4. Into a separate table called GRADE
Step 5: for an M:N relationship a relationship table is created with the two foreign keys (and a primary key made of their combination); the relationship's attributes go here too. Since Grade belongs to a (student, course) pair, it fits in neither the student's nor the course's row.

The specialization PERSON → {STUDENT, STAFF} is overlapping and partial. Which option can be used?

  1. Only 8B
  2. Only 8C
  3. 8B or 8C
  4. 8A or 8D
8A can be used for any specialization. 8B does not fit because it is partial (people with no subclass would be lost). 8C does not fit because it is overlapping (a single type column cannot show two subclasses). In 8D each subclass has its own Boolean column, so overlapping can be expressed too.

In the category OWNER = PERSON ∪ BANK ∪ COMPANY the three superclasses have different keys (Ssn, Bname, Cname). What is done in the mapping?

  1. The primary key of the OWNER table becomes {Ssn, Bname, Cname}.
  2. OWNER gets a surrogate key (Owner_id); an Owner_id foreign key is added to the PERSON, BANK and COMPANY tables.
  3. No table is created for OWNER.
  4. OWNER's primary key becomes PERSON's Ssn.
Step 9: if the superclasses have different keys, the category table gets a surrogate key. Each superclass table gets a foreign key that refers to this key; in rows that do not belong to the category this column is NULL.
