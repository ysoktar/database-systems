Constraints, triggers, views, ALTER

Assertions: general constraints (7.2.1)

CREATE ASSERTION is a declarative constraint not tied to a single table. It takes a name and a CHECK condition; the condition must be TRUE in every state of the database. The pattern: "write a query that finds the violating rows, and put NOT EXISTS in front of it."

-- "An employee's salary must not be greater than the salary of the manager of the department
--  that the employee works for."
CREATE ASSERTION SALARY_CONSTRAINT
CHECK ( NOT EXISTS ( SELECT *
                     FROM   EMPLOYEE E, EMPLOYEE M, DEPARTMENT D
                     WHERE  E.Salary > M.Salary
                       AND  E.Dno = D.Dnumber
                       AND  D.Mgr_ssn = M.Ssn ) );
  • The DBMS rejects any operation that would change the database so that this condition is violated.
  • The difference from CHECK (on an attribute / tuple / domain): a CHECK is checked only when the row concerned is inserted or modified. That is why it is not reliable for conditions that look at other tables. An assertion must hold at all times. CHECK is preferred when possible, because it is enforced more efficiently.
  • Few DBMSs support assertions; MySQL does not either. In practice the same rule is enforced with a trigger (below). But the query inside the assertion runs on any DBMS: an empty result means the rule holds.

The box below runs the query in the assertion's condition: at first there are no violating rows; then Narayan's salary is raised above that of his manager Wong (40000) and the same query now returns a row. With the assertion, the DBMS would reject this UPDATE.

-- violating rows before the update (none)
SELECT E.Lname AS employee, E.Salary, M.Lname AS manager, M.Salary AS mgr_salary
FROM   EMPLOYEE E, EMPLOYEE M, DEPARTMENT D
WHERE  E.Salary > M.Salary AND E.Dno = D.Dnumber AND D.Mgr_ssn = M.Ssn;
-- now break the rule and look again
UPDATE EMPLOYEE SET Salary = 45000 WHERE Lname = 'Narayan';
-- violating rows after the update
SELECT E.Lname AS employee, E.Salary, M.Lname AS manager, M.Salary AS mgr_salary
FROM   EMPLOYEE E, EMPLOYEE M, DEPARTMENT D
WHERE  E.Salary > M.Salary AND E.Dno = D.Dnumber AND D.Mgr_ssn = M.Ssn;

Triggers (7.2.2)

A trigger specifies an action to be taken when certain events occur and certain conditions are satisfied: an ECA rule (Event–Condition–Action).

  1. Event: usually an update operation: INSERT, DELETE, UPDATE (or UPDATE OF Salary, Super_ssn on particular columns). Timing: BEFORE, AFTER (or INSTEAD OF).
  2. Condition: with WHEN; optional. Without a condition the action runs when the event occurs; with one, only if the condition is TRUE.
  3. Action: usually a sequence of SQL statements or a call to a stored procedure.

FOR EACH ROW (row-level): once for each affected row; NEW and OLD are the new and old versions of that row. FOR EACH STATEMENT: once per statement. The book's example (close to Oracle syntax):

-- R5: inform the supervisor whenever an employee's salary becomes greater than the supervisor's
CREATE TRIGGER SALARY_VIOLATION
BEFORE INSERT OR UPDATE OF Salary, Super_ssn ON EMPLOYEE
FOR EACH ROW
WHEN ( NEW.Salary > ( SELECT Salary FROM EMPLOYEE WHERE Ssn = NEW.Super_ssn ) )
  INFORM_SUPERVISOR(NEW.Super_ssn, NEW.Ssn);

In MySQL the same trigger is written a little differently: a trigger is tied to a single event (a separate trigger for each event instead of INSERT OR UPDATE), there is no UPDATE OF columns and no WHEN; the condition is written inside the action with IF … THEN … END IF. Since the action contains several statements, it is in a BEGIN … END block. So that the ;s inside the block do not end the statement, the delimiter is changed temporarily with DELIMITER // (as in the mysql client; the boxes on this site understand it too).

The version below logs the event in a table (demo.SALARY_LOG) instead of informing the supervisor. Smith's supervisor Wong earns 40000. When Smith's salary is set to 42000 the condition is TRUE and the trigger writes a row; when Narayan's is set to 31000 the condition is FALSE and nothing is written.

DROP TRIGGER IF EXISTS SALARY_VIOLATION;   -- so that the box can be run again
DROP TABLE IF EXISTS demo.SALARY_LOG;
CREATE TABLE demo.SALARY_LOG (Super_ssn CHAR(9), Ssn CHAR(9), New_salary DECIMAL(10,2), At DATETIME);

DELIMITER //
CREATE TRIGGER SALARY_VIOLATION
BEFORE UPDATE ON EMPLOYEE                 -- event (a second trigger would cover BEFORE INSERT)
FOR EACH ROW
BEGIN
  IF NEW.Salary > (SELECT Salary FROM EMPLOYEE WHERE Ssn = NEW.Super_ssn) THEN    -- condition
    INSERT INTO demo.SALARY_LOG VALUES (NEW.Super_ssn, NEW.Ssn, NEW.Salary, NOW()); -- action
  END IF;
END//
DELIMITER ;

-- Smith (supervisor Wong, 40000) gets a raise to 42000: the trigger fires
UPDATE EMPLOYEE SET Salary = 42000 WHERE Ssn = '123456789';
-- Narayan (supervisor Wong) gets 31000: the condition is FALSE, nothing is logged
UPDATE EMPLOYEE SET Salary = 31000 WHERE Ssn = '666884444';
SELECT * FROM demo.SALARY_LOG;

A trigger can also be used to enforce a constraint: the action stops the operation with an error. In MySQL the way to do this is SIGNAL SQLSTATE '45000' (a user-defined error). In DBMSs that do not support assertions, the rule "a salary cannot exceed the supervisor's" is enforced like this:

DROP TRIGGER IF EXISTS SALARY_VIOLATION;
DROP TRIGGER IF EXISTS SALARY_CONSTRAINT;
DELIMITER //
CREATE TRIGGER SALARY_CONSTRAINT
BEFORE UPDATE ON EMPLOYEE
FOR EACH ROW
BEGIN
  IF NEW.Salary > (SELECT Salary FROM EMPLOYEE WHERE Ssn = NEW.Super_ssn) THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'A salary cannot exceed the supervisor''s salary';
  END IF;
END//
DELIMITER ;
UPDATE EMPLOYEE SET Salary = 35000 WHERE Ssn = '453453453';   -- English, supervisor Wong (40000): fine
UPDATE EMPLOYEE SET Salary = 50000 WHERE Ssn = '453453453';   -- rejected by the trigger

This trigger runs only when the supervisee's row changes. A violation can still arise when the supervisor's salary is lowered; a complete solution needs a second condition that also checks changes on the supervisor side of EMPLOYEE. That is why giving the "TRUE in every state" meaning of an assertion with triggers takes more effort. To remove the trigger: DROP TRIGGER SALARY_CONSTRAINT; or Reset database.

Uses of triggers: enforcing constraints (instead of assertions), keeping derived data up to date (e.g. a Total_sal column added to DEPARTMENT: the book's rules R1–R4), notifying users of a situation, keeping materialized views up to date, an audit log.

Views (7.3)

A view is a single table derived from other tables: a virtual table. Usually not stored physically. Used to simplify complex queries that are asked often, for security (showing the user only some columns) and for logical data independence.

-- the book writes CREATE VIEW; OR REPLACE lets the box run again
CREATE OR REPLACE VIEW WORKS_ON1 AS
  SELECT Fname, Lname, Pname, Hours
  FROM   EMPLOYEE, PROJECT, WORKS_ON
  WHERE  Ssn = Essn AND Pno = Pnumber;

CREATE OR REPLACE VIEW DEPT_INFO (Dept_name, No_of_emps, Total_sal) AS
  SELECT   Dname, COUNT(*), SUM(Salary)
  FROM     DEPARTMENT, EMPLOYEE
  WHERE    Dnumber = Dno
  GROUP BY Dname;

-- QV1: a view is queried like a table
SELECT Fname, Lname FROM WORKS_ON1 WHERE Pname = 'ProductX';
SELECT * FROM DEPT_INFO;

A view is always up to date: when the base tables change, the view's result changes too. It is computed when it is queried, not when it is defined. (Compare with the WORKS_ON_INFO copy in Ch 6.)

SELECT * FROM DEPT_INFO;          -- before
UPDATE EMPLOYEE SET Dno = 1 WHERE Lname = 'English';
SELECT * FROM DEPT_INFO;          -- after: Research lost one employee, Headquarters gained one

How are views implemented?

  • Query modification: a query on the view is turned into a query on the base tables (QV1 → a query combined with WORKS_ON1's definition). Disadvantage: complex views that are queried often are recomputed every time.
  • View materialization: the view is stored physically when it is first queried (a materialized view) and updated as the base tables change. Update strategies: immediate (as soon as a base table changes), lazy (when the view is queried), periodic (at intervals; being out of date for a short time is accepted). Efficient updating is called incremental update.

Updating through views

An INSERT/UPDATE/DELETE on a view is possible if it can be turned into updates that have a counterpart on the base tables. The general rules:

  • A view on a single table, without aggregates, that contains the base table's primary key (and its NOT NULL columns without a DEFAULT) is updatable: each view row corresponds to exactly one base table row.
  • In views with joins over several tables an update is usually ambiguous: the same view update can be done by several different base table updates.
  • Views with grouping and aggregates cannot be updated: changing DEPT_INFO.Total_sal has no single meaning on the base tables.
  • In SQL WITH CHECK OPTION is added to a view that is meant to be updatable: inserts and updates through the view must satisfy the view's condition, otherwise they are rejected.
  1. How many base tables are there? If more than one (a join), an update is usually ambiguous: not updatable in standard SQL.
  2. Is there grouping, an aggregate or DISTINCT? If so, a view row was computed from many base rows: not updatable.
  3. Are the base table's primary key and its NOT NULL columns (without a DEFAULT) in the view? If not, you cannot INSERT into the view (the missing columns cannot be given values); UPDATE and DELETE may still be possible.

Apply it: WORKS_ON1 is a join over three tables (stuck at question 1). DEPT_INFO contains GROUP BY and COUNT/SUM (stuck at question 2). DEPT5_EMPS below is a single table, no aggregate, Ssn included: updatable.

-- UV1: Smith moves from ProductX to ProductY? or ProductX is renamed? Ambiguous:
UPDATE WORKS_ON1 SET Pname = 'ProductY'
WHERE  Lname = 'Smith' AND Fname = 'John' AND Pname = 'ProductX';

The book gives two possible translations of this update: (a) move Smith's ProductX row in WORKS_ON to ProductY (the intended one), (b) rename ProductX to ProductY in PROJECT (a change that is also visible for the project's other employees; wrong). That is why standard SQL does not consider views with joins updatable. MySQL, however, updates a view with a join if all the changed columns belong to a single base table: since Pname is a column of PROJECT, it does (b) and ProductX is renamed for everybody. That is the practical consequence of the ambiguity.

The engine on this site does not support updating through views (an UPDATE on a view gives an error). You can make the two translations on the base tables and look at how the view changes:

-- (a) the intended one: Smith's WORKS_ON row for ProductX (1) moves to ProductY (2)?
--     Smith already works on ProductY, so (Essn, Pno) would repeat the key; move his hours instead:
UPDATE WORKS_ON SET Hours = Hours + 32.5 WHERE Essn = '123456789' AND Pno = 2;
DELETE FROM WORKS_ON WHERE Essn = '123456789' AND Pno = 1;
SELECT * FROM WORKS_ON1 WHERE Lname = 'Smith';
-- (b) the other one (what MySQL does): rename the project for everybody
UPDATE PROJECT SET Pname = 'ProductY2' WHERE Pname = 'ProductX';   -- Pname is UNIQUE, so 'ProductY2'
SELECT * FROM WORKS_ON1 WHERE Pname LIKE 'ProductY%' ORDER BY Pname, Lname;

A single-table view without aggregates, on the other hand, is updatable. WITH CHECK OPTION prevents an update through the view from moving a row out of the view:

CREATE VIEW DEPT5_EMPS AS
  SELECT Ssn, Fname, Lname, Salary, Dno
  FROM   EMPLOYEE
  WHERE  Dno = 5
  WITH CHECK OPTION;
UPDATE DEPT5_EMPS SET Salary = Salary + 1000 WHERE Lname = 'Wong';   -- fine: changes one EMPLOYEE row
UPDATE DEPT5_EMPS SET Dno = 4 WHERE Lname = 'Wong';                 -- Wong would leave the view: rejected
-- MySQL: ERROR 1369 (HY000): CHECK OPTION failed 'company.DEPT5_EMPS'

This box cannot be run (the engine on the site does not support updating through views); in real MySQL the first UPDATE changes Wong's EMPLOYEE row and the second is rejected with the error in the comment. Without CHECK OPTION the second UPDATE would be accepted and Wong would "disappear" from the view.

Other uses of views: authorization (giving a user privileges only on a view: the employees of one department, or a view of EMPLOYEE without salaries) and inline views (views defined inside FROM). To remove a view: DROP VIEW WORKS_ON1;

Schema change (7.4)

DROP

  • DROP SCHEMA COMPANY CASCADE; deletes the schema and everything in it. RESTRICT: deletes it only if the schema is empty.
  • DROP TABLE DEPENDENT CASCADE; deletes the table and all the constraints and views that refer to it. RESTRICT: rejects the drop if an FK or a view refers to the table.
  • DROP TABLE also deletes the table's definition; to delete only the rows, DELETE.

In MySQL these rules work differently; in the exam write the book's (standard SQL) meaning. MySQL accepts the words RESTRICT and CASCADE but ignores them: if another table's foreign key refers to it, DROP TABLE is always rejected (error 3730), while views are not checked at all: the table is dropped and the view that depends on it is left invalid. In MySQL DROP SCHEMA and DROP DATABASE are the same.

DROP TABLE DEPARTMENT;   -- EMPLOYEE.Dno, PROJECT.Dnum, DEPT_LOCATIONS.Dnumber reference it

CREATE OR REPLACE VIEW DEP_VIEW AS SELECT Essn, Dependent_name FROM DEPENDENT;
-- the book: RESTRICT refuses the drop, because the view depends on DEPENDENT.
-- MySQL ignores RESTRICT: DEPENDENT is dropped (no foreign key references it) ...
DROP TABLE DEPENDENT RESTRICT;
-- ... and the view is left behind, invalid:
SELECT * FROM DEP_VIEW;

ALTER

Changes the definition of a table: adding/dropping columns, changing a column definition, adding/dropping constraints.

-- add a column: existing rows get NULL (or the DEFAULT); NOT NULL is only allowed with a DEFAULT
ALTER TABLE COMPANY.EMPLOYEE ADD COLUMN Job VARCHAR(12);
UPDATE EMPLOYEE SET Job = 'Engineer' WHERE Dno = 5;
SELECT Lname, Dno, Job FROM EMPLOYEE ORDER BY Dno;
-- change a default, drop a default
ALTER TABLE COMPANY.DEPARTMENT ALTER COLUMN Mgr_ssn DROP DEFAULT;
ALTER TABLE COMPANY.DEPARTMENT ALTER COLUMN Mgr_ssn SET DEFAULT '333445555';
-- drop a named constraint (the book: DROP CONSTRAINT EMPSUPERFK CASCADE), then a column
ALTER TABLE COMPANY.EMPLOYEE DROP FOREIGN KEY EMPSUPERFK;
ALTER TABLE COMPANY.EMPLOYEE DROP COLUMN Address;
SELECT COLUMN_NAME FROM information_schema.COLUMNS
WHERE  TABLE_SCHEMA = 'company' AND TABLE_NAME = 'EMPLOYEE' ORDER BY ORDINAL_POSITION;

In the book, for DROP COLUMN either CASCADE (the constraints and views that refer to the column are deleted too) or RESTRICT (deleted only if nothing refers to it) must be chosen; MySQL does not use these words. To be able to drop a constraint it must have a name: that is why constraints are named in Ch 6. (MySQL writes DROP FOREIGN KEY name for a foreign key, and DROP CONSTRAINT name or DROP CHECK name for other constraints.)

Test yourself

CREATE VIEW V AS SELECT Ssn, Lname, Salary FROM EMPLOYEE WHERE Salary > 30000 WITH CHECK OPTION; Which update through this view is rejected?

  1. UPDATE V SET Salary = 45000 WHERE Lname = 'Wong'
  2. UPDATE V SET Lname = 'Wang' WHERE Lname = 'Wong'
  3. UPDATE V SET Salary = 28000 WHERE Lname = 'Wong'
  4. DELETE FROM V WHERE Lname = 'Wong'
WITH CHECK OPTION requires that after an INSERT or UPDATE through the view the row still satisfies the view's condition. Since Wong, with his salary lowered to 28000, would "disappear" from the view, the update is rejected.

If you read a trigger as "when an employee is inserted or their salary changes, inform the supervisor if the salary exceeds the supervisor's", what are its ECA components?

  1. Event: an INSERT or a Salary update · Condition: new salary > the supervisor's salary · Action: inform the supervisor
  2. Event: the salary exceeding the supervisor's · Condition: INSERT · Action: inform the supervisor
  3. Event: an INSERT or a Salary update · Condition: inform the supervisor · Action: none
  4. Event: a salary update · Condition: none · Action: reject the update
First "when?" (the event: an INSERT/UPDATE/DELETE), then "in which situation?" (the condition, optional), then "what should be done?" (the action). The book's SALARY_VIOLATION trigger is this sentence in SQL.

Which is true of the view CREATE VIEW V AS SELECT Dno, AVG(Salary) AS Avg_sal FROM EMPLOYEE GROUP BY Dno;?

  1. UPDATE V SET Avg_sal = 40000 WHERE Dno = 5 is valid; the DBMS raises the salaries proportionally.
  2. V cannot be updated because it contains an aggregate; but it can be queried and is always up to date.
  3. V stores the data of the moment it was defined; it does not show later changes.
  4. V becomes updatable if WITH CHECK OPTION is added.
Changing an average has no single counterpart on the base tables. A view is recomputed when it is queried (query modification), so it is always up to date. WITH CHECK OPTION enforces the condition in updatable views; it does not make a non-updatable view updatable.

Why can the rule "an employee's salary cannot exceed their supervisor's" not be enforced reliably with a tuple CHECK?

  1. CHECK cannot make numeric comparisons.
  2. CHECK can only be used on primary keys.
  3. A CHECK is checked only when that row is inserted or changed; when the supervisor's salary is lowered, the supervisee's row is not checked.
  4. CHECK gives an error on NULL values.
The rule depends on two different rows. A violation can arise when the supervisor's row changes, but the CHECK on the supervisee's row is not triggered. Such rules are enforced with an assertion or a trigger.

What are the three components of a trigger, in order?

  1. Event, Condition, Action
  2. Condition, Event, Action
  3. Action, Event, Condition
  4. Event, Action, Commit
ECA: an event (INSERT/UPDATE/DELETE) happens; if the condition (WHEN) is TRUE, the action runs. The condition is optional.

What happens with DROP TABLE DEPARTMENT RESTRICT; in COMPANY?

  1. DEPARTMENT and all the FKs referring to it are deleted.
  2. Only the rows are deleted, the table definition remains.
  3. DEPARTMENT is dropped and the EMPLOYEE.Dno values become NULL.
  4. It is rejected: EMPLOYEE, PROJECT and DEPT_LOCATIONS refer to DEPARTMENT.
RESTRICT rejects the drop if a constraint or a view refers to the table. With CASCADE the table and the referring constraints (the FKs) would be dropped; the referring tables themselves are not dropped. (In MySQL a table referenced by a foreign key cannot be dropped, whether RESTRICT is written or not; you saw it in the box above.)
-- MySQL: a table that a foreign key refers to cannot be dropped (RESTRICT or not)
DROP TABLE DEPARTMENT RESTRICT;
