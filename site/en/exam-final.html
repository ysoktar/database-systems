Study plan

The topics build on one another, so the order below is recommended. At each step first read the page, then use its player or SQL boxes yourself, and finally solve the page's quizzes.

  1. Concepts (Ch 1–2): definitions, the three-schema architecture, data independence. To prepare for short-answer questions, answer the concept questions of the midterm guide.
  2. ER and EER (Ch 3–4): practise drawing diagrams from requirements with at least two exercises in the ER studio.
  3. Mapping (Ch 9): right after that, turn the diagrams you drew into tables. The step-by-step player shows Steps 1–9 on one schema.
  4. The relational model and constraints (Ch 5): keys and which operation violates which constraint.
  5. Normalization (Ch 14): finding keys, normal forms and decomposition. It is good to study it after mapping, because a good mapping usually already produces 3NF tables.
  6. SQL (Ch 6–7) and relational algebra (Ch 8): write the same questions in both languages. Check the notebook exercises with the site's MySQL, then write the algebra for the same queries.
  7. PHP (Ch 11): reading code, string types, the fetchRow loop and placeholders.
  8. Files and indexes (Ch 16–17): solve block and index cost computations and B+-tree insertion on paper and check them with the players.
  9. Transactions (Ch 20): concurrency problems, ACID, recoverability and serializability of schedules.
  10. Mixed review: solve the end-to-end problem and the mixed practice set; go back to the topics you got wrong.

Ch 8–20: short-answer concept questions

  1. What is the difference between a natural join and an equijoin?

    An equijoin is a θ-join that uses only equality comparisons, and in the result the matching attributes of the two relations stay separate (as two columns with the same values). A natural join (*) does an equijoin on the attributes with the same name and drops one of these repeated columns.

  2. Why does the foreign key go to the N side when a 1:N relationship is mapped?

    Each entity on the N side takes part in the relationship at most once, so the other side's key fits into its row as a single value. In the other direction a row on the 1 side would have to hold many values; that breaks 1NF.

  3. What is the difference between 3NF and BCNF? When is a relation in 3NF but not in BCNF?

    BCNF requires X to be a superkey for every X → A. 3NF allows one extra escape: if A is a prime attribute, X need not be a superkey. So a dependency whose left side is not a superkey and whose right side is prime (like Instructor → Course in TEACH) leaves the relation in 3NF but breaks BCNF.

  4. How is a decomposition tested for losslessness?

    For a decomposition into two parts {R1, R2}, the NJB test: if the common attributes (R1 ∩ R2) determine the rest of one of the parts, that is, if (R1 ∩ R2) → (R1 − R2) or (R1 ∩ R2) → (R2 − R1) is in F⁺, the decomposition is lossless.

  5. Why is a primary index sparse and a dense secondary index dense?

    In a primary index the file is sorted on the index field, so knowing the first record of each block (the block anchor) is enough; the anchors tell which block a wanted value falls into. In a secondary index the file is not sorted on this field; the values are scattered over the blocks, so an entry is needed for every record.

  6. What is the difference between a leaf split and an internal node split in a B+-tree?

    When a leaf splits, the last value of the left leaf is copied to the parent; the value also stays in the leaf, because all values must be in the leaves. When an internal node splits, its middle value is moved to the parent and does not stay in the internal node, because internal nodes only show the way.

  7. Define recoverable, cascadeless and strict schedules in one sentence each.

    Recoverable: a transaction does not commit before the transactions whose values it read have committed. Cascadeless: transactions read only committed values, so there is no cascading rollback. Strict: nobody reads or writes X before the last transaction that wrote X ends; undoing is just restoring the before image.

  8. What is the difference between single-quoted and double-quoted PHP strings?

    Single-quoted strings are taken literally; a $variable inside is printed as is. In double-quoted strings (and here documents) the values of variables are put into the text and escape sequences such as \n are interpreted.

  9. Which DBMS component ensures each ACID property?

    Atomicity and durability are the responsibility of the recovery subsystem, isolation of concurrency control. Consistency preservation is the responsibility of the programmer who writes the transaction and of the modules that enforce integrity constraints.

End-to-end worked problem: a library

  • The library's members are kept with a member number (unique), a name and one or more phones.
  • Every book has a unique ISBN, a title and a publisher.
  • A book can have several copies. Copies are numbered within the book (1, 2, …): the same copy number is used in different books. Every copy has a shelf code.
  • A copy is loaned to at most one member at a time; a member can borrow many copies. A due date is kept with the loan.

(a) The ER diagram (Ch 3)

Determine the entities, relationships, constraints and keys.

  • MEMBER(Mid, Name, {Phones}): Phones is multivalued.
  • BOOK(Isbn, Title, Publisher).
  • BOOK_COPY is a weak entity: the copy number is unique only within the book. Partial key Copy_no, owner BOOK; identifying relationship HAS_COPY (BOOK 1, BOOK_COPY N, the BOOK_COPY side total). Shelf is an attribute.
  • LOAN: a relationship between MEMBER (1) and BOOK_COPY (N); Due_date is the relationship's attribute. A copy may not be on loan and a member may have no loan: both sides are partial.

You can draw this diagram in the ER studio and see the next step there automatically too.

(b) Mapping to tables (Ch 9)

  • Step 1: MEMBER(Mid, Name), BOOK(Isbn, Title, Publisher).
  • Step 2: BOOK_COPY(Isbn, Copy_no, Shelf): Isbn is a foreign key to BOOK, and when the owner is deleted the copies must go too (ON DELETE CASCADE).
  • Step 4: LOAN is 1:N, so the foreign key goes to the N side, BOOK_COPY, and the relationship's attribute comes with it: BOOK_COPY(Isbn, Copy_no, Shelf, Mid, Due_date); Mid is a foreign key to MEMBER and is NULL for copies not on loan.
  • Step 6: MEMBER_PHONES(Mid, Phone).

The box below creates these tables with sample data; the next boxes use these tables.

DROP TABLE IF EXISTS demo.BOOK_COPY;
DROP TABLE IF EXISTS demo.BOOK;
DROP TABLE IF EXISTS demo.MEMBER;
CREATE TABLE demo.MEMBER (Mid INT PRIMARY KEY, Name VARCHAR(20) NOT NULL);
CREATE TABLE demo.BOOK (Isbn CHAR(4) PRIMARY KEY, Title VARCHAR(30), Publisher VARCHAR(20));
CREATE TABLE demo.BOOK_COPY (

  Mid      INT,

(c) A constraint violation (Ch 5)

Which constraint does INSERT INTO BOOK_COPY VALUES ('B009', 1, 'Z9', NULL, NULL); violate?

BOOK has no book with ISBN 'B009': the Isbn foreign key is not found in the referenced table, so referential integrity is violated and the DBMS rejects the insertion. The primary key (B009, 1) is not NULL and is unique, so the entity and key constraints hold; Mid being NULL is also valid, because a foreign key may be NULL. The box below shows this error (MySQL error code 1452).

INSERT INTO demo.BOOK_COPY VALUES ('B009', 1, 'Z9', NULL, NULL);

(d) SQL (Ch 6–7)

(1) Write the names and loan counts of the members who borrowed at least two copies. (2) Write the titles of the books all of whose copies are on loan.

(1) "A count per member" means GROUP BY, and "at least two" is a group condition, so HAVING. (2) "All copies on loan" means "no copy that is not on loan": NOT EXISTS.

SELECT   M.Name, COUNT(*) AS Loans
FROM     demo.MEMBER M JOIN demo.BOOK_COPY C ON C.Mid = M.Mid
GROUP BY M.Mid, M.Name
HAVING   COUNT(*) >= 2;

SELECT B.Title
FROM   demo.BOOK B
WHERE  NOT EXISTS (SELECT * FROM demo.BOOK_COPY C
                   WHERE C.Isbn = B.Isbn AND C.Mid IS NULL);

(e) Relational algebra (Ch 8)

Write in relational algebra the titles of the books Ayşe borrowed, and the loan count of every member.

AYSE ← σName='Ayse'(MEMBER)
AYSE_ISBNS ← πIsbn(BOOK_COPY ⋈BOOK_COPY.Mid=MEMBER.Mid AYSE)
RESULT ← πTitle(AYSE_ISBNS * BOOK)

COUNTS ← MidℑCOUNT Copy_no(σMid IS NOT NULL(BOOK_COPY))

Ayşe's books are Database Systems, Operating Systems and Algorithms. The attribute to the left of the grouping operation (Mid) forms the groups; the function to its right gives the value computed for each group.

(f) Normalization (Ch 14)

A developer uses a single table without mapping: LOAN_INFO(Mid, Isbn, Copy_no, Name, Title, Due_date). FDs: Mid → Name; Isbn → Title; {Isbn, Copy_no} → Mid, Due_date. Find the key, the normal form and the decomposition into BCNF.

Key: Isbn and Copy_no are on no right side. {Isbn, Copy_no}⁺: Isbn → Title adds Title, {Isbn, Copy_no} → Mid, Due_date adds Mid and Due_date, Mid → Name adds Name; all the attributes. The candidate key is {Isbn, Copy_no}.

Normal form: Isbn → Title is a partial dependency (Isbn is part of the key, Title is not prime): the relation is in 1NF. Mid → Name is transitive ({Isbn, Copy_no} → Mid → Name).

Decomposition: first {Isbn, Title} is split off (2NF), then {Mid, Name} (3NF); what remains is {Isbn, Copy_no, Mid, Due_date}. All three are in BCNF, the decomposition is lossless and every dependency is preserved. The result is the same tables as the mapping in (b): part of BOOK, MEMBER and BOOK_COPY. A good ER design and a correct mapping produce normalized tables.

(g) Choosing an index and its cost (Ch 16–17)

The BOOK_COPY table has 120,000 rows, the row size is 100 bytes and the block size 4096 bytes. The file is sorted on {Isbn, Copy_no}. The query "the copies borrowed by a member" runs very often. Which index do you recommend, and how many blocks does a dense secondary index on Mid (V = 4 bytes, P = 6 bytes) read, single-level and multilevel?

The file is sorted on {Isbn, Copy_no}, so no primary or clustering index can be built on Mid; a secondary index on Mid (in practice a B+-tree) is needed. The query is an equality search, so a hash index could work too, but a B+-tree also supports range queries.

Computation: bfr = ⌊4096 / 100⌋ = 40, b = ⌈120,000 / 40⌉ = 3000 blocks. An index entry is 10 bytes, fo = ⌊4096 / 10⌋ = 409. The 120,000 entries of the dense index take ⌈120,000 / 409⌉ = 294 blocks; a single-level search reads ⌈log₂ 294⌉ + 1 = 9 + 1 = 10 blocks. In the multilevel version the levels are 294 → 1 blocks: t = 2, a search reads 3 blocks (Mid is not unique, so each further matching copy reads at most one more block). Without an index the whole file, 3000 blocks, would be scanned.

(h) Transactions (Ch 20)

Two librarians try to lend the same copy to different members at the same time. Each reads the copy's Mid, sees that it is NULL, and writes their own member: r1(C); r2(C); w1(C); w2(C); c1; c2. What happens? Is the schedule serializable?

This is a lost update: both librarians saw the copy as free, T2's write overwrote T1's, and the copy lent to the first member is lost from the system. r1(C) and w2(C) give T1 → T2, r2(C) and w1(C) give T2 → T1: the graph has a cycle, so the schedule is not serializable. The schedule is recoverable (nobody reads an uncommitted value), but it is not correct. The DBMS prevents this with concurrency control (the locking protocols of Ch 21) and a suitable isolation level. You can try the schedule in the schedule analyzer.

Problem 1: relational algebra

On COMPANY: write in relational algebra the first and last names of the employees who work on all the projects John Smith works on.

The word "all" means division. First Smith's projects and the employee–project pairs are found, then the second is divided by the first:

SMITH ← σFname='John' AND Lname='Smith'(EMPLOYEE)
SMITH_PNOS ← πPno(WORKS_ON ⋈Essn=Ssn SMITH)
SSN_PNOS ← πEssn, Pno(WORKS_ON)
SSNS(Ssn) ← SSN_PNOS ÷ SMITH_PNOS
RESULT ← πLname, Fname(SSNS * EMPLOYEE)

Smith works on projects 1 and 2; those who work on both are Smith and English. The book's Figure 8.8 is this query; in the division player of the algebra page you can see every step before and after.

Problem 2: ER-to-relational mapping

Schema: STUDENT(Sid key, Name); COURSE(Cno key, Title); INSTRUCTOR(Iid key, Name, Phones multivalued). ENROLLS is an M:N relationship between STUDENT and COURSE with the attribute Grade. TEACHES is a relationship between INSTRUCTOR (1) and COURSE (N), and every course has an instructor (the COURSE side is total). Write the tables with their primary and foreign keys.

  • Step 1: STUDENT(Sid, Name), COURSE(Cno, Title), INSTRUCTOR(Iid, Name).
  • Step 4: TEACHES is 1:N, so the foreign key goes to the N side, COURSE: COURSE(Cno, Title, Iid), Iid → INSTRUCTOR. The COURSE side is total, so Iid can be NOT NULL.
  • Step 5: ENROLLS is M:N, so it becomes a new table: ENROLLS(Sid, Cno, Grade); Sid → STUDENT, Cno → COURSE.
  • Step 6: Phones is multivalued, so it becomes a new table: INSTRUCTOR_PHONES(Iid, Phone); Iid → INSTRUCTOR.

Problem 3: normalization

In the relation R(A, B, C, D, E), F = {AB → C, C → D, B → E}. Find the candidate key, the highest normal form of the relation and a lossless decomposition into BCNF. Are the dependencies preserved?

Key: A and B are on the right side of no dependency, so they are in every key. AB⁺: AB → C adds C, C → D adds D, B → E adds E; AB⁺ = {A, B, C, D, E}. The candidate key is {A, B}; the prime attributes are A and B.

Normal form: in B → E, B is part of the key and E is not prime: a partial dependency. The relation is in 1NF but not in 2NF.

Decomposition: B → E splits off R1(B, E), leaving R(A, B, C, D) (2NF). C → D is transitive (AB → C → D): R2(C, D) is split off, leaving R(A, B, C). All three relations are in BCNF: {B, E}, {C, D}, {A, B, C}. At each step the common attribute (B and C) determines the rest of one part, so the decomposition is lossless, and each of the three dependencies stays inside one part, so all are preserved.

Type this schema into the normalization tool to see the steps before and after.

Problem 4: file and index cost

r = 50,000 records, R = 200 bytes, B = 2048 bytes, unspanned placement. Key field V = 10 bytes, block pointer P = 6 bytes. (a) What are bfr and b? (b) If the file is sorted on the key, how many blocks does binary search read? (c) How many blocks does a search with a primary index read? (d) If the file is not sorted, how many blocks does a search with a dense secondary index and with its multilevel version read?

  1. bfr = ⌊2048 / 200⌋ = 10; b = ⌈50,000 / 10⌉ = 5000 blocks.
  2. ⌈log₂ 5000⌉ = 13 (2¹² = 4096 < 5000 ≤ 8192).
  3. An index entry is 16 bytes, fo = ⌊2048 / 16⌋ = 128. The 5000 entries of the primary index take ⌈5000 / 128⌉ = 40 blocks; a search reads ⌈log₂ 40⌉ + 1 = 6 + 1 = 7 blocks.
  4. The 50,000 entries of the dense secondary index take ⌈50,000 / 128⌉ = 391 blocks; a search reads ⌈log₂ 391⌉ + 1 = 9 + 1 = 10 blocks. In the multilevel version the levels are 391 → ⌈391/128⌉ = 4 → 1 blocks, so t = 3 and a search reads 4 blocks. Without an index, b/2 = 2500 blocks would be read on average.

You can check the same numbers in the cost calculator of Ch 17.

Problem 5: inserting into a B+-tree

Insert the values 20, 10, 30, 40, 50 in this order into an empty B+-tree with p = 3 and pleaf = 2. Explain every split and draw the final tree.

  • 20 and 10: a single leaf [10, 20].
  • 30: the leaf becomes [10, 20, 30] and overflows. The first ⌈3/2⌉ = 2 values stay left: [10, 20]; [30] moves to a new leaf; 20 is copied to a new root. Root [20].
  • 40: 40 > 20, so it goes to the right leaf: [30, 40].
  • 50: the right leaf becomes [30, 40, 50] and overflows: [30, 40] and [50]; 40 is copied to the root. The root can hold 2 values (p − 1 = 2), so it does not split: [20, 40].

Final tree: root [20, 40]; leaves [10, 20] → [30, 40] → [50]. In the B+-tree player, type "20 10 30 40 50" instead of "8 5 1 …" to see the tree before and after each insertion.

Problem 6: schedules

S: r1(X); r2(X); w1(Y); r3(Y); w2(Z); r3(Z); c1; c2; c3. (a) Is S conflict serializable? If so, give an equivalent serial order. (b) Is S recoverable, cascadeless, strict?

  1. There are only reads on X, so no conflict. Y: w1(Y) comes before r3(Y): T1 → T3. Z: w2(Z) comes before r3(Z): T2 → T3. The graph has no cycle: S is serializable; equivalent serial orders are T1 → T2 → T3 or T2 → T1 → T3.
  2. T3 reads Y from T1 and Z from T2, and commits after both have committed: recoverable. But T3 reads these values before T1 and T2 have committed: it is not cascadeless, and therefore not strict either.

Paste the schedule into the schedule analyzer to see the graph at every step.

The most common mistakes of the whole term

  • Solving an "every" question in SQL with a join. "Every" needs division or a double NOT EXISTS; the same rule holds in algebra.
  • Writing = NULL. A comparison with NULL gives UNKNOWN; IS NULL is used.
  • Confusing WHERE and HAVING. A condition with an aggregate is written after grouping, in HAVING.
  • Taking the primary key of a weak entity to be only its partial key. The owner's key together with the partial key is the primary key; this is asked both in ER and in mapping.
  • Putting the foreign key on the 1 side of 1:N, or mapping M:N with a single foreign key.
  • Deciding prime attributes without finding all candidate keys.
  • Rounding bfr up and the number of blocks down. It is the other way round.
  • Confusing serializable with serial; counting two reads as a conflict.

Mistakes specific to Ch 8–20

  • Using a join instead of division for an "all" question. A join means "at least one"; "all" needs division (or a double NOT EXISTS).
  • Putting the foreign key on the 1 side of a 1:N relationship. Many employee numbers do not fit in one department row; the foreign key always goes to the N side.
  • Mapping an M:N relationship with a foreign key. M:N always becomes a new table whose primary key combines the keys of both sides.
  • Keeping a multivalued attribute in a single column. It breaks 1NF; a separate table is needed whose primary key is the owner's key together with the value.
  • Confusing partial and transitive dependencies. Partial: the left side is part of a key. Transitive: the left side is part of no key and not a superkey either.
  • Deciding prime attributes from the primary key alone. An attribute is prime if it is part of any candidate key; the normal form cannot be told without finding all candidate keys.
  • Rounding bfr up. With unspanned placement bfr = ⌊B / R⌋; the number of blocks is rounded up: ⌈r / bfr⌉.
  • Taking the number of entries of a primary index to be the number of records. A primary index is sparse: its number of entries is the number of blocks of the data file.
  • Moving the value in a B+-tree leaf split. From a leaf it is copied to the parent; only from an internal node is it moved.
  • Confusing serializable with serial. A serializable schedule may be interleaved; what matters is that it is equivalent to a serial schedule.
  • Counting two reads as a conflict. A conflict needs at least one write.

Mixed practice set

The questions come from all chapters in mixed order, as in the final. Eight more questions specific to Ch 8–20 follow. For a set on Ch 1–7 see the midterm guide's practice set.

(Ch 2) When a new column is added to a table and the application programs that do not use it need no change, which independence is achieved?

  1. Physical data independence
  2. Logical data independence
  3. Program-operation independence
  4. View independence
A change in the conceptual schema not affecting the external schemas is logical data independence. Adding an index or reorganizing a file is an example of physical independence; this second kind also relates to the indexes of Ch 17.

(Ch 3 and 9) How does an attribute of an M:N relationship (for example Hours in WORKS_ON) end up in the tables?

  1. As a column of the EMPLOYEE table
  2. As a column of the PROJECT table
  3. In the new table created for the relationship
  4. In no table, because relationship attributes are not stored
An M:N relationship always becomes a new table and its attributes are added to that table. Ch 3 explains that such an attribute can be moved to an entity only for 1:1 and 1:N relationships; the mapping follows the same rule.

(Ch 5) A project is to be deleted from PROJECT, but WORKS_ON has rows referring to it. What happens if the foreign key is defined with ON DELETE CASCADE?

  1. The project and the WORKS_ON rows referring to it are deleted.
  2. The deletion is rejected.
  3. The Pno values in WORKS_ON are set to NULL.
  4. Only the project is deleted; WORKS_ON does not change.
ON DELETE CASCADE propagates the deletion to the referring rows. This is also why CASCADE is used on the foreign key of weak entities in Ch 9: when the owner is deleted, the weak entities become meaningless.

(Ch 7) What does SELECT COUNT(Super_ssn) FROM EMPLOYEE; return when COMPANY has 8 employees and one has a NULL Super_ssn?

  1. 8
  2. An error
  3. 1
  4. 7
Aggregate functions skip NULLs; only COUNT(*) counts all rows. The same rule holds for ℑ COUNT in relational algebra.

(Ch 8) What is the difference between σDno=5(EMPLOYEE) and πDno(EMPLOYEE)?

  1. σ selects columns, π rows.
  2. σ returns the rows with Dno 5 with all columns; π returns only the Dno column without duplicates.
  3. Both keep duplicates.
  4. Both give the same result.
σ is a horizontal partition (rows), π a vertical one (columns). In SQL σ corresponds to WHERE and π to SELECT DISTINCT.

(Ch 14) R(A, B, C) and F = {AB → C, C → A}. Which normal form is R in?

  1. 1NF
  2. Only 2NF
  3. 3NF but not BCNF
  4. BCNF
AB⁺ = {A, B, C} and BC⁺ = {B, C, A}: the candidate keys are AB and BC; every attribute is prime. The left side of C → A is not a superkey, but the right side is prime, so 3NF holds; BCNF does not. The book's TEACH relation has the same structure.

(Ch 16) For which search is a sorted file better than an unordered (heap) file?

  1. A range search on the ordering field
  2. An equality search on a field other than the ordering field
  3. Inserting a new record
  4. Reading all records in no particular order
A sorted file wins for searches on the ordering field; insertion and deletion are expensive because records must be shifted. Indexes (Ch 17) resolve this trade-off with an additional structure.

(Ch 17) Why does a search in a B+-tree always end in a leaf?

  1. Because the tree is balanced
  2. Because internal nodes hold no values
  3. Because the leaves are linked
  4. Because data pointers are only in the leaves
The internal nodes of a B+-tree only route; the pointer to the record is in the leaf. In a B-tree the search can stop at an internal node if the value is found there.

(Ch 20) The system crashed after a transaction committed. Which ACID property, and which mechanism, ensures its changes are not lost?

  1. Isolation; locks
  2. Durability; force-writing the log to disk before commit
  3. Atomicity; ROLLBACK
  4. Consistency; CHECK constraints
The log buffer is force-written to disk before the commit point. If the system crashes, the changes of transactions with a commit record are redone from the log; those without one are undone.

(Ch 11) A PHP program adds the last name typed by the user to SQL as "... WHERE Lname = '" . $_POST['ln'] . "'". What is the biggest problem?

  1. The period operator does not work in PHP.
  2. $_POST cannot be accessed from SQL.
  3. The user input can change the structure of the query (SQL injection).
  4. The result cannot be read with fetchRow.
In a query built by string concatenation, a quote mark typed by the user can close the value and add new conditions. With placeholders the value is used only as a value. You can compare the two cases in the placeholder lab of Ch 11.

(Ch 4 and 9) A specialization is total and disjoint, the subclasses have many specific attributes, and the superclass has no other relationship. Which mapping option produces no NULLs and lets all the information of an object be read from one table?

  1. 8A
  2. 8C
  3. 8D
  4. 8B
8B creates no table for the superclass. Being total ensures no object is lost, being disjoint that nothing repeats. If the superclass had relationships, 8B would not fit, because there would be no superclass table to connect them to.

(Ch 6 and 17) What do DBMSs usually do when a column is declared UNIQUE in CREATE TABLE?

  1. They automatically build an index on the column to check uniqueness.
  2. They physically sort the table on this column.
  3. They scan the whole table on every insertion.
  4. Nothing; UNIQUE is only a comment.
Enforcing a key constraint requires finding quickly whether the new value already exists; so indexes are built for primary key and UNIQUE columns. You can see these indexes of COMPANY in the SHOW INDEX box of Ch 17.

Additional Ch 8–20 questions

Which operation is needed in a relational algebra expression for "employees who do not work in the Research department"?

  1. Division (÷)
  2. Natural join (*)
  3. Difference (−)
  4. Union (∪)
"Not" questions are solved with difference: first all employees, then those satisfying the condition are found, and the second is removed from the first. Difference needs both sides to be union compatible, so only Ssn is kept on both.

A specialization is partial and overlapping. Which Step 8 option cannot be used?

  1. 8A
  2. 8B
  3. 8D
  4. None can be used
In 8B there is no table for the superclass, so an entity in no subclass is lost; that is why 8B is used only for total specializations. 8C cannot be used for this specialization either, since one type column is not enough for overlap; the right options are 8A and 8D.

R(A, B, C) and F = {A → B, B → C}. Which normal form is R in?

  1. 1NF
  2. BCNF
  3. 3NF
  4. 2NF
A is on no right side and A⁺ = {A, B, C}, so the key is A. With a single-attribute key there can be no partial dependency (2NF), but in B → C, B is not a superkey and C is not prime: a transitive dependency, a 3NF violation.

B = 1024 bytes, R = 300 bytes, r = 9000 records. How many blocks does the file take with unspanned placement?

  1. 3000
  2. 2637
  3. 2640
  4. 4500
bfr = ⌊1024 / 300⌋ = 3 (each block leaves 124 bytes free) and b = ⌈9000 / 3⌉ = 3000 blocks.

If a B-tree and a B+-tree hold the same values, which one has more search values in its internal nodes, and why?

  1. The B-tree, because all values are in internal nodes
  2. Both the same, because their orders are the same
  3. The B+-tree, because its internal nodes have no data pointers
  4. The internal nodes of a B+-tree hold no values at all
With the same block size, more values fit in an internal node of a B+-tree, because no data pointer is kept next to each value. In the book's example the internal node order of the B+-tree is 34; under the same conditions the order of a B-tree is 23.

Schedule: r1(X); w2(X); w1(X); c1; c2. Which edges are in the precedence graph?

  1. Only T1 → T2
  2. T1 → T2 and T2 → T1
  3. Only T2 → T1
  4. No edges
r1(X) and w2(X) are a read-write conflict (T1 first: T1 → T2); w2(X) and w1(X) are a write-write conflict (T2 first: T2 → T1). With both directions the graph has a cycle.

Which isolation level prevents dirty reads but allows nonrepeatable reads?

  1. READ UNCOMMITTED
  2. REPEATABLE READ
  3. SERIALIZABLE
  4. READ COMMITTED
By Table 20.1, READ COMMITTED prevents dirty reads; nonrepeatable reads and phantoms are still possible.

In PHP, while ($r = $q->fetchRow()) { print "$r[0] "; }: how many times does the loop body run when the query returns 3 rows?

  1. 3
  2. 4
  3. 1
  4. 0
fetchRow is called four times: the first three return a row each and the body runs; the fourth returns false and the while condition becomes false.
