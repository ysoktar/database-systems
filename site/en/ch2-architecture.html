Architecture and data models

At which levels of abstraction does a DBMS show data to users? Why are the schema and the data kept apart, and how does this separation protect programs from changes?

  • Tell the schema and the state (intension/extension) apart on an example.
  • Draw the three-schema architecture and explain its levels and mappings.
  • Say whether a change is an example of logical or of physical data independence.
  • Say which language (DDL, SDL, VDL, DML) a command belongs to, and the difference between 2-tier and 3-tier.

Data models

Data model: a collection of concepts used to describe the structure of a database: data types, relationships and constraints. Most models also include basic operations and user-defined operations (the dynamic aspect / behavior).

Schema, state, instance

  • Database schema: the description of the database. Specified during design and rarely changed. A drawing of the schema is a schema diagram, each object in it a schema construct.
  • Database state (snapshot, current set of occurrences/instances): the data at a particular moment. Changes with every update.
  • Empty state: the schema is defined but there is no data. Initial state: the first load. Valid state: a state that satisfies the structure and constraints of the schema.
  • Schema = intension, state = extension.
  • Schema evolution: changing the schema when requirements change (e.g. adding a column to EMPLOYEE). Most DBMSs support it: ALTER TABLE (Ch 7).

In COMPANY: the definition EMPLOYEE(Fname, …, Ssn, …, Dno) is the schema. Today there are 8 employees: that is a state. Adding a new employee (INSERT) changes the state, not the schema. Adding an Email column (ALTER TABLE) changes the schema.

The box below shows the difference on COMPANY (you will see the SQL commands in detail in Ch 6; here reading the comment lines is enough). It first counts the rows in EMPLOYEE (8), then adds an employee (INSERT) and counts again (9): the state changed. Then it reads EMPLOYEE's columns from the catalog: still the same ten columns, so the schema did not change. The last command deletes the added row, so COMPANY is back to its starting state and the box can be run again.

-- the current state: 8 employees
SELECT COUNT(*) AS employees FROM EMPLOYEE;
-- an update changes the state ...
INSERT INTO EMPLOYEE (Fname, Lname, Ssn, Dno) VALUES ('Ayşe', 'Yılmaz', '111222333', 5);
SELECT COUNT(*) AS employees FROM EMPLOYEE;
-- ... the schema (the columns, read from the catalog) is still the same
SELECT COLUMN_NAME FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'company' AND TABLE_NAME = 'EMPLOYEE' ORDER BY ORDINAL_POSITION;
-- undo the insert, so that the box can be run again
DELETE FROM EMPLOYEE WHERE Ssn = '111222333';

The three-schema architecture

The goal: to separate user applications from the physical database. The schema is defined at three levels:

  1. Internal level → the internal schema: the physical storage structure, in full detail with a physical data model: files, record formats, access paths.
  2. Conceptual level → the conceptual schema: the structure of the whole database for all users. Hides the physical details; describes entities, data types, relationships, operations and constraints. Usually implemented with a representational model (e.g. relational).
  3. External level (view level) → several external schemas (user views): each shows the part one user group is interested in and hides the rest.

The transformations of requests and results between levels are called mappings: the external/conceptual mapping and the conceptual/internal mapping. Mappings add overhead; that is why some DBMSs do not fully support the external level.

Data independence

Definition: the capacity to change the schema at one level without having to change the schema at the next higher level.

Logical data independence: changing the conceptual schema without changing the external schemas or application programs. E.g. adding a column to a table, removing a record type, adding a constraint; only the view definitions and mappings change. Harder to achieve, because programs depend on the logical structure.

Physical data independence: changing the internal schema without changing the conceptual schema. E.g. adding an index, reorganizing a file, moving to a different storage device. Queries give the same result (perhaps faster). Well supported in most DBMSs.

You can try both kinds of independence on COMPANY. In the first box EXPLAIN shows how the DBMS will run a query (the execution plan), not the result. Before the index is added the plan scans the whole table and filters the rows (Filter + Table). CREATE INDEX adds a new access path to the internal schema; the plan now uses the index (IndexedTableAccess). The query itself and its result are the same.

-- the query plan before: scan the whole table, keep the rows with Lname = 'Wong'
EXPLAIN FORMAT=TREE SELECT * FROM EMPLOYEE WHERE Lname = 'Wong';
-- a change to the internal schema (a new access path)
CREATE INDEX emp_lname_idx ON EMPLOYEE (Lname);
-- the query plan after: the new index is used
EXPLAIN FORMAT=TREE SELECT * FROM EMPLOYEE WHERE Lname = 'Wong';
-- the same query still gives the same answer
SELECT Fname, Lname FROM EMPLOYEE WHERE Lname = 'Wong';
-- undo, so that the box can be run again
DROP INDEX emp_lname_idx ON EMPLOYEE;

The plan text is produced by the engine on this site (go-mysql-server); real MySQL's EXPLAIN FORMAT=TREE output looks different but says the same thing: first a full scan, then access through the index.

In the second box an external schema, i.e. a view, is defined for a user group (in detail in Ch 7): this group sees only the employee's name and the department name. Then the conceptual schema changes: a column is added to EMPLOYEE (ALTER TABLE). The query that uses the view keeps giving the same result without any change.

-- an external schema for a user group: name and department name only
CREATE OR REPLACE VIEW EMP_DEPT AS
  SELECT E.Fname, E.Lname, D.Dname
  FROM   EMPLOYEE E JOIN DEPARTMENT D ON E.Dno = D.Dnumber;
SELECT * FROM EMP_DEPT WHERE Dname = 'Research';
-- the conceptual schema changes: a new column
ALTER TABLE EMPLOYEE ADD COLUMN Email VARCHAR(40);
-- programs that use the view do not notice
SELECT * FROM EMP_DEPT WHERE Dname = 'Research';
-- undo, so that the box can be run again
ALTER TABLE EMPLOYEE DROP COLUMN Email;
DROP VIEW EMP_DEPT;

DBMS languages

LanguageWhat does it define?
DDL (data definition language)The conceptual schema (and, in systems without a clear internal/external separation, all of them). In SQL: CREATE, ALTER, DROP.
SDL (storage definition language)The internal schema. Today's relational DBMSs have no separate language; it is done with parameters and commands (e.g. CREATE INDEX).
VDL (view definition language)The external schemas. In SQL: CREATE VIEW.
DML (data manipulation language)Access and updates: retrieval, insertion, deletion, modification. In SQL: SELECT, INSERT, UPDATE, DELETE.
  • High-level / nonprocedural DML (set-at-a-time, declarative): says what is wanted, not how to find it. One command returns many records. E.g. SQL. Can be used interactively on its own or embedded in a program (embedded; then the programming language is the host language and the DML a data sublanguage).
  • Low-level / procedural DML (record-at-a-time): retrieves records one by one; must be used together with programming constructs such as loops. E.g. the old network-model DML (DL/1).
  • Query language: a high-level DML used interactively.
  • SQL combines DDL + VDL + DML (and constraint and privilege definitions) in one language.

DBMS interfaces

Menu-based (web) interfaces, apps for mobile devices, forms, graphical user interfaces (GUI), natural-language interfaces, keyword-based search, speech input and output, interfaces for parametric users (ready-made operations with few keystrokes) and interfaces for the DBA (privileged commands such as creating accounts, granting privileges, changing the schema).

The DBMS environment and its components

A summary of Figure 2.3 in the book: users at the top (DBA, casual, programmer, parametric), compilers and processors in the middle, storage at the bottom:

  • DDL compiler: processes schema definitions and writes the meta-data to the system catalog.
  • Interactive query interface → query compiler → query optimizer: parses and validates a query and turns it into an efficient execution plan.
  • Precompiler: extracts the DML commands embedded in an application program; the DML compiler compiles them; the rest of the code goes to the host-language compiler. All of it is linked into canned transactions.
  • Runtime database processor: runs the plans and canned transactions; accesses the disk through the stored data manager and buffer management.
  • Concurrency control / backup / recovery subsystems work together with the runtime processor.
  • Database system utilities: loading (files into the database), backup, database storage reorganization, performance monitoring; also sorting, data compression, user monitoring.
  • Other tools: CASE tools, data dictionary / repository systems (which also store design decisions and usage standards), application development environments, communications software.

Centralized and client/server architectures

  • Centralized: all DBMS functionality, the applications and the interface on one system (formerly a mainframe; terminals were only displays).
  • Basic client/server: specialized servers (file server, printer server, web server, DBMS server …) and the clients that connect to them.
  • Two-tier client/server: the user interface and application programs on the client; query and transaction functionality on the server (query server / transaction server; in a relational DBMS an SQL server). The connection is through an API such as ODBC or JDBC.
  • Three-tier / n-tier (web applications): client (GUI, web browser) ↔ application server / web server (business rules, the middle tier) ↔ database server. The middle tier improves security (the client does not access the database directly). In n-tier the business logic is split into more layers.

Classification of DBMSs

  • By data model: relational (the most common), object, object-relational, NoSQL (key-value, document, column-based, graph), hierarchical and network (legacy), XML.
  • By number of users: single-user and multiuser.
  • By distribution: centralized (data in one place) and distributed (a DDBMS; data at many sites of a network). Homogeneous (the same DBMS everywhere) or heterogeneous; federated (multidatabase) systems loosely combine independent DBMSs.
  • By cost: open source (MySQL, PostgreSQL), commercial (Oracle, SQL Server, DB2), different kinds of licences.
  • By types of access paths and purpose: general-purpose and special-purpose (e.g. the old airline reservation systems: OLTP, online transaction processing).

Test yourself

A company split the EMPLOYEE table in two: the personal information moved to EMP_PERSONAL, the salary information to EMP_PAY. The old programs keep working unchanged through a view named EMPLOYEE. What is this an example of?

  1. Physical data independence
  2. Logical data independence
  3. Program-operation independence
  4. None; this is just a data update
Splitting tables changes the conceptual schema. Because the programs depend on the external schema (the view), only the external/conceptual mapping (the view definition) is updated: logical data independence. The EMP_DEPT box above shows the same idea.

A new index was added to the EMPLOYEE table; all applications keep giving the same results without any change. What is this an example of?

  1. Logical data independence
  2. Physical data independence
  3. Self-describing nature
  4. Program-operation independence
An index is an access path, i.e. part of the internal schema. The internal schema changed, the conceptual schema stayed the same: this is physical data independence.

Which pairs intension and extension correctly?

  1. Intension = the database state; extension = the schema
  2. Intension = the internal schema; extension = the external schema
  3. Intension = the schema; extension = the database state
  4. Intension = DDL; extension = DML
The schema is the description of the database (intension) and rarely changes. The state is the data at a particular moment (extension) and changes with every update.

Which language category and which schema level does CREATE VIEW correspond to?

  1. VDL, external schema
  2. DDL, internal schema
  3. SDL, conceptual schema
  4. DML, external schema
A view is a view specific to a user group: the external level. The language that defines it is VDL. In SQL VDL looks like part of DDL, but conceptually it is separate.

In a web application, which architecture is the arrangement browser → application server → database server?

  1. Centralized
  2. Two-tier client/server
  3. Distributed (DDBMS)
  4. Three-tier client/server
The middle tier (application/web server) runs the business rules and accesses the database on behalf of the client. In two-tier the client connects directly to the database server with ODBC/JDBC.
