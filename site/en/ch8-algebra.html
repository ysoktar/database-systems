Relational algebra

Relational algebra is the basic set of operations of the relational model: each operation takes one or two relations and produces a new relation as its result. It is the formal language behind SQL. On this page you can see the input and the result of every operation side by side on the COMPANY data, and run the SQL equivalent of the same query.

  • Write a query with σ, π, ρ, set operations, ⋈ and ÷, both as a single expression and as a sequence of operations that names its intermediate results.
  • Predict how many rows and which columns the result of each operation will have; for example, know that π removes duplicates and that σ never increases the number of rows.
  • Explain the difference between theta join, equijoin and natural join; answer "for every …" questions with the division operation.
  • Draw a query tree for a query; recognize the aggregate, outer join and outer union operations.

Overview

The result of every operation of relational algebra is again a relation. This property is called closure, and it lets us nest operations: the result of one operation becomes the input of the next. A sequence of operations forms a relational algebra expression, and its result is also a relation, the answer to a query.

The algebra is procedural: it says step by step how the result is obtained. SQL is declarative: it says what is wanted and leaves how to find it to the DBMS. Before running an SQL query, the DBMS internally translates it into an algebra expression (a query tree). The algebra treats relations as sets, so the same row never appears twice in a result; SQL removes duplicates only when DISTINCT is written.

SELECT and PROJECT

SELECT (σ): filtering rows

σ<condition>(R) selects the rows of R that satisfy the condition and discards the others. The condition is a Boolean expression on the attributes of R; for example σDno=4(EMPLOYEE) gives the employees of department 4, and σSalary>30000(EMPLOYEE) those who earn more than 30000. In SQL this is the job of WHERE.

  • The schema of the result is the same as that of R: the columns do not change, only the rows decrease. The number of rows in the result cannot exceed the number of rows in R.
  • σ is commutative: σc1(σc2(R)) = σc2(σc1(R)). So successive selections can be applied in any order, and they can all be combined into one selection: σc1(σc2(σc3(R))) = σc1 AND c2 AND c3(R).

PROJECT (π): choosing columns

π<attribute list>(R) keeps only the columns of R that are in the list and discards the others. For example πLname, Fname, Salary(EMPLOYEE) gives the name and salary of every employee. In SQL this is the job of the SELECT list.

  • Since the result must be a set, π removes duplicate rows. This corresponds to writing SELECT DISTINCT in SQL.
  • The number of rows in the result cannot exceed that of R. If the list contains a key of R, no row repeats and the number of rows stays the same.
  • π is not commutative. The expression πlist1(πlist2(R)) is valid only if list2 contains all the attributes of list1, and then it equals πlist1(R).

Expressions and RENAME

There are two ways to apply several operations one after the other. The first is to build a single expression by nesting the operations. The second is to apply the operations one at a time and give each intermediate result a name; the ← sign is an assignment here. For example, the question "the first name, last name and salary of the employees in department 5" can be written either way:

πFname, Lname, Salary(σDno=5(EMPLOYEE))

DEP5_EMPS ← σDno=5(EMPLOYEE)
RESULT    ← πFname, Lname, Salary(DEP5_EMPS)

RENAME (ρ) changes the name of a relation, the names of its columns, or both. It is needed in queries that use two copies of the same relation and in joins where column names must match. It has three forms:

  • ρS(B1, …, Bn)(R) renames the relation to S and its columns to B1, …, Bn.
  • ρS(R) renames only the relation.
  • ρ(B1, …, Bn)(R) renames only the columns.

Renaming can also happen during an assignment: writing RESULT(F, M, L, S, B, A, SX, SAL, SU, DNO) ← ρ…(DEP5_EMPS) gives the ten columns of DEP5_EMPS these names, in order. In SQL renaming is done with AS.

Set operations

UNION (R ∪ S) contains all the rows that are in R, in S or in both, and removes duplicates. INTERSECTION (R ∩ S) contains only the rows that are in both relations, and DIFFERENCE (R − S, also called MINUS or EXCEPT) the rows that are in R but not in S.

The two inputs of these three operations must be type compatible (union compatible): the two relations must have the same number of columns, and corresponding columns must have compatible domains. By convention the columns of the result carry the column names of the first input.

  • ∪ and ∩ are commutative (R ∪ S = S ∪ R) and associative (R ∪ (S ∪ T) = (R ∪ S) ∪ T); so they can be applied to more than two relations.
  • Difference is not commutative: in general R − S ≠ S − R.

The book's example: the Ssns of the employees who work in department 5 or who directly supervise an employee who works in department 5. RESULT1 holds the Ssns of the department's employees; RESULT2 the Ssns of their supervisors. RESULT2's column is renamed from Super_ssn to Ssn so that the two relations are type compatible.

DEP5_EMPS   ← σDno=5(EMPLOYEE)
RESULT1     ← πSsn(DEP5_EMPS)
RESULT2(Ssn) ← πSuper_ssn(DEP5_EMPS)
RESULT      ← RESULT1 ∪ RESULT2

Cartesian product and JOIN

Cartesian product (×)

R × S combines every row of R with every row of S. If R has n columns and S has m, the result has n + m columns; if R has nR rows and S has nS, the result has nR · nS rows. The two inputs do not have to be type compatible. On its own the product is usually meaningless, because it also pairs rows that have nothing to do with each other; it becomes meaningful when a selection follows it. The book's example finds the names of the female employees and of their dependents:

FEMALE_EMPS    ← σSex='F'(EMPLOYEE)
EMPNAMES       ← πFname, Lname, Ssn(FEMALE_EMPS)
EMP_DEPENDENTS ← EMPNAMES × DEPENDENT
ACTUAL_DEPS    ← σSsn=Essn(EMP_DEPENDENTS)
RESULT         ← πFname, Lname, Dependent_name(ACTUAL_DEPS)

JOIN (⋈)

A selection after a product is needed so often that the two are combined into one operation: R ⋈<join condition> S = σ<join condition>(R × S). The columns of the result are again the columns of R and of S, but only the pairs of rows that satisfy the join condition reach the result. So the result usually has far fewer than nR · nS rows. For example, to find the manager of each department, every DEPARTMENT row is combined with the EMPLOYEE row whose Ssn equals its Mgr_ssn:

DEPT_MGR ← DEPARTMENT ⋈Mgr_ssn=Ssn EMPLOYEE
  • Theta join is the general form of join: the condition (θ) can be any Boolean expression on the attributes of the two relations, for example R.A < S.B AND (R.C = S.D OR R.E < S.F).
  • Equijoin uses only equality comparisons in its condition. Its result always has one or more pairs of columns whose values are the same in every row (like Mgr_ssn and Ssn in DEPT_MGR). Most joins are equijoins.
  • Natural join (R * S) was defined to drop this superfluous second column of an equijoin. No condition is written: an equality condition is added automatically for each pair of columns that have the same name in the two relations, and only one column of each pair remains in the result. If the column names differ, ρ is applied first. For example DEPARTMENT * DEPT_LOCATIONS joins on Dnumber, the common column of the two relations.

A complete set of operations. The set {σ, π, ∪, −, ρ, ×} is complete: every other algebra operation can be expressed with these six. For example R ∩ S = (R ∪ S) − ((R − S) ∪ (S − R)) and R ⋈condition S = σcondition(R × S). The other operations exist only to make writing easier.

DIVISION

In R(Z) ÷ S(X), X is a subset of Z; Y = Z − X are the columns of R that are not in S. The result is a relation T(Y), and a value t reaches the result only if it occurs in R together with every row of S. That is why division is the algebra's counterpart of questions with "for every …" (∀).

The book's example: "the Ssns of the employees who work on all the projects that John Smith works on." First Smith's projects are found (SMITH_PNOS), then each employee's projects (SSN_PNOS) are divided by them:

SMITH        ← σFname='John' AND Lname='Smith'(EMPLOYEE)
SMITH_PNOS   ← πPno(WORKS_ON ⋈Essn=Ssn SMITH)
SSN_PNOS     ← πEssn, Pno(WORKS_ON)
SSNS(Ssn)    ← SSN_PNOS ÷ SMITH_PNOS

In the walkthrough below, the rows of each employee in SSN_PNOS on the left share a colour. Smith works on projects 1 and 2; the rows of employees who do not work on both of these projects are red. Only the Ssns that occur with both projects remain in the result.

SQL has no division operation. The same question is written with the double negation we saw in Ch 7: "there is no project that Smith works on and this employee does not."

SELECT DISTINCT W.Essn
FROM   WORKS_ON W
WHERE  NOT EXISTS (SELECT S.Pno FROM WORKS_ON S WHERE S.Essn = '123456789'
                   EXCEPT
                   SELECT X.Pno FROM WORKS_ON X WHERE X.Essn = W.Essn);

Query trees

A query tree shows an algebra expression as a tree. The leaves are base relations (such as EMPLOYEE and PROJECT), and the inner nodes are operations (such as σ, π and ⋈). A node is executed once the results of its children are ready, and the result of the operation at the root is the answer to the query. DBMSs keep queries internally as such a tree; it makes it easy to see how much work a query needs and which intermediate results are produced. Algebraic query optimization (Ch 15) turns the tree into an equivalent but cheaper tree.

Additional operations

Aggregate functions and grouping (ℑ)

One kind of request that cannot be expressed in the basic algebra is a mathematical summary over a collection of values: the average or total salary of all employees, the number of employees, and so on. The ℑ (or ℱ) operation is used for this. For example ℑMAX Salary(EMPLOYEE) gives the highest salary, and ℑCOUNT Ssn, AVERAGE Salary(EMPLOYEE) the number of employees and the average salary. COUNT counts rows and does not remove duplicates.

The grouping attribute is written to the left of the ℑ symbol, the aggregate functions to its right. DnoℑCOUNT Ssn, AVERAGE Salary(EMPLOYEE) groups the employees by department number and computes the number of employees and the average salary for each department. This is the counterpart of GROUP BY in SQL. Forms of the book's Figure 8.10 are below.

Recursive closure

Another operation that in general cannot be written in the basic algebra is recursive closure on a recursive relationship. For example, the question "the supervisees of James Borg at all levels" needs Borg's direct supervisees, their direct supervisees, and so on along the whole chain. It is possible to find each level separately and take their union, but if the number of levels is unknown, this query cannot be written without a loop. The SQL3 standard added recursive queries for this (WITH RECURSIVE in Ch 7). The book's Figure 8.11 finds two levels like this:

BORG_SSN            ← πSsn(σFname='James' AND Lname='Borg'(EMPLOYEE))
SUPERVISION(Ssn1, Ssn2) ← πSsn, Super_ssn(EMPLOYEE)
RESULT1(Ssn)        ← πSsn1(SUPERVISION ⋈Ssn2=Ssn BORG_SSN)
RESULT2(Ssn)        ← πSsn1(SUPERVISION ⋈Ssn2=Ssn RESULT1)
RESULT              ← RESULT2 ∪ RESULT1

Outer join

In natural join and equijoin, rows without a matching partner are dropped from the result; rows whose join column is NULL are dropped too. This is a loss of information. The outer join operations are used when we want to keep all the rows of a relation in the result, whether or not they have a partner.

  • Left outer join (R ⟕ S) keeps every row of the left relation R; for rows with no partner in S, the columns of S are filled with NULL.
  • Right outer join (R ⟖ S) keeps every row of the right relation S in the same way.
  • Full outer join (R ⟗ S) keeps the unmatched rows of both sides, filling with NULL where needed.

The book's Figure 8.12 lists every employee with the name of the department they manage; employees who manage no department are in the result too, with NULL as the department name:

TEMP   ← (EMPLOYEE ⟕Ssn=Mgr_ssn DEPARTMENT)
RESULT ← πFname, Minit, Lname, Dname(TEMP)

Outer union

Outer union was defined to take the union of two relations that are not type compatible. The relations R(X, Y) and S(X, Z) are only partially compatible: the X columns are shared, Y and Z are not. The result is a relation T(X, Y, Z); the shared columns appear once, and both sets of incompatible columns are kept. Rows are merged when the values of their shared columns are the same.

In the book's example STUDENT(Name, Ssn, Department, Advisor) and INSTRUCTOR(Name, Ssn, Department, Rank) are combined, and the result is STUDENT_OR_INSTRUCTOR(Name, Ssn, Department, Advisor, Rank). For someone who is both a student and an instructor both Advisor and Rank have values; for the others one of these two columns is NULL. SQL has no outer union; the box below produces the same result with the union of two outer joins.

DROP TABLE IF EXISTS demo.STUDENT, demo.INSTRUCTOR;   -- so that the box can be run again
CREATE TABLE demo.STUDENT    (Name VARCHAR(20), Ssn CHAR(9), Department VARCHAR(15), Advisor VARCHAR(20));
CREATE TABLE demo.INSTRUCTOR (Name VARCHAR(20), Ssn CHAR(9), Department VARCHAR(15), `Rank` VARCHAR(15));
INSERT INTO demo.STUDENT    VALUES ('Ali', '111', 'CS', 'Kaya'), ('Ece', '222', 'EE', 'Demir');
INSERT INTO demo.INSTRUCTOR VALUES ('Kaya', '333', 'CS', 'Professor'), ('Ece', '222', 'EE', 'Assistant');
-- STUDENT_OR_INSTRUCTOR(Name, Ssn, Department, Advisor, Rank): Ece is both, so her row has both values
SELECT S.Name, S.Ssn, S.Department, S.Advisor, I.`Rank`
FROM   demo.STUDENT S LEFT JOIN demo.INSTRUCTOR I ON S.Name = I.Name AND S.Ssn = I.Ssn AND S.Department = I.Department
UNION
SELECT I.Name, I.Ssn, I.Department, S.Advisor, I.`Rank`
FROM   demo.INSTRUCTOR I LEFT JOIN demo.STUDENT S ON S.Name = I.Name AND S.Ssn = I.Ssn AND S.Department = I.Department;

Q6: the names of the employees who have no dependents

This query uses the difference operation: the Ssns of employees with dependents are removed from the Ssns of all employees, and the remaining Ssns are joined with EMPLOYEE to get the names.

ALL_EMPS          ← πSsn(EMPLOYEE)
EMPS_WITH_DEPS(Ssn) ← πEssn(DEPENDENT)
EMPS_WITHOUT_DEPS ← (ALL_EMPS − EMPS_WITH_DEPS)
RESULT            ← πLname, Fname(EMPS_WITHOUT_DEPS * EMPLOYEE)

As a single expression:
πLname, Fname((πSsn(EMPLOYEE) − ρSsn(πEssn(DEPENDENT))) * EMPLOYEE)

Test yourself

EMPLOYEE has 8 rows. How many rows does πSex, Salary(EMPLOYEE) return? (The women's salaries are 25000, 43000, 25000; the men's are 30000, 40000, 38000, 55000, 25000.)

  1. 8
  2. 7
  3. 6
  4. 2
Since the result of π is a set, the same (Sex, Salary) pair appears once. Among the women (F, 25000) appears twice and one is removed: 8 − 1 = 7. Jabbar, a man who earns 25000, has the row (M, 25000), which differs from the women's (F, 25000).
SELECT DISTINCT Sex, Salary FROM EMPLOYEE;

R has 4 rows and S has 3. At most how many rows can R × S and R ⋈condition S have?

  1. R × S: 7; R ⋈ S: 7
  2. R × S: 12; R ⋈ S: 24
  3. R × S: exactly 12; R ⋈ S: at most 12
  4. R × S: 12; R ⋈ S: at most 3
In a Cartesian product every row is paired with every row, so the result always has nR · nS = 12 rows. A join is σcondition(R × S), so it is a subset of these 12 rows: 12 if every pair satisfies the condition, 0 if none does.

Which statement is not true of natural join?

  1. No join condition is written; it is formed automatically from the pairs of columns with the same name.
  2. Only one column of each pair of same-named columns remains in the result.
  3. If the column names differ, RENAME must be applied first.
  4. The join condition can contain any comparison (<, >, …).
A join that can contain any comparison is a theta join. A natural join is an equijoin made of equalities between same-named columns, and it drops one column of each equal pair.

Which operation is most suitable for "the Ssns of the employees who work on all the projects"?

  1. DIVISION: πEssn, Pno(WORKS_ON) ÷ ρ(Pno)(πPnumber(PROJECT))
  2. JOIN: πEssn(WORKS_ON ⋈Pno=Pnumber PROJECT)
  3. PROJECT: πEssn(WORKS_ON)
  4. DIFFERENCE: πSsn(EMPLOYEE) − πEssn(WORKS_ON)
"With all …" (∀) questions are the typical use of division: R(Essn, Pno) ÷ S(Pno) gives the Essns that occur with every Pno in S. Joins and projections answer only "at least one" (∃) questions.

Which of the following is true?

  1. R − S = S − R
  2. πA(πB(R)) = πB(πA(R)) always holds.
  3. σc1(σc2(R)) = σc1 AND c2(R)
  4. The two inputs of a Cartesian product must be type compatible.
σ is commutative; successive selections can be applied in any order and combined into one selection with the AND of the conditions. Difference and projection are not commutative; type compatibility is needed only for ∪, ∩ and −.

How many rows does EMPLOYEE ⟕Ssn=Mgr_ssn DEPARTMENT return? (EMPLOYEE has 8 employees; each of the 3 departments is managed by a different employee.)

  1. 3
  2. 8
  3. 11
  4. 24
A left outer join keeps every row of the left relation. The 3 employees who manage a department are matched with it; the 5 who do not are in the result too, with NULL in DEPARTMENT's columns. Since each employee manages at most one department, the result has 8 rows.
SELECT E.Fname, E.Minit, E.Lname, D.Dname
FROM   EMPLOYEE E LEFT OUTER JOIN DEPARTMENT D ON E.Ssn = D.Mgr_ssn;
