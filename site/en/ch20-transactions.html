Transaction processing

In a banking application a money transfer is two updates: subtracting from one account and adding to another. What happens if the system crashes between the two, or another user changes the same account at the same time? This page explains how the database deals with these situations: the transaction concept, the problems of concurrent execution, the ACID properties, and which schedules count as correct.

Introduction to transaction processing

A transaction is an executing program that forms a logical unit of database processing. Transaction processing systems are systems with large databases and hundreds of concurrent users that require high availability and fast response, such as airline reservations, banking and stock markets. A single-user DBMS is used by at most one user at a time (for example a home computer); a multiuser DBMS is accessed by many users concurrently.

Multiprogramming means the operating system executes several processes concurrently: it runs commands of one process, suspends it, and runs commands of another. On a single CPU this means interleaved processing; with several CPUs processes can run truly in parallel (the book's Figure 20.1). The theory on this page assumes interleaved execution.

The boundaries of a transaction are given by begin transaction and end transaction statements. A transaction that does not change the database is read-only, one that does is read-write. The database is seen as a collection of named data items. A data item can be a record, a disk block or a single attribute value of a record; the size of an item is its granularity. The concepts here do not depend on granularity.

A transaction accesses the database with two basic operations:

  • read_item(X): reads the data item named X into a program variable named X. The address of the disk block containing X is found, the block is copied into a buffer (if it is not there yet), and X is copied from the buffer into the variable.
  • write_item(X): writes the value of the program variable X into the data item X. The block is found and copied into a buffer, the variable X is written into the right place in the buffer, and the updated block is written back to disk (immediately or later).

All items a transaction reads form its read set, all items it writes its write set. The two transactions of the book's Figure 20.2 are used below: T1 transfers N seats from flight X to flight Y (read_item(X); X := X − N; write_item(X); read_item(Y); Y := Y + N; write_item(Y)); T2 reserves M seats on flight X (read_item(X); X := X + M; write_item(X)). The DBMS keeps several buffers in the database cache; when they are full, a buffer replacement policy such as LRU decides which one is replaced.

Why concurrency control is needed

Transactions of different users may run at the same time and access the same items. If their operations interleave without control, the result can be wrong even though each transaction is correct on its own. The book gives four problems:

  • Lost update: two transactions read the same item and both write it; the second write overwrites the first one's update.
  • Temporary update (dirty read): a transaction updates an item and then fails; meanwhile another transaction has read the updated value, which never became valid.
  • Incorrect summary: while one transaction computes a summary such as a sum, another updates some items; the summary uses old values for some items and new values for others.
  • Unrepeatable read: a transaction reads the same item twice, but another transaction changes it in between, so the two reads give different values.

Why recovery is needed

A transaction either completes all its operations successfully and its effect is recorded permanently in the database (commit), or it has no effect on the database at all (abort). Some operations of a transaction may not be applied while others are not. Transactions can fail for these reasons: a computer failure (system crash); a transaction or system error (for example division by zero or a wrong parameter); local errors or exceptions detected by the transaction itself (for example insufficient balance); concurrency control aborting the transaction (for example to resolve a deadlock); disk failure; physical problems and catastrophes (fire, power failure, accidental overwriting). The system must keep enough information to recover quickly after a failure; recovering from disk failures and catastrophes takes long.

Transaction and system concepts

The system keeps track of when each transaction starts, terminates, commits or aborts. The operations used for this are: BEGIN_TRANSACTION, READ or WRITE, END_TRANSACTION (reads and writes are done; now it is checked whether the changes can be made permanent), COMMIT_TRANSACTION (successful end; the changes are permanent) and ROLLBACK or ABORT (unsuccessful end; the changes are undone).

The system log is a sequential, append-only file that records every operation of transactions that affects database items. It is not affected by any failure except disk or catastrophic failure. Log records are first collected in a log buffer in main memory; when it is full it is appended to the end of the log file on disk. The log file is backed up periodically. Using the log, a transaction's operations can be undone (undo) or redone (redo).

A transaction reaches its commit point when all its operations that access the database have completed successfully and their effect has been recorded in the log. The transaction writes a commit record into the log. If the system crashes, the log is searched for transactions that have a start_transaction record but no commit record; their effect is undone. So the log buffer is force-written to disk before the transaction reaches its commit point.

There are also DBMS-specific buffer replacement policies. In the domain separation method each domain handles one type of disk pages (index pages, data file pages, log pages), and the number of buffers for each domain is predetermined. The hot set method helps queries that scan a set of pages repeatedly: the set is not replaced in the buffers until processing is done. The DBMIN method predetermines the page reference pattern for the algorithm of a particular type of database operation and calculates the locality set with the query locality set model (QLSM).

Desirable properties of transactions: ACID

  • Atomicity: a transaction is performed in its entirety or not at all. The recovery subsystem ensures this.
  • Consistency preservation: a transaction, run alone and to completion, takes the database from one consistent state to another. This is the responsibility of the programmer and of the DBMS modules that enforce constraints.
  • Isolation: a transaction should appear as if it were not interfered with by other transactions, even when running concurrently with them. Concurrency control ensures this.
  • Durability: the changes of a committed transaction must not be lost in any later failure. The recovery subsystem ensures this too.

Isolation has levels. Level 0 isolation does not overwrite the dirty reads of higher-level transactions; level 1 has no lost updates; level 2 has no lost updates and no dirty reads; level 3 (true isolation) adds repeatable reads. There is also snapshot isolation, explained in the SQL section below.

The boxes below show atomicity on a small table outside COMPANY. In the first box the transfer is cancelled halfway with ROLLBACK and the table returns to its state before the transfer; in the second the two updates become permanent together with COMMIT.

DROP TABLE IF EXISTS demo.ACCOUNT;
CREATE TABLE demo.ACCOUNT (Acc CHAR(1) PRIMARY KEY, Balance INT);
INSERT INTO demo.ACCOUNT VALUES ('X', 80), ('Y', 100);
START TRANSACTION;
UPDATE demo.ACCOUNT SET Balance = Balance - 5 WHERE Acc = 'X';
SELECT * FROM demo.ACCOUNT;
ROLLBACK;
SELECT * FROM demo.ACCOUNT;

DROP TABLE IF EXISTS demo.ACCOUNT;
CREATE TABLE demo.ACCOUNT (Acc CHAR(1) PRIMARY KEY, Balance INT);
INSERT INTO demo.ACCOUNT VALUES ('X', 80), ('Y', 100);
START TRANSACTION;
UPDATE demo.ACCOUNT SET Balance = Balance - 5 WHERE Acc = 'X';
UPDATE demo.ACCOUNT SET Balance = Balance + 5 WHERE Acc = 'Y';
COMMIT;
SELECT * FROM demo.ACCOUNT;

Characterizing schedules by recoverability

A schedule (history) is the order in which the operations of several transactions execute; operations of different transactions may interleave, but each transaction's own operations appear in its own order. The shorthand is: ri(X) = read_item(X) of Ti, wi(X) = write_item(X), ci = commit, ai = abort. For example the lost update schedule Sa is written r1(X); r2(X); w1(X); r1(Y); w2(X); w1(Y). The operations in a schedule are totally ordered: of any two operations, one comes before the other.

Two operations conflict if they satisfy all three conditions: they belong to different transactions, they access the same item X, and at least one of them is a write_item(X). In other words, operations conflict if changing their order can change the outcome. r1(X) and w2(X) are a read-write conflict, w1(X) and w2(X) a write-write conflict; two reads do not conflict.

There are three classes by recoverability; each contains the next:

  • Recoverable: no committed transaction ever needs to be rolled back. The condition: if T read an item written by T′, T does not commit before T′ commits. The DBMS should not permit nonrecoverable schedules. Even a recoverable schedule can have cascading rollback: uncommitted transactions that read from an aborted transaction must be rolled back too.
  • Cascadeless: every transaction reads only items written by committed transactions; so there is no cascading rollback.
  • Strict: no transaction can read or write an item X until the last transaction that wrote X has committed or aborted. Recovery becomes very simple: to undo the writes of an aborted transaction, the before image of the items is restored.

In the book's examples Sc: r1(X); w1(X); r2(X); r1(Y); w2(X); c2; a1 is not recoverable, because T2 reads the X written by T1 and commits before T1; when T1 aborts, the value T2 read becomes invalid but T2 can no longer be undone. Sd, with the commits swapped, is recoverable; but it is not cascadeless. The schedule analyzer states these classes with the reason for every schedule.

Characterizing schedules by serializability

If the operations of transactions do not interleave in a schedule, that is, each transaction runs from start to end one after another, the schedule is serial. Serial schedules are always considered correct, because each transaction is correct on its own. But serial schedules prohibit concurrency: the CPU sits idle while a transaction waits for I/O. That is unacceptable in practice. The solution is to allow schedules that are equivalent to a serial schedule. A schedule of n transactions is serializable if it is equivalent to some serial schedule of the same n transactions.

There are three ways to define equivalence:

  • Result equivalence: the two schedules produce the same final database state. This may be accidental; in the book's Figure 20.6 two schedules give the same result only for the initial value X = 100. So it cannot be used alone.
  • Conflict equivalence: the relative order of every pair of conflicting operations is the same in both schedules. A schedule S is conflict serializable if it is conflict equivalent to some serial schedule S′.
  • View equivalence: each read operation reads the result of the same write operation in both schedules, and the final writes are the same; the reads see the same "view" in both schedules. A schedule view equivalent to a serial schedule is view serializable. Without blind writes (each write comes after reading the item's old value; the constrained write assumption) conflict and view serializability coincide. If a written value may be independent of the old value (the unconstrained write assumption), view serializability is broader. For some applications, such as debit-credit transactions on bank accounts, even less stringent conditions are enough.

Conflict serializability is tested with a precedence graph (the book's Algorithm 20.1). Each transaction is a node. An edge Ti → Tj is added if Tj later reads an item Ti wrote, later writes an item Ti read, or later writes an item Ti wrote. If the graph has no cycle, the schedule is conflict serializable and a topological sort of the graph gives an equivalent serial order; if it has a cycle, it is not serializable.

In the analyzer below choose one of the book's schedules or type your own. As you step through, the conflicting pairs of operations are found one by one and each adds an edge to the graph; the graph before and after is shown side by side. The last step shows the cycle (if any) in red and gives the equivalent serial order and the recoverability classes.

Being serializable is different from being serial: a serializable schedule gives the benefit of concurrent execution without giving up any correctness. But in practice testing a schedule in advance is hard; the order of operations depends on system load, the time transactions are submitted and process priorities, and cannot be known beforehand. So DBMSs enforce protocols (sets of rules) that guarantee serializability; locking protocols are the topic of the next chapter (Ch 21).

Transaction support in SQL

SQL has no explicit Begin_Transaction statement; a transaction starts implicitly with the first SQL statement (in MySQL it can also be started explicitly with START TRANSACTION). But every transaction must have an explicit end statement: COMMIT or ROLLBACK. The SET TRANSACTION statement sets three characteristics: the access mode (READ ONLY or READ WRITE), the diagnostic area size (the number of conditions that can be held in the diagnostic area at the same time) and the isolation level.

The lower the isolation level, the more of these violations become possible: dirty read (reading an uncommitted value), nonrepeatable read (reading the same row twice and seeing different values) and phantoms (reading twice with the same condition and seeing a different set of rows, because another transaction inserted new rows in between). The book's Table 20.1:

READ UNCOMMITTEDYesYesYes
READ COMMITTEDNoYesYes

SERIALIZABLENoNoNo

Snapshot isolation is used in some commercial DBMSs: a transaction sees the items it reads as the committed values in the database snapshot taken when the transaction started. It ensures the phantom problem does not occur.

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT @@transaction_isolation;
