Approach to question types

Most midterm questions fit one of four patterns. For each there is a method worked out on the site; follow the same order in the exam.

Short-answer concept questions

"Define / compare" questions that come up often in exams. Answer in your own words, then open the answer.

  1. Define logical and physical data independence; which one is harder to achieve, and why?

    Logical: being able to change the conceptual schema without changing the external schemas/programs (e.g. adding a column to a table). Physical: being able to change the internal schema without changing the conceptual schema (e.g. adding an index, reorganizing a file). Logical independence is harder, because application programs depend directly on the logical structure of the data (tables, columns); they do not depend on the physical details anyway.

  2. What is a weak entity type? Why is its participation in the identifying relationship always total?

    An entity type with no key of its own, whose entities are identified by being related to an entity of another entity type (the owner). Its full identifier = the owner's key + the partial key. Since it cannot be identified without its owner, every weak entity must be related to an owner: existence dependency, i.e. total participation.

  3. What is the difference between a superkey and a key (candidate key)? Give an example.

    Superkey: a set of attributes whose values are the same in no two tuples in any valid state. Key: a minimal superkey: no attribute can be removed from it. In EMPLOYEE {Ssn, Lname} is a superkey but not a key; {Ssn} is a key.

  4. Define the entity integrity and referential integrity constraints.

    Entity integrity: no primary key value (no part of a composite PK) can be NULL. Referential integrity: a foreign key value is either equal to an existing PK value in the referenced relation or NULL.

  5. Explain disjoint vs. overlapping and total vs. partial specialization with an example each.

    Disjoint: an entity is in at most one subclass (EMPLOYEE → {HOURLY, SALARIED}). Overlapping: it can be in several subclasses (PART → {MANUFACTURED, PURCHASED}). Total: every entity of the superclass is in at least one subclass (every employee is hourly or salaried). Partial: some are in none (not every employee is a SECRETARY/ENGINEER/TECHNICIAN).

  6. What is the difference between a shared subclass and a category?

    The members of a shared subclass are in the intersection of all the superclasses and inherit from all of them (multiple inheritance). The members of a category are in the union of the superclasses, belong to only one of them and inherit only from it (selective inheritance).

  7. What is the difference between WHERE and HAVING?

    WHERE is applied to individual rows before grouping and cannot contain aggregates. HAVING is applied to groups after grouping and can contain aggregates.

  8. When is a view updatable?

    A view defined on a single base table, without aggregates or grouping, that contains the base table's primary key (and its NOT NULL columns without a default) is updatable: each view row corresponds to a single base row. In views with joins an update is usually ambiguous, in those with aggregates/grouping impossible.

  9. What is the difference between an assertion and a trigger?

    An assertion is a declarative constraint: the condition must always be TRUE and an operation that violates it is rejected. A trigger is procedural: when an event (INSERT/UPDATE/DELETE) and an optional condition occur, it runs the specified action (ECA). The action does not have to be a rejection: it can be sending a notification or updating another table.

Worked problem 1: ER design

  • University students are kept with a student number (unique), a name, one or more phones and a grade point average (computed from the grades).
  • Every course has a unique code and a number of credits. A course's prerequisites are other courses.
  • Courses are offered in terms as sections. A section is identified by a section number, a term and a year, but only within its course (the same section number is used in different courses).
  • Each section is taught by exactly one instructor; an instructor can teach many sections or none.
  • Students enroll in sections and a grade is kept for each enrollment.
  • Each instructor works in exactly one department; each course is offered by exactly one department.

Worked problem 2: constraint violations

On COMPANY's starting data (the data all the boxes on the site use), which constraints does each of the following operations violate if applied on its own? If there is a violation, what can the DBMS do? You can look at the rows needed for the answer from the table names below. The values are written in the order of the tables' columns: DEPENDENT(Essn, Dependent_name, Sex, Bdate, Relationship), WORKS_ON(Essn, Pno, Hours), DEPT_LOCATIONS(Dnumber, Dlocation).

  1. INSERT INTO DEPENDENT VALUES ('453453453', 'John', 'M', '1990-12-12', 'Son');
  2. INSERT INTO WORKS_ON VALUES ('677678989', NULL, 40.0);
  3. DELETE FROM PROJECT WHERE Pname = 'ProductX';
  4. UPDATE PROJECT SET Pnumber = 30 WHERE Pnumber = 10;
  5. INSERT INTO DEPT_LOCATIONS VALUES (2, 'Houston');
  1. No violation: English (453453453) has no dependent named 'John', the PK (Essn, Dependent_name) is new; Essn refers to an existing employee.
  2. Two violations: entity integrity (Pno is part of the PK and NULL) and referential integrity (there is no employee 677678989). Rejected.
  3. Referential integrity: rows in WORKS_ON refer to ProductX (Pno = 1). Options: reject; CASCADE (delete those WORKS_ON rows too); SET NULL cannot be used, because Pno is part of the PK.
  4. Key constraint: Pnumber = 30 already exists (Newbenefits). Also WORKS_ON rows refer to 10: if the PK changes, referential integrity is affected too (with ON UPDATE CASCADE they would become 30 as well; the key violation would still remain).
  5. Referential integrity: there is no department 2. Rejected.

Worked problem 3: keys

FLIGHT(Flight_no, Date, Gate, Pilot_id, Departure_time). Rules: the same flight number flies once a day; a pilot cannot take two flights on the same day at the same time; a single flight departs from a gate on the same day at the same time. Find all the candidate keys; choose one as the primary key.

{Flight_no, Date}: a flight number once a day. {Pilot_id, Date, Departure_time}: a pilot on a single flight at a time. {Gate, Date, Departure_time}: a gate with a single flight at a time. All three are minimal (the rule breaks when an attribute is removed), so all three are candidate keys. The smallest, {Flight_no, Date}, is chosen as the primary key; the others are defined as UNIQUE. {Flight_no, Date, Gate} is a superkey but not a key.

Common mistakes

  1. Forgetting the join condition → a Cartesian product. Usually n − 1 join conditions for n tables in FROM.
  2. Writing = NULL. It is always UNKNOWN; use IS NULL.
  3. NOT IN + NULL. If the inner query returns a NULL, NOT IN selects no rows; use NOT EXISTS.
  4. An aggregate in WHERE. WHERE COUNT(*) > 2 is invalid; HAVING.
  5. A non-grouped column. Only GROUP BY columns and aggregates in SELECT.
  6. The Q28 trap. A condition in WHERE also reduces the rows HAVING counts. For a condition about all the members of a group, a subquery.
  7. "At least one" instead of "every". IN means ∃; for ∀ a double NOT EXISTS or EXCEPT.
  8. Outer join + COUNT(*). Rows padded with NULLs are counted too; COUNT(a_column_of_the_right_table).
  9. Duplicates. Joins can produce the same row several times; DISTINCT (or EXISTS) if needed.
  10. Mixing up where (min,max) and 1:N go. (min,max) is written next to its own entity, 1/N on the other side.
  11. Taking a weak entity's partial key for a key. The full identifier = the owner's key + the partial key.
  12. Putting an M:N relationship's attribute on an entity. It can be moved only in 1:1 and 1:N (to the N side).
  13. Saying a deletion violates the domain or key constraint. A deletion can violate only referential integrity.
  14. Taking a superkey for a key. A key must be minimal.
