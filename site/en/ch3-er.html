The ER model

The Entity-Relationship (ER) model is a high-level data model that turns requirements into a conceptual schema: it describes the real world with entities, their attributes and the relationships among them.

  • Extract the entities, attributes (with their kinds) and keys from a requirements text.
  • Find the relationships and determine the cardinality (1:1, 1:N, M:N) and participation (total/partial) of each; write the same constraint with (min,max) too.
  • Recognize a weak entity, its partial key and its identifying relationship, and draw them correctly.
  • Decide which entity a relationship attribute can be moved to; tell a ternary relationship apart from three binary ones.

The database design process

  1. Requirements collection and analysis: data requirements and functional requirements (user operations).
  2. Conceptual design: a conceptual schema in a high-level model (ER). Independent of the DBMS; used to communicate with users.
  3. Logical design (data model mapping): translating the conceptual schema into the DBMS's model (e.g. relational). The ER→relational mapping is in Ch 9 of the book.
  4. Physical design: internal storage structures, indexes, access paths.

This page covers step 2: reading a requirements text and drawing an ER diagram. This is the typical exam question: you are given a paragraph and asked to show its entities, attributes, relationships and constraints in a diagram. At the end of the page you will do it yourself with a hospital example.

Notation

The book uses Chen notation. All the diagrams on this site are drawn with the same symbols. The meaning of the symbols is explained one by one in the sections below; you do not need to memorize them now, you can come back to this table while reading:

Entities and attributes

  • Entity: a "thing" with an independent existence in the real world: physical (a person, a car) or conceptual (a company, a job, a course).
  • Attribute: a property that describes an entity: Name, Ssn, Salary.
  • Entity type: the type of entities with the same attributes (schema level: intension). Entity set (collection): the set of entities of that type at a particular moment (extension). The book calls both by the same name: EMPLOYEE.

Keys and value sets

  • Key attribute: the attribute(s) whose value is distinct for each entity. Underlined in the diagram. A key is a constraint that holds for all possible states of the entity type (not just for today's data).
  • A key can be composite: then the composite attribute must be minimal (e.g. a car's Registration(Number, State)).
  • An entity type can have several keys: CAR has both Vehicle_id and Registration. A type with no key at all is a weak entity type.
  • Value set (domain): the set of values an attribute can take (e.g. integers between 16 and 70 for Age). Mathematically an attribute A is a function from E to the power set of V: A : E → P(V).

COMPANY: from requirements to a schema

Let us see the concepts on an example. The requirements in the book (Section 3.2) are below; the diagram was drawn from them. The diagram contains constructs not explained yet (relationships, the 1/N numbers, double lines, a weak entity); they are explained in the sections relationship types, structural constraints and weak entities. For now look at the entities (rectangles) and attributes (ellipses).

  1. The company is organized into departments. Each department has a unique name, a unique number and a particular employee who manages it; the date the manager started is kept. A department may have several locations.
  2. A department controls a number of projects. Each project has a unique name, a unique number and a single location.
  3. For each employee the name, Ssn, address, salary, sex and birth date are kept. An employee is assigned to one department but may work on several projects controlled by different departments; the weekly hours on each project and the employee's direct supervisor are kept.
  4. For insurance purposes each employee's dependents are kept: name, sex, birth date, relationship to the employee.

How did the words of the requirements turn into the diagram? "unique" → key; "several locations" → the multivalued Locations; "manages" → the 1:1 MANAGES, with the start date as the relationship's attribute Start_date; "weekly hours" → WORKS_ON's attribute Hours; "direct supervisor" → the recursive SUPERVISION relationship of EMPLOYEE with itself; "dependents" → the weak entity DEPENDENT (a dependent's name alone is not unique).

Relationship types

  • A relationship type R is a set of associations among n entity types (E1, …, En). Each relationship instance ri associates exactly one entity from each Ej. Mathematically R ⊆ E1 × E2 × … × En.
  • Degree: the number of participating entity types: binary (2, the most common), ternary (3), n-ary.
  • Attribute or relationship? In a first draft a relationship can look like an attribute (e.g. an EMPLOYEE attribute Department). In ER design attributes that refer to an entity type are turned into relationships.
  • Role name: the role an entity plays in the relationship. When the same entity type takes part twice in a relationship in different roles (a recursive / self-referencing relationship), role names are required: in SUPERVISION EMPLOYEE is both supervisor and supervisee.

Structural constraints of binary relationships

A relationship type is constrained by two questions: how many times can an entity take part in this relationship at most (cardinality), and how many times must it take part at least (participation)?

Cardinality ratio

The maximum number of relationship instances an entity can take part in: 1:1, 1:N (or N:1), M:N. In the diagram 1, N, M are written on the edges. All the relationships of COMPANY are in the table below.

Participation constraint

Does the existence of an entity depend on its being related to another entity? That is, how many participations at least?

  • Total (existence dependency): every entity must take part in at least one relationship instance. A double line. E.g. every employee works for a department.
  • Partial: some entities may not take part. A single line. E.g. not every employee manages a department.

The (min, max) notation

Cardinality gives the maximum, participation the minimum; together they are the structural constraints of the relationship. (min, max) combines both in one notation: a pair (min, max) for each participation of E in R, with 0 ≤ min ≤ max and max ≥ 1. Each entity in E takes part in at least min and at most max instances of R. min = 0 → partial, min ≥ 1 → total.

The reading-direction trap. In the 1:N notation N is the number of entities "on the other side": EMPLOYEE —N— WORKS_FOR —1— DEPARTMENT reads "a department has N employees, an employee is in 1 department". In the (min,max) notation the numbers are the participation of the entity on their own side: EMPLOYEE (1,1) — WORKS_FOR — (1,N) DEPARTMENT. So in the (min,max) diagram of an N:1 relationship the "N" side is swapped. Exams can ask you to translate between the two notations.

Requirement: "Each department controls several projects; each project is controlled by a single department. There may be departments that control no projects."

  1. How many CONTROLS instances does one PROJECT take part in? At least 1 ("each project"), at most 1 ("a single department"): (1,1). Since min = 1, the PROJECT side is total (a double line).
  2. How many CONTROLS instances does one DEPARTMENT take part in? At least 0 ("there may be departments that control none"), at most many ("several"): (0,N). Since min = 0, the DEPARTMENT side is partial.
  3. The cardinality ratio is read from the two maxima: a department is related to many projects, a project to a single department: DEPARTMENT:PROJECT = 1:N. In the 1:N notation "1" is written next to DEPARTMENT and "N" next to PROJECT; in (min,max) (0,N) is next to DEPARTMENT and (1,1) next to PROJECT.

Attributes of relationships

Relationship types can have attributes too: WORKS_ON's Hours, MANAGES's Start_date.

  • The attribute of a 1:1 relationship can be moved to either of the two entities (Start_date → DEPARTMENT as Mgr_start_date; that is how it is in the relational schema too).
  • The attribute of a 1:N relationship can be moved only to the N side (each N-side entity takes part in a single relationship instance).
  • The attribute of an M:N relationship cannot be moved to any entity; its value is determined by the combination of the entities (Hours belongs to an employee–project pair). In the relational schema it becomes a separate table: WORKS_ON(Essn, Pno, Hours).

Weak entity types

  • An entity type with no key of its own. Its entities are identified by being related to a particular entity of another entity type (the identifying / owner entity type).
  • The relationship that makes this link is the identifying relationship (a double diamond). The weak entity's participation in it is always total (it cannot exist without its owner: existence dependency).
  • Partial key (discriminator): the attribute(s) that tell apart the weak entities related to the same owner; underlined with a dashed line. DEPENDENT's partial key is Dependent_name: both Wong and Smith have a daughter named Alice, but two dependents of the same employee do not have the same name. What fully identifies a dependent is the owner's key combined with the partial key: (the EMPLOYEE's Ssn, Dependent_name). In the relational schema this becomes DEPENDENT's primary key (Essn, Dependent_name) (Ch 5).
  • Not every existence dependency produces a weak entity: DRIVER_LICENSE is related to PERSON with total participation, but it is not weak because it has its own key (the licence number).
  • A weak entity can sometimes be modelled as a complex (composite, multivalued) attribute instead; if it takes part in independent relationships, it has to be an entity.

Relationships of higher degree

  • A ternary relationship usually does not carry the same information as three binary relationships: even if CAN_SUPPLY(s,p), USES(j,p) and SUPPLIES(s,j) hold, it does not follow that s supplies p to j.
  • A ternary relationship is sometimes shown with a weak entity and three identifying relationships (making SUPPLY an entity type tied to its three owners).
  • A ternary relationship and binary relationships can both be in the schema together: a binary relationship can add a constraint to the ternary one.
  • Cardinality of ternary relationships: writing 1 on one participant means that each combination of the other two is matched with at most one entity of that participant. E.g. if 1 is written on the SUPPLIER side of SUPPLY: for each (project, part) pair there is at most one supplier that supplies that part to that project. The same supplier can still supply many parts to many projects.

Ternary, or three binaries? When deciding, ask: is the information really a fact made up by the three entities together? "Supplier s supplied part p to project j" is ternary; you cannot get the same information back from the binaries "s can supply p", "j uses p", "s works with j": s can supply p and j uses p, but that does not say j got p from s.

Naming and design choices

  • Entity type and relationship type names are singular nouns in UPPER case: EMPLOYEE, WORKS_FOR. Attributes start with a capital letter: Fname. Role names are lower case: supervisor.
  • In the requirements the nouns are candidates for entity types, the verbs for relationship types, and the words describing the nouns for attributes.
  • Design is iterative: an attribute that refers to another entity becomes a relationship; an attribute shared by several entities (e.g. Location repeated in DEPARTMENT and PROJECT) can become an entity of its own; an entity with a single attribute related to only one entity can be turned into an attribute.

Alternative notations. The book also shows UML class diagrams: entity = class (attributes inside the box), relationship = association, multiplicity (0..1, 1..*, *) instead of (min,max); weak entity = qualified association; relationship attribute = link attribute. The crow's foot notation is also common.

Test yourself

"Each student enrolls in at least one and at most six courses; a course may have no students or many students." What is the correct (min,max) pair for STUDENT —ENROLLS— COURSE?

  1. STUDENT (1,6), COURSE (0,N)
  2. STUDENT (0,N), COURSE (1,6)
  3. STUDENT (1,N), COURSE (0,N)
  4. STUDENT (1,6), COURSE (1,N)
First think of one student: how many ENROLLS instances does it take part in? At least 1, at most 6 → (1,6), total. Then of one course: at least 0, at most many → (0,N), partial. The cardinality ratio is M:N (both sides more than one).

A student can have several phone numbers. How should Phone be drawn in the ER diagram?

  1. A dashed ellipse
  2. A double ellipse (multivalued)
  3. A composite attribute connected to its components
  4. An underlined ellipse
An attribute that can take several values for one entity is multivalued and is shown with a double ellipse. In the relational schema it becomes a separate table (like DEPT_LOCATIONS).

"Each project is controlled by exactly one department; a department may control no projects or many projects." What are the (min,max) values for CONTROLS?

  1. DEPARTMENT (1,1), PROJECT (0,N)
  2. DEPARTMENT (1,N), PROJECT (1,1)
  3. DEPARTMENT (0,N), PROJECT (1,1)
  4. DEPARTMENT (0,1), PROJECT (1,N)
(min,max) gives each entity's own participation. A department controls 0 or more projects: (0,N). Each project exactly once: (1,1). Compare with DEPARTMENT:PROJECT = 1:N in the 1:N notation; notice that the numbers swap places.

Why can WORKS_ON's Hours attribute not be moved to EMPLOYEE or PROJECT?

  1. Because WORKS_ON is M:N; Hours belongs to an (employee, project) pair.
  2. Because Hours is a derived attribute.
  3. Because relationships cannot have attributes; this is a design mistake.
  4. Because the participation of both sides is total.
In 1:1 the attribute can be moved to either side, in 1:N to the N side. In M:N an employee works different hours on many projects; a single value belongs to no entity.

Which statement about DEPENDENT is false?

  1. DEPENDENT is a weak entity type; its owner is EMPLOYEE.
  2. DEPENDENT's participation in DEPENDENTS_OF is total.
  3. Dependent_name is a partial key.
  4. Dependent_name is DEPENDENT's key, because every dependent has a different name.
Two different employees can have dependents with the same name (Wong and Smith both have a daughter named "Alice"). The name distinguishes only among the dependents of the same employee. The full identifier (the owner's key + the partial key) = (Essn, Dependent_name).

In a hospital every patient has exactly one room; at most 2 patients stay in a room and rooms may be empty. Which are the correct constraints for PATIENT–STAYS_IN–ROOM?

  1. PATIENT:ROOM = 1:N; PATIENT partial, ROOM total
  2. PATIENT:ROOM = N:1; PATIENT total, ROOM partial; (min,max): PATIENT (1,1), ROOM (0,2)
  3. PATIENT:ROOM = M:N; both partial
  4. PATIENT:ROOM = N:1; both total; (min,max): PATIENT (1,1), ROOM (1,2)
Each patient is in exactly 1 room → on the PATIENT side max 1, min 1 (total). A room has 0–2 patients → ROOM (0,2), partial. The ratio is N:1 (many patients, one room). The (min,max) notation can express more than the cardinality (at most 2).
