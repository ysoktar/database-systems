Indexing structures

On the previous page we saw how many block reads it takes to find a record: b/2 on average in an unordered file, log2 b in a sorted file. Indexes are additional access paths that, like the index at the back of a book, tell which block holds the wanted value with far fewer reads. This page explains the index types, their costs, and the B+-tree that almost every database uses today.

Single-level ordered indexes

An index is an additional access structure used to reach records faster for certain search conditions; it does not change where the records of the data file are on disk, it provides a secondary access path to them. An index can be built on any field, and a file can have several indexes. The field the index is built on is the indexing field. An ordered index stores each value (or some values) of the indexing field with pointers to the disk blocks that contain that value, sorted by value. Because the index file is much smaller than the data file, a binary search on it reads far fewer blocks.

There are three kinds of single-level ordered indexes:

  • Primary index: built on the ordering key when the data file is sorted on a key field. The index has an entry for each block of the data file: the key of the block's first record (the block anchor) and the block's address. So a primary index is sparse.
  • Clustering index: used when the data file is sorted on a non-key field, where a value can repeat in many records. The index has an entry for each distinct value of the field, pointing to the first block where the value appears. Since a file can be sorted on only one field, a file has at most one primary or one clustering index.
  • Secondary index: built on any field the file is not sorted on, and a file can have many secondary indexes. The records are scattered with respect to that field, so the index needs an entry for each record; a secondary index is therefore dense. It takes more space than a primary index and the search is longer, but without the index the same search would scan the whole file.

A dense index has an entry for every search value in the data file; a sparse index has entries for only some values. The big problem of a primary index is insertion and deletion: keeping the order moves records and changes block anchors. An unordered overflow file or a linked list of overflow records per block is used for this.

Computing index costs

An index entry consists of a key value (V bytes) and a pointer (P bytes), so the blocking factor of the index is bfri = ⌊B / (V + P)⌋. The index takes bi = ⌈ri / bfri⌉ blocks, where ri is the number of index entries: the number of data blocks for a primary index, the number of records for a dense secondary index. A binary search on the index reads ⌈log2 bi⌉ blocks, and one more block is needed to read the record itself.

The book's example: r = 300,000 records, R = 100 bytes, B = 4096 bytes. The data file has bfr = 40 and b = 7500 blocks; if the file is sorted, binary search reads ⌈log2 7500⌉ = 13 blocks. With a key of V = 9 bytes and a pointer of P = 6 bytes an index entry is 15 bytes and 273 entries fit in a block. The 7500 entries of the primary index take ⌈7500 / 273⌉ = 28 blocks, and a search reads ⌈log2 28⌉ + 1 = 6 blocks. If the same file is not sorted on this field, the 300,000 entries of a dense secondary index take 1099 blocks and a search reads ⌈log2 1099⌉ + 1 = 12 blocks; without the index, b/2 = 3750 blocks would be read on average.

Multilevel indexes

Binary search halves the search space at each step. A multilevel index shrinks it by the fan-out (fo) at each step; fo is the number of entries that fit in an index block (bfri). The idea: the index file is itself a sorted file, so a primary index can be built on it too. The first index is the first level (base level); the second level is a primary index holding the anchors of the first level's blocks; the third level is the index of the second. This continues until the top level fits in a single block. If the first level has r1 entries, the number of levels is t = ⌈logfo r1⌉, and a search reads t + 1 blocks.

In the book's example the first level of the dense secondary index is 1099 blocks. With fo = 273 the second level is ⌈1099 / 273⌉ = 5 blocks and the third level 1 block; so t = 3 and a search reads 4 blocks. The same search read 12 blocks with the single-level index. The book's Figure 17.6 shows a two-level primary index resembling the ISAM (indexed sequential access method) organization.

The problem of a multilevel index is again insertion and deletion: every level is a sorted file. B-trees and B+-trees solve this by leaving some free space in each node; they are called dynamic multilevel indexes.

Search trees and B-trees

A tree is made of nodes. Every node except the root has one parent and zero or more children. A node with no children is a leaf, a non-leaf node an internal node. The subtree of a node is the node and all its descendants. If leaves are at different levels, the tree is unbalanced.

In a search tree of order p each node holds at most p − 1 search values and p pointers: <P1, K1, P2, K2, …, Kq−1, Pq>. The values in a node are sorted, and every value X in the subtree under Pi satisfies Ki−1 < X < Ki. A search starts at the root and in each node follows a pointer according to the range the wanted value falls in. But if the insertion and deletion algorithms do not keep the tree balanced, it becomes unbalanced and search slows down.

A B-tree is a search tree that solves this problem. A B-tree is always balanced: all leaves are at the same level. Space wasted by deletion never becomes excessive, because every node except the root is at least half full. In a B-tree of order p each node holds at most p − 1 search values, and in a B-tree each value comes with a data pointer to its record. When a value is inserted into a full node, the node splits in two and the middle value moves up to the parent; if the root splits, the tree grows by one level. B+-trees

Most databases use a variant of the B-tree, the B+-tree. In a B+-tree data pointers are stored only in the leaves. The leaves have an entry for every value of the search field; if the search field is a key the entry points straight to the record, otherwise to a block holding the pointers of the records with that value. Internal nodes only guide the search: some values from the leaves are repeated in internal nodes. The leaves are also linked by a pointer to the next leaf, so all values in a range can be read in order along the leaves.

Compare the four node structures side by side. A search tree node and a B+-tree internal node have the same shape; a B-tree adds a data pointer next to every value; a B+-tree leaf carries data pointers instead of tree pointers, plus a pointer to the next leaf. Hover over a cell to see what it is.

Since internal nodes have no data pointers, more values fit in an internal node, so the fan-out is larger and the tree is flatter. In the book's example B = 512 bytes, V = 9 bytes, the tree pointer P = 6 bytes and the data pointer Pr = 7 bytes. The order of an internal node comes from (p − 1)·V + p·P ≤ B, giving p = 34; the order of a leaf from pleaf·(V + Pr) + P ≤ B, giving pleaf = 31. If nodes are 69% full on average, a three-level B+-tree (root, two internal levels and the leaves) can point to about 255,507 records.

To search for a value, start at the root. In an internal node, with the wanted value K, follow the first pointer if K ≤ K1, the i-th pointer if Ki−1 < K ≤ Ki, and the last pointer if K > Kq−1 (the book's Algorithm 17.2). On reaching a leaf, look for the value there. Insertion follows the same path: the value is added to the right leaf. If the leaf overflows it splits: the first ⌈(pleaf + 1)/2⌉ values stay, the rest move to a new leaf, and the last value of the left leaf is copied up to the parent. If an internal node overflows it also splits, but this time the middle value is moved up to the parent (not copied). If the root splits, a new root is created and the tree grows by one level.

Indexes on multiple keys

Many queries have conditions on several attributes, for example "employees in department 4 who are 59 years old". There are three methods for this:

  • An index on a composite key: a pair of values such as <Dno, Age> is used as a single search key, and pairs are sorted first on Dno and, if equal, on Age. It also helps conditions on only the first attribute, but not conditions on only the second.
  • Partitioned hashing: each attribute is turned into a few bits by its own hash function, and the bits are concatenated into the bucket address. It suits equality comparisons only; it does not support range queries.
  • Grid file: an array with one dimension per search attribute is built; for example one dimension is divided by Dno values and the other by age ranges. Each cell of the array points to the bucket holding the records with that pair of values (the book's Figure 17.14).

Other types of indexes

A hash index is a secondary access structure that uses hashing on a search key other than the one used for the organization of the data file. Its entries are of the form (K, Pr) or (K, P): Pr points to the record containing the key, P to the block containing that record. It is very fast for equality searches but does not help range queries.

A bitmap index suits columns with many rows and few distinct values. For each value of the column an array of as many bits as there are rows is kept: bit i is 1 if row i has that value, 0 otherwise. Several conditions are combined very quickly with AND, OR and NOT on the bitmaps. An existence bitmap is used to tell deleted rows apart; bitmaps can also be used in the leaves of a B+-tree. Below you can see the bitmaps of the Sex and Dno columns for the COMPANY employees and, by choosing a condition, follow how the bitmaps are ANDed.

In a function-based index a function is applied to one or more fields and the result becomes the index key. It was introduced in Oracle. For example an index created with CREATE INDEX upper_ix ON Employee (UPPER(Lname)); can be used in a query with the condition WHERE UPPER(Lname) = 'SMITH'; an ordinary index on Lname could not be used for this condition.

General issues concerning indexing

In a physical index the pointer gives the physical address of the record; if the record moves, the pointer must change too. When record addresses are expected to change often, a logical index is used: its entries are of the form (K, Kp), where Kp is a key value used to find the record in the primary organization.

The general form of the command that creates an index is: CREATE [UNIQUE] INDEX <name> ON <table> (<column> [ASC | DESC], …) [CLUSTER];. UNIQUE and CLUSTER are optional. A UNIQUE index is also used to enforce a key constraint: an insertion is rejected if the new record's key value already exists. On an index over a non-key field values may repeat. In the boxes below you can list the indexes of COMPANY, create a UNIQUE index and see how it rejects a duplicate.

SHOW INDEX FROM EMPLOYEE;

DROP TABLE IF EXISTS demo.EMP_IDX;
CREATE TABLE demo.EMP_IDX AS SELECT Ssn, Fname, Lname, Dno FROM EMPLOYEE;
CREATE UNIQUE INDEX idx_lname ON demo.EMP_IDX (Lname);
CREATE INDEX idx_dno ON demo.EMP_IDX (Dno);
SHOW INDEX FROM demo.EMP_IDX;
INSERT INTO demo.EMP_IDX VALUES ('999999999', 'Ann', 'Smith', 5);

The last INSERT is rejected because of the UNIQUE index on Lname (MySQL error code 1062), since the table already has an employee with the last name Smith. The index on Dno is not UNIQUE, so the same department number can appear in many rows.

Other issues are these. Long, variable-length strings lower the fan-out; prefix compression is used against this: internal nodes store only as much of a key's prefix as is needed to separate the subtrees, instead of the whole key. Index tuning means reorganizing indexes to fit the requirements; the initial choice is revised for these reasons: some queries take too long because an index is missing, some indexes are never used, some indexes are updated too often because they are on a frequently changing attribute. A file with a secondary index on every field is a fully inverted file. Some systems allow indexing hints in queries. Finally, relations can be stored column by column instead of row by row (column-based storage); it gives advantages for read-only queries and extra freedom in choosing indexes.

Physical database design in relational databases

The goal of physical design is to create an appropriate storage structure for the data and to guarantee good performance. For this one must know the job mix of the applications: which queries and updates run, how often, and with what time constraints. For each query the files accessed and the attributes in selection and join conditions are analyzed; for each update the kind of operation (insert, delete, modify) and the attributes updated.

  • Frequency of queries and transactions: how often each attribute is used as a selection or join attribute is examined. By the 80-20 rule, 80 percent of the processing is accounted for by only 20 percent of the queries and transactions; the design targets this 20%.
  • Time constraints: the selection attributes of queries with time constraints are candidates for the primary access structure.
  • Frequency of updates: a frequently updated file should have few access paths, because every index must itself be updated and slows down updates.
  • Uniqueness constraints: there should be an access path on every candidate key attribute that is a primary key or UNIQUE.

The design decisions about indexing are: whether to index an attribute (yes if it is a key or a query uses it); which attribute or attributes to index on (single or multiple); whether to set up a clustered index (there can be only one per table); whether to use a hash index instead of a tree index (hash indexes do not support range queries); whether to use dynamic hashing (it suits very volatile files).

A dense secondary index has one entry per record: 300,000 entries, with 273 per block, take 1099 blocks. Binary search reads ⌈log2 1099⌉ = 11 blocks, plus 1 block for the record itself. You can try the same numbers in the calculator.

What is the most important difference between a B+-tree and a B-tree?

  1. Data pointers are only in the leaves, and the leaves are linked.
  2. A B+-tree is balanced, a B-tree is not.
  3. In a B+-tree nodes need not be half full.
  4. A B+-tree can be used only for equality searches.
In a B-tree each value sits in its node with its own data pointer. In a B+-tree all values are in the leaves with their data pointers; values in internal nodes are repeated only to show the way. Since internal nodes have no data pointers, more values fit and the tree is flatter.

A B+-tree with p = 3 and pleaf = 2 has a single leaf [5, 8]. What happens when 1 is inserted?

  1. The leaf becomes [1, 5, 8] and the tree does not change.
  2. The leaf splits and 1 goes up to the root.
  3. The leaf splits, 5 moves to the root and is removed from the leaves.
  4. The leaf splits into [1, 5] and [8], and 5 is copied to a new root.
The overflowing leaf splits: the first ⌈(pleaf + 1)/2⌉ = 2 values stay, the rest move to a new leaf. The last value of the left leaf (5) is copied to the parent; since there is no parent, a new root is created. This is exactly the third step of the book's insertion order in the player.

A column has only two distinct values (M and F) and the table has millions of rows. Which index fits this column best?

  1. A hash index
  2. A bitmap index
  3. A clustering index
  4. A function-based index
A bitmap index keeps as many bits as rows for each distinct value; two values need only two bit arrays. Conditions such as "Sex = 'F' AND Dno = 5" are found directly by ANDing two bitmaps. You can try this in the bitmap example on the page.
