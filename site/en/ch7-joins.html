Joins, grouping, WITH

Explicit joins in FROM (inner and outer), aggregate functions, grouping and group conditions, WITH for intermediate results, CASE for conditional values, and recursive queries.

  • Predict the results of inner, left/right/full outer, natural and cross joins.
  • Use COUNT, SUM, AVG, MIN, MAX and know how they handle NULLs.
  • Write group queries with GROUP BY and HAVING; put WHERE and HAVING in the right place and follow the conceptual order of evaluation.
  • Read WITH, CASE and WITH RECURSIVE and write simple examples of them.

Joined tables (explicit joins)

Writing the join condition in FROM instead of mixing it into WHERE makes the query readable and makes outer joins possible.

SELECT Fname, Lname, Address
FROM   (EMPLOYEE JOIN DEPARTMENT ON Dno = Dnumber)
WHERE  Dname = 'Research';

NATURAL JOIN

No condition is written: an equality condition is added automatically for every pair of columns with the same name in the two tables, and these columns appear once in the result. In EMPLOYEE the department number is called Dno, in DEPARTMENT Dnumber; since there is no common name, DEPARTMENT's columns are renamed first. The book writes this as (EMPLOYEE NATURAL JOIN (DEPARTMENT AS DEPT (Dname, Dno, Mssn, Msdate))). Since MySQL does not accept renaming with a column list on base tables, the same is done with a subquery:

SELECT Fname, Lname, Address
FROM   EMPLOYEE NATURAL JOIN
       (SELECT Dname, Dnumber AS Dno, Mgr_ssn AS Mssn, Mgr_start_date AS Msdate
        FROM   DEPARTMENT) AS DEPT          -- now the only common column is Dno
WHERE  Dname = 'Research';

NATURAL JOIN also equates same-named columns you do not want equated. EMPLOYEE NATURAL JOIN DEPENDENT tries to equate both the identifying columns (none: Ssn ≠ Essn) and Sex and Bdate; the result is meaningless. If you see NATURAL JOIN in an exam, check the common column names one by one.

Compare the kinds of join

  • INNER JOIN (the default JOIN): only the matching pairs.
  • LEFT / RIGHT / FULL OUTER JOIN: unmatched rows are kept too, with the other side padded with NULLs. (Old Oracle syntax: +=, =+, +=+.) MySQL has no FULL OUTER JOIN; the same result is obtained with the UNION of a LEFT and a RIGHT join (the FULL tab of the comparison above).
  • CROSS JOIN: the Cartesian product. Combinations such as NATURAL LEFT OUTER JOIN are valid too.
  • Joins can be nested (a multiway join):
-- Q8B: every employee with the supervisor's name; Borg appears with NULL
SELECT E.Lname AS Employee_name, S.Lname AS Supervisor_name
FROM   (EMPLOYEE AS E LEFT OUTER JOIN EMPLOYEE AS S ON E.Super_ssn = S.Ssn);
-- Q2A: projects in Stafford, controlling department, manager
SELECT Pnumber, Dnum, Lname, Address, Bdate
FROM   ((PROJECT JOIN DEPARTMENT ON Dnum = Dnumber)
          JOIN EMPLOYEE ON Mgr_ssn = Ssn)
WHERE  Plocation = 'Stafford';

Aggregate functions

COUNT, SUM, MAX, MIN, AVG: summarize a set of rows into a single value. Used in the SELECT list or in HAVING; they cannot be used in WHERE.

SELECT SUM(Salary), MAX(Salary), MIN(Salary), AVG(Salary)
FROM   EMPLOYEE;
SELECT SUM(Salary) AS Total_sal, MAX(Salary) AS Highest_sal, MIN(Salary) AS Lowest_sal, AVG(Salary) AS Average_sal
FROM   (EMPLOYEE JOIN DEPARTMENT ON Dno = Dnumber)
WHERE  Dname = 'Research';

SELECT COUNT(*) FROM EMPLOYEE;                                       -- Q21
SELECT COUNT(*) FROM EMPLOYEE, DEPARTMENT
WHERE  Dno = Dnumber AND Dname = 'Research';                          -- Q22
SELECT COUNT(DISTINCT Salary) FROM EMPLOYEE;                          -- Q23

Aggregates and NULL: COUNT(*) counts rows (NULLs included). COUNT(A), SUM(A), AVG(A), MAX(A), MIN(A) are computed over the non-NULL values of A. On an empty set COUNT returns 0, the others NULL. COUNT(DISTINCT A) drops duplicates.

SELECT COUNT(*) AS all_rows, COUNT(Hours) AS non_null_hours,
       SUM(Hours) AS total, AVG(Hours) AS avg_non_null,
       SUM(Hours) / COUNT(*) AS avg_if_null_were_0
FROM   WORKS_ON;

SELECT Lname, Fname
FROM   EMPLOYEE
WHERE  (SELECT COUNT(*) FROM DEPENDENT WHERE Ssn = Essn) >= 2;

GROUP BY and HAVING

GROUP BY divides the rows into groups by the values of the grouping columns; the aggregates are applied to each group separately. Rule: the SELECT list can contain only grouping columns and aggregates.

To see the grouping, first list the rows without grouping, ordered by Dno. Rows with the same Dno will form a group; each group shrinks to a single row in the result. Predict: how many rows does the second query return, and what is the average salary of department 5?

-- the rows before grouping: three groups by Dno (1, 4, 5)
SELECT   Dno, Lname, Salary
FROM     EMPLOYEE
ORDER BY Dno;
-- Q24: one row per group
SELECT   Dno, COUNT(*), AVG(Salary)
FROM     EMPLOYEE
GROUP BY Dno;

Group 5 has four rows (Smith 30000, Wong 40000, Narayan 38000, English 25000): COUNT(*) = 4, AVG = 133000 / 4 = 33250. Lname cannot be in SELECT, because it is undefined which of the group's four different Lnames would be shown.

SELECT   Pnumber, Pname, COUNT(*)
FROM     PROJECT, WORKS_ON
WHERE    Pnumber = Pno
GROUP BY Pnumber, Pname;

If the grouping column has NULL values, the NULLs form a single group of their own (e.g. employees whose Dno is NULL).

HAVING is a condition applied to groups: the groups that do not satisfy it are dropped from the result.

SELECT   Pnumber, Pname, COUNT(*)
FROM     PROJECT, WORKS_ON
WHERE    Pnumber = Pno
GROUP BY Pnumber, Pname
HAVING   COUNT(*) > 2;

SELECT   Pnumber, Pname, COUNT(*)
FROM     PROJECT, WORKS_ON, EMPLOYEE
WHERE    Pnumber = Pno AND Ssn = Essn AND Dno = 5
GROUP BY Pnumber, Pname;

Conceptual order of evaluation

SELECT   <attribute and function list>     -- 5
FROM     <table list>                      -- 1
[ WHERE  <condition> ]                    -- 2  rows
[ GROUP BY <grouping attribute(s)> ]      -- 3
[ HAVING <group condition> ]              -- 4  groups
[ ORDER BY <attribute list> ];            -- 6

The Q28 trap: WHERE or HAVING? The question: "For each department that has more than five employees, the number of its employees who earn more than 40000." The first query below is wrong: WHERE runs before HAVING. Salaries below 40000 are discarded first, then HAVING selects "the departments with more than five employees earning over 40000". The right way is to find "the departments with more than five employees" in a separate inner query.

-- WRONG: counts only employees with Salary > 40000 when testing the department size
SELECT   Dno, COUNT(*)
FROM     EMPLOYEE
WHERE    Salary > 40000
GROUP BY Dno
HAVING   COUNT(*) > 2;
-- RIGHT: departments with more than 2 employees (in total), then count their high earners
SELECT   Dno, COUNT(*)
FROM     EMPLOYEE
WHERE    Salary > 30000
  AND    Dno IN (SELECT   Dno
                 FROM     EMPLOYEE
                 GROUP BY Dno
                 HAVING   COUNT(*) > 2)
GROUP BY Dno;

In the second query the threshold was lowered to 30000 to show the difference. The wrong query returns nothing (at most one person per department earns over 40000); the right query returns 2 for Research (5) and 1 for Administration (4).

The non-grouped column error. SELECT Dno, Lname, COUNT(*) FROM EMPLOYEE GROUP BY Dno is invalid: every group has many Lnames, and it is undefined which one would be shown. MySQL 8 rejects it with error 1055 ("nonaggregated column … is not functionally dependent on columns in GROUP BY clause"; this rule is the ONLY_FULL_GROUP_BY setting). In old MySQL versions, or with this setting turned off, the query runs but shows an arbitrary Lname for each group; in the exam this query counts as wrong. One exception: MySQL 8 recognizes functional dependency. When grouping by a table's primary key there is one row of that table in each group, so the table's other columns can be selected too: SELECT Pnumber, Pname, COUNT(*) … GROUP BY Pnumber is accepted. For the book and the exam keep the rule simple: write every non-grouped column in SELECT into GROUP BY too (GROUP BY Pnumber, Pname, as in Q25).

SELECT Dno, Lname, COUNT(*) FROM EMPLOYEE GROUP BY Dno;

WITH and CASE

WITH defines a temporary table (an intermediate result) that exists only for that query: a kind of "single-use view".

WITH BIGDEPTS (Dno) AS
     ( SELECT   Dno
       FROM     EMPLOYEE
       GROUP BY Dno
       HAVING   COUNT(*) > 2 )
SELECT   Dno, COUNT(*)
FROM     EMPLOYEE
WHERE    Salary > 30000 AND Dno IN (SELECT Dno FROM BIGDEPTS)
GROUP BY Dno;

CASE chooses a value according to conditions: it can be used anywhere a value is expected, such as SELECT, WHERE or the SET of an UPDATE.

UPDATE EMPLOYEE
SET    Salary = CASE WHEN Dno = 5 THEN Salary + 2000
                     WHEN Dno = 4 THEN Salary + 1500
                     WHEN Dno = 1 THEN Salary + 3000
                     ELSE Salary + 0
                END;
SELECT Fname, Lname, Dno, Salary,
       CASE WHEN Salary >= 40000 THEN 'high' WHEN Salary >= 30000 THEN 'mid' ELSE 'low' END AS band
FROM   EMPLOYEE ORDER BY Dno, Salary DESC;

Recursive queries

WITH RECURSIVE: the UNION of a base query and a query that uses itself. It repeats until no new rows are produced (a fixed point). Used for chains of unknown depth in recursive relationships such as supervisor/supervisee.

WITH RECURSIVE SUP_EMP (SupSsn, EmpSsn) AS
     ( SELECT Super_ssn, Ssn
       FROM   EMPLOYEE
       WHERE  Super_ssn IS NOT NULL     -- base: direct supervision
       UNION
       SELECT E.Super_ssn, S.EmpSsn
       FROM   EMPLOYEE AS E, SUP_EMP AS S
       WHERE  E.Ssn = S.SupSsn          -- one level higher
         AND  E.Super_ssn IS NOT NULL )
SELECT * FROM SUP_EMP ORDER BY SupSsn, EmpSsn;

The book's Q29 has no IS NOT NULL in the base query; Borg's NULL supervisor produces a (NULL, Borg) row in the result. For a version that also keeps the level, see notebook Exercise 10.

Test yourself

How many rows does SELECT Dno, COUNT(*) FROM EMPLOYEE WHERE Salary >= 30000 GROUP BY Dno HAVING COUNT(*) >= 2; return? (Salaries: in dept 5, 30000, 40000, 38000, 25000; in dept 4, 25000, 43000, 25000; in dept 1, 55000.)

  1. 3
  2. 1
  3. 2
  4. 0
Apply them in order: WHERE first filters the rows (English, Zelaya, Jabbar are discarded), then GROUP BY groups the rest (5: 3 people, 4: 1 person, 1: 1 person), then HAVING filters the groups. The result is a single row: (5, 3).
SELECT Dno, COUNT(*) FROM EMPLOYEE WHERE Salary >= 30000 GROUP BY Dno HAVING COUNT(*) >= 2;

For "every employee and their number of dependents (0 for those with none)" you wrote FROM EMPLOYEE E LEFT JOIN DEPENDENT D ON E.Ssn = D.Essn GROUP BY E.Ssn. What should you count in SELECT?

  1. COUNT(*)
  2. COUNT(E.Ssn)
  3. SUM(D.Essn)
  4. COUNT(D.Essn)
An outer join keeps the unmatched row with NULLs. COUNT(*) counts that row (1); COUNT(D.Essn) skips the NULL (0). This is exactly the notebook's exercise 6.

EMPLOYEE has 8 rows; DEPENDENT holds the dependents of only 3 different employees (Wong 3, Wallace 1, Smith 3: 7 rows in all). What does SELECT COUNT(*) FROM EMPLOYEE E LEFT OUTER JOIN DEPENDENT D ON E.Ssn = D.Essn return?

  1. 7
  2. 12
  3. 8
  4. 56
The 3 employees with dependents produce 7 rows (one per dependent). The 5 employees with no dependents produce one row each with NULLs: 7 + 5 = 12.

Which query is invalid?

  1. SELECT Dno, MAX(Salary) FROM EMPLOYEE GROUP BY Dno
  2. SELECT Dno FROM EMPLOYEE GROUP BY Dno HAVING AVG(Salary) > 30000
  3. SELECT COUNT(*) FROM EMPLOYEE WHERE Salary > 30000
  4. SELECT Dno, COUNT(*) FROM EMPLOYEE WHERE COUNT(*) > 2 GROUP BY Dno
Aggregates cannot be used in WHERE: WHERE is evaluated row by row, before the groups are formed. The right way is HAVING COUNT(*) > 2.

What does SELECT AVG(Hours) FROM WORKS_ON return if WORKS_ON has 16 rows, one of them with a NULL Hours, and the total is 275?

  1. 275 / 15 ≈ 18.33
  2. 275 / 16 ≈ 17.19
  3. NULL
  4. An error
AVG drops NULLs: the average of the 15 non-NULL values. To count the NULL as 0 we would write SUM(Hours)/COUNT(*) or AVG(COALESCE(Hours, 0)).

What is the difference between WHERE and HAVING?

  1. There is none; HAVING is a synonym of WHERE used with GROUP BY.
  2. HAVING applies to rows, WHERE to groups.
  3. WHERE applies to rows before grouping, HAVING to groups after grouping.
  4. HAVING can only be used together with ORDER BY.
The order: FROM → WHERE (rows) → GROUP BY → HAVING (groups) → SELECT → ORDER BY. A row discarded in WHERE takes part in no group's aggregate (the Q28 trap).
