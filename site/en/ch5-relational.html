The relational model and constraints

The relational model sees a database as a collection of relations: informally, each one a table of values. This page covers the formal concepts of the model and the constraints that keep the data correct.

  • Show the terms relation, tuple, attribute, domain, degree and cardinality on COMPANY.
  • Tell superkey, key, candidate key and primary key apart; decide whether a set of attributes is a superkey/key.
  • Define entity integrity and referential integrity; show the foreign keys in a schema.
  • Say which constraints an INSERT/DELETE/UPDATE violates and list the DBMS's options (reject, cascade, set null, set default).

Look at the DEPARTMENT relation (you can open its rows with the button below):

  • Relation schema: DEPARTMENT(Dname, Dnumber, Mgr_ssn, Mgr_start_date). Four attributes: degree = 4.
  • Relation state: today's three rows (Research, Administration, Headquarters): cardinality = 3. Adding a department changes the state, not the schema.
  • Tuple: t = <'Research', 5, '333445555', '1988-05-22'>. t[Dname] = 'Research', t[Dnumber, Mgr_ssn] = <5, '333445555'>.
  • Domain: dom(Mgr_ssn) = 9-character Ssns, dom(Mgr_start_date) = dates. Mgr_ssn and EMPLOYEE.Ssn come from the same domain; that is the first condition for a foreign key (below).
  • Relational database schema: COMPANY = {EMPLOYEE, DEPARTMENT, DEPT_LOCATIONS, PROJECT, WORKS_ON, DEPENDENT} and its constraints.

E.g. STUDENT(Name, Ssn, Home_phone, Address, Office_phone, Age, Gpa) is a schema of degree 7. The attributes can also be written with their types: STUDENT(Name: string, Ssn: string, …, Gpa: real). t[Ai] or t.Ai is the Ai value of t; t[Au, Aw, …] is a subtuple.

Characteristics of relations

  1. Tuples have no order. A relation is a set; the order in which rows are displayed is logically irrelevant (in SQL an order is guaranteed only by ORDER BY).
  2. The order of values within a tuple: matters under the first definition (tuple = an ordered list); does not matter under the alternative definition (tuple = a set of (attribute, value) pairs). The book mostly uses the first definition.
  3. Values are atomic (indivisible): the flat relational model. Composite and multivalued attributes cannot be stored directly; composites are split into their parts, multivalued ones are moved to a separate relation. This assumption is known as first normal form (1NF).
  4. NULL: the value is unknown, not applicable, or exists but has not been entered yet. It has different meanings and causes problems in comparisons (the three-valued logic of Ch 7).
  5. Interpretation: a relation schema can be read as an assertion; each tuple is a fact, an instance for which a predicate is true. Relations represent both entities and relationships.

Table ≠ relation, exactly. Because a formal relation is a set, the same tuple cannot appear twice. SQL tables, however, can contain duplicate rows if there is no primary key or a query result has no DISTINCT (a multiset / bag). You will meet this again in Ch 6.

Constraints

  • Inherent model-based (implicit): come from the model itself. E.g. the same tuple cannot appear twice in a relation.
  • Schema-based (explicit): expressed in the schema with DDL: domain, key, NULL, entity integrity and referential integrity constraints.
  • Application-based (semantic, business rules): cannot be expressed directly in the schema; enforced by application programs or with triggers/assertions. E.g. "an employee's salary cannot exceed their supervisor's", "an employee can work at most 56 hours a week".

Also: data dependencies (functional and multivalued dependencies, for normalization in Ch 14–15), state constraints (static: must hold in every valid state) and transition constraints (dynamic: about state changes; e.g. "the salary can only increase").

Domain constraint

In every tuple the value of each attribute A must be an atomic value from dom(A): types (INT, VARCHAR(15), DATE…), subranges, enumerated values.

INSERT INTO WORKS_ON VALUES ('123456789', 3, 1000.0);

Key constraints

TermDefinitionIn EMPLOYEE
Superkey (SK)A subset of attributes such that in no valid state do two distinct tuples have the same values for SK: t1[SK] ≠ t2[SK]. Every relation has at least one superkey: the set of all its attributes.{Ssn}, {Ssn, Lname}, {Ssn, Fname, Bdate}, all the attributes…
Key (minimal superkey)(1) is a superkey, (2) is minimal: if any attribute is removed it is no longer a superkey. A key is a time-invariant property of the schema.{Ssn}
Candidate keyA relation can have several keys; each one is a candidate key.In CAR, {License_number} and {Engine_serial_number}
Primary keyThe candidate key chosen to identify tuples; underlined in the schema. Usually the smallest one is chosen.Ssn
Unique key (alternate)The other candidate keys, not chosen as primary; UNIQUE in SQL.Dname in DEPARTMENT (Dnumber is primary)

Superkey ⊇ key. Every key is a superkey; a superkey is a key only if it is minimal. Adding an attribute to a superkey always gives a superkey again. {Ssn, Lname} is a superkey but not a key, because when Lname is removed the remaining {Ssn} is still unique.

Try it: a superkey check

Choose a table and some columns; the tool looks at today's data to see whether two rows have the same values in the columns you chose. If a duplicate is found, the set is definitely not a superkey. If none is found, that is only a hint: a key is a constraint that holds for all possible states and cannot be proved by looking at the data alone.

The NULL constraint and entity integrity

  • NOT NULL: an attribute is not allowed to be NULL (e.g. every student must have a name).
  • Entity integrity constraint: no primary key value can be NULL. Because the PK is used to identify tuples; if two tuples had a NULL PK, they could not be told apart. (No part of a composite PK can be NULL.)

Referential integrity and foreign keys

Consistency between two relations: a tuple in one relation must refer to an existing tuple in another relation.

A set of attributes FK in R1 is a foreign key referencing the primary key of R2 if and only if: (1) the attributes of FK have the same domains as those of PK; (2) for every t1 in R1, either there is a t2 ∈ r(R2) with t1[FK] = t2[PK], or t1[FK] is NULL. R1 is the referencing relation, R2 the referenced relation.

  • An FK can also refer to the PK of its own relation: EMPLOYEE.Super_ssn → EMPLOYEE.Ssn (a recursive relationship).
  • An FK can be part of the PK: in WORKS_ON(Essn, Pno, Hours) Essn and Pno are both part of the PK and FKs. In that case they cannot be NULL (entity integrity).
  • In a schema diagram an arrow is drawn from an FK to the PK it refers to (Figure 5.7 in the book).

Update operations and constraint violations

There are three basic update operations: Insert, Delete, Update (Modify). Each can violate some constraints. The boxes below are exactly the examples in Section 5.3 of the book and run on COMPANY's starting data (click the table names above a box to see their rows). Run them all in order: you will see which constraint the DBMS enforces, and with which message. (Reset database when needed.)

Enough SQL to read the commands in the boxes (details in Ch 6):

  • INSERT INTO EMPLOYEE VALUES (…) adds a row. The values are written in the order of the table's columns: (Fname, Minit, Lname, Ssn, Bdate, Address, Sex, Salary, Super_ssn, Dno). So the fourth value in Insert 1 (NULL) is Ssn, and the 4 at the end is Dno.
  • DELETE FROM T WHERE condition deletes the rows that satisfy the condition.
  • UPDATE T SET column = value WHERE condition changes the column in the rows that satisfy the condition.

The error message is written as in the MySQL client: ERROR 1062 (23000): …. The number is MySQL's error number: 1062 key (duplicate), 1048 cannot be NULL, 1452 / 1451 foreign key (inserted row / deleted row), 1264 value out of range.

Insert

Can violate all four constraints: domain (the value is not in the domain), key (the PK or UNIQUE value already exists), entity integrity (the PK is NULL), referential integrity (the FK refers to a value that does not exist in the referenced relation). On a violation the default behaviour is to reject the operation (and tell the user why).

Because MySQL makes primary key columns NOT NULL automatically, the message of Insert 1 says "non-nullable" (1048); its name in the book is an entity integrity violation.

INSERT INTO EMPLOYEE VALUES ('Cecilia', 'F', 'Kolonsky', NULL, '1960-04-05',
       '6357 Windy Lane, Katy, TX', 'F', 28000, NULL, 4);

INSERT INTO EMPLOYEE VALUES ('Alicia', 'J', 'Zelaya', '999887777', '1960-04-05',
       '6357 Windy Lane, Katy, TX', 'F', 28000, '987654321', 4);

INSERT INTO EMPLOYEE VALUES ('Cecilia', 'F', 'Kolonsky', '677678989', '1960-04-05',
       '6357 Windswept, Katy, TX', 'F', 28000, '987654321', 7);

INSERT INTO EMPLOYEE VALUES ('Cecilia', 'F', 'Kolonsky', '677678989', '1960-04-05',
       '6357 Windy Lane, Katy, TX', 'F', 28000, NULL, 4);
SELECT Fname, Lname, Ssn, Dno FROM EMPLOYEE WHERE Ssn = '677678989';

Delete

Can violate only referential integrity: if other tuples refer to the deleted tuple. The options:

  • Restrict / reject (NO ACTION, RESTRICT): reject the deletion.
  • Cascade (ON DELETE CASCADE): delete the referencing tuples too.
  • Set null (ON DELETE SET NULL) or set default (ON DELETE SET DEFAULT): set the referencing FK values to NULL or to the default. Set null cannot be used if the FK is part of the PK (entity integrity). (MySQL's standard storage engine, InnoDB, does not accept SET DEFAULT; it exists in standard SQL and in the book.)
DELETE FROM WORKS_ON WHERE Essn = '999887777' AND Pno = 10;

DELETE FROM EMPLOYEE WHERE Ssn = '999887777';

DELETE FROM EMPLOYEE WHERE Ssn = '333445555';

Update

Changing an attribute that is neither a PK nor an FK only needs the domain and NOT NULL constraints checked. Changing the PK is like deleting a tuple and inserting a new one (it affects key, entity integrity and referential integrity). Changing an FK can violate referential integrity.

UPDATE EMPLOYEE SET Salary = 28000 WHERE Ssn = '999887777';

UPDATE EMPLOYEE SET Dno = 1 WHERE Ssn = '999887777';

UPDATE EMPLOYEE SET Dno = 7 WHERE Ssn = '999887777';

UPDATE EMPLOYEE SET Ssn = '987654321' WHERE Ssn = '999887777';

The book gives this example as a key violation. But rows in WORKS_ON and EMPLOYEE.Super_ssn also refer to Zelaya's Ssn: changing the PK violates referential integrity at the same time, and the DBMS reports the first violation it meets (in this engine, the foreign key). To see the key constraint alone, do the same thing on a table nothing refers to:

-- department 5 is in Bellaire, Sugarland and Houston; moving Bellaire to Houston duplicates the key (Dnumber, Dlocation)
UPDATE DEPT_LOCATIONS SET Dlocation = 'Houston' WHERE Dnumber = 5 AND Dlocation = 'Bellaire';

Referential triggered actions: seeing CASCADE and SET NULL

In the COMPANY schema (Figure 6.2) ON DELETE SET NULL ON UPDATE CASCADE is defined for EMPLOYEE.Super_ssn, and ON DELETE CASCADE ON UPDATE CASCADE for DEPT_LOCATIONS.Dnumber. Let us see their effects. Before running the boxes, predict the result: which rows will change?

-- department 4 becomes 6; EMPLOYEE.Dno and DEPT_LOCATIONS.Dnumber follow (ON UPDATE CASCADE).
-- PROJECT.Dnum has no ON UPDATE action, so first move the projects out of the way:
UPDATE PROJECT SET Dnum = 5 WHERE Dnum = 4;
UPDATE DEPARTMENT SET Dnumber = 6 WHERE Dnumber = 4;
SELECT Lname, Dno FROM EMPLOYEE WHERE Dno = 6;
SELECT * FROM DEPT_LOCATIONS WHERE Dnumber = 6;

-- Borg has no works_on/dependent rows that block him except one WORKS_ON row; remove it, then delete Borg.
-- Wong and Wallace had Borg as supervisor: their Super_ssn becomes NULL.
DELETE FROM WORKS_ON WHERE Essn = '888665555';
UPDATE DEPARTMENT SET Mgr_ssn = '333445555' WHERE Mgr_ssn = '888665555';
DELETE FROM EMPLOYEE WHERE Ssn = '888665555';
SELECT Lname, Super_ssn FROM EMPLOYEE WHERE Lname IN ('Wong', 'Wallace');

A pattern often asked in exams: "Which constraints does this operation violate? If it violates any, what can the DBMS do?" Plan of the answer: (1) Is a PK field NULL? → entity integrity. (2) Does the PK/UNIQUE value already exist? → key. (3) Does the FK value exist in the referenced table? (For a deletion: does anything refer to this tuple?) → referential integrity. (4) Does the value fit its type/range? → domain. A deletion can violate only referential integrity; the options are restrict, cascade, set null, set default.

Other concepts

  • Transaction: a sequence of operations that read and update the database and must leave it in a valid and consistent state at the end (e.g. a money transfer). Either all of them are applied or none (Ch 20).
  • Some of the constraints (FDs, normalization) are in Ch 14–15, triggers and assertions in Ch 7.

In COMPANY's starting data, what are the degree and the cardinality of the relation WORKS_ON(Essn, Pno, Hours)?

  1. degree 16, cardinality 3
  2. degree 3, cardinality 16
  3. degree 2, cardinality 16
  4. degree 3, cardinality 8
Degree is a property of the schema (how many attributes) and does not change; cardinality is a property of the state (how many tuples) and changes with every INSERT/DELETE.
-- cardinality: the number of tuples (rows)
SELECT COUNT(*) AS cardinality FROM WORKS_ON;
-- degree: the number of attributes (columns), read from the catalog
SELECT COUNT(*) AS degree FROM information_schema.COLUMNS
WHERE  TABLE_SCHEMA = 'company' AND TABLE_NAME = 'WORKS_ON';

In the relation R(A, B, C, D), {A, B} is a key. Which is definitely true?

  1. {A} is a superkey.
  2. {A, B} must be the primary key.
  3. {A, B, C} is a superkey but not a key.
  4. {C, D} is not a superkey.
Adding an attribute to a superkey gives a superkey again, but since it is not minimal it is not a key. {A} is a proper subset of the key, so by minimality it cannot be a superkey. {A,B} may be one of several candidate keys. {C,D} may also be another candidate key; we cannot know.

An attempt is made to insert (NULL, 10, 5.0) into the table WORKS_ON(Essn, Pno, Hours). Which constraint is violated?

  1. Only referential integrity
  2. Entity integrity (part of the PK is NULL)
  3. The key constraint
  4. None; FKs can be NULL
Essn is both an FK and part of the PK. If it were only an FK it could be NULL; but no part of the PK can be NULL.
-- Essn is part of the primary key (Essn, Pno), so it cannot be NULL
INSERT INTO WORKS_ON VALUES (NULL, 10, 5.0);

Which update operation can violate only referential integrity?

  1. Insert
  2. An update that changes the PK
  3. An update that changes an FK
  4. Delete
Since a deletion brings no new value, it cannot violate domain, key or entity integrity. The only risk is that other tuples refer to the deleted tuple. An update that changes an FK can violate the domain as well as referential integrity.

Which delete option makes no sense for DEPENDENT.Essn → EMPLOYEE.Ssn?

  1. ON DELETE SET NULL
  2. ON DELETE CASCADE
  3. ON DELETE RESTRICT
  4. ON DELETE NO ACTION
Essn is part of DEPENDENT's PK (Essn, Dependent_name); it cannot be set to NULL. When the owner of a weak entity is deleted, the most natural choice for its dependents is CASCADE.
